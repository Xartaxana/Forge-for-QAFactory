### 3.2 Путь записи

```
branch_accounting.delivery_records(art) -> [record]
check_delivery.assess: records += branch_records(artifacts)      # новая функция, одна строка в assess
DV.decide([rec["kind"] ...])   # без правки
build_left_items(records, ...)                                   # правка: item_key, to_check
report_facts: блок left-branches, _requirements                  # §3.4
```

Запись: `{"text": "", "kind": K, "case": "", "ref": "BN-1", "item_key": "BN-1", "requirements": ["R-11"], "to_check": "<текст ветки>", "how": "<причина или что нужно>", "source": "branches"}`.

**Позиция правки `build_left_items` и её инвариант.** Сейчас `keys = cases or [(rec.get("requirements") or [rec.get("ref") or "?"])[0]]` — ключ по R-n сольёт две ветки одного требования, вторая `how` пропадёт. Правка: `rec.get("item_key")` читается, только когда `cases` пуст, раньше `requirements`. Инварианты: (а) запись с кейсом и любая запись без `item_key` дают те же байты пункта, что до правки (пин: существующие ключи `test_check_delivery.py`); (б) две ветки одного R — два пункта, ни одна не исчезает. `to_check` записи переносится на пункт, только если пункт его ещё не имеет; ветви `elif meta.get("path")` его не перезаписывают, потому что у пункта без кейса `meta` пуст.

**`lines` (С4).** Литерал пункта `check_delivery.py:1719` `lines` не несёт и запись §3.2 тоже: `lines` (полный список единиц/текст) копируется на пункт и в `ledger.json`; `owns` шага 3 это называет.

**`VERDICT_WITHOUT_ITEMS` недостижим для новых видов:** у записи всегда есть `item_key`. Инвариант «`after_checks` без пунктов невозможен» остаётся.

## 5. F-1 по слову оператора: сверка на настоящей задаче

На настоящей задаче нет полных прогонов эталонов и копий стендов; ни одна посылка спеки не зависит от замера на них. **Предлагаемое решение (F-1, вариант а):**

### 5.1 Источник — материал задачи и тикетов скоупа

Цепочка (слово 30.10, поправка §2): `work/ticket-snapshot.json` истории плюс `work/source-inventory.json`, `sources[]` с `relevance == "relevant"`, `status == "read"` и непустым `snapshot_ref` (kept) → `snapshot_ref` текущей ревизии (`description`, `acceptance_criteria`, `comments[].text`; `title` связанного единицей не становится) → реестр → план → кейсы → манифест. Связанный читается только через инвентарь своей истории; вложения единиц не дают. Снимок истории: `work/ticket-snapshot.json` (`description`, `acceptance_criteria[]`, `comments[]{text}`; на пути файла и вставки ключи комментария `author, date, text`, поля `id` нет (`ticket_adapter.py:55`, посылка критика); читается `text`, `G-` считается от текста, `id` не нужен). Не читаются, как и прежде: другие истории (кроме kept-связанных через инвентарь, см. выше), архив прогонов, стенды, `experiments/`. Снимок — структурные поля, а не разбор заголовков `ticket-view.md`: комментарий с текстом `DESCRIPTION` не собьёт, и в сравнительном прогоне requirement — это снимок человека, а view — текст трекера.

### 5.2 Единица и инструмент

`python "${CLAUDE_PLUGIN_ROOT}/scripts/branch_accounting.py" --units --task <T>`: единицы — пункт критерия, пункт списка, предложение описания, предложение комментария; `U-<12 hex sha256 нормализованного текста>` (нормализация: NFC, схлопнуть пробелы и переводы строк). Разбор только структурный (маркеры списка, `.!?…` + пробел/конец); никаких списков слов (FR-12). Обязательство ли — решает роль. Группа `G-<12 hex>` — один комментарий целиком: дом на группу покрывает все её единицы. Это и есть управление ценой без предела: длинная переписка стоит одну строку, а не потолок покрытия.

Единица несёт `KEY` своего тикета, id считается от текста без `KEY` (одна фраза в двух тикетах — один id, один дом, в выводе оба `KEY`). Дополнительные режимы по слову 30.10: `--images --task <T>` (картинки скоупа, поправка §4) и `--attachments --task <T>` (вложения скоупа; читатель `attachments_view`, поправка §3.1), оба листаются как `--units`.

`--unhomed --task <T>` печатает единицы, ещё не имеющие дома (дверь при длинном отказе); листается как `--units` (`--page`). У `--units`, `--unhomed` и строки отказа текст единицы режется по символам данными (`unit_text_shown`), id целиком (замер: предложение в 979 символов) (Б4).

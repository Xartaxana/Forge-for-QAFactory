## 2. Почему сеть форджа пропустила блокеры (разведка t-356, прочитано из кода и тестов)

Шесть повторяющихся причин — это и есть классы, которые чинятся:

| # | Причина | Пример из прогона |
|---|---|---|
| A | Тест кормит читателя рукописным входом, а не тем, что пишет сегодняшний писатель | Формы S3/S4 велят роли писать `<P-n>` (`handoffs/s3-strategist-to-designer.yaml:52`), читатель принимает только `TS-n` (`contract.py:3052`, `s5_precheck.py:79`); все тесты пишут `TS-1` руками |
| B | Тест закрепляет поведение, которое владелец потом назвал дефектом | Срезка слов человека до 240 символов закреплена `test_brief_pack.py:2428-2440`; «никакое слово не снимает отказ» — `test_row_fields.py:370-378` (против P13) |
| C | Шов под тестом заменён заглушкой-лямбдой | `stage_review_exhausted` подменён в четырёх тестах; какие ходы предлагаются человеку, не проверяет никто |
| D | Тесты цикла драйвера выключают формы передач | `story_run_common.py:201` `handoffs.required = False` — приёмка по форме в цикле не исполняется |
| E | Аудит «состояний без хода» считает места в коде драйвера, а не состояния и виды отказов | `audit_factory.py:1640-1714`: `row-fields-missing` и отказ `stage_done` вне его досягаемости |
| F | Сети «писатель — читатель» сверяют имена полей, а не значения | `test_stage_joints.py:1-13`, `design/architecture.md:236` |

Вывод: подход «роли + код + проверки» не опровергнут, но фордж проверял, что узел сделан по правилам и что код
согласован сам с собой на придуманных входах. Ни один слой не подавал настоящий выход одной стороны на вход другой и
не мерил результат фабрики против чего-то внешнего.

## 3. Что строим (слои до живого прогона)

Живой прогон остаётся приёмкой (UAT). До него блокеры ловят четыре слоя, от дешёвого к дорогому.

### П1-а. Круг «писатель → читатель» на сегодняшних формах (причины A, F)

- Каждая форма, которую пакет даёт роли (`handoffs/*.yaml`, контракты артефактов, шаблон кейса, ключи передач),
  заполняется кодом по её же подсказкам (`<P-n>` → `P-1`) и подаётся КАЖДОМУ читателю этого поля: регулярки, валидаторы,
  гейты выхода, `stage_done`.
- Обратный ход: для каждого поля, которое читатель ТРЕБУЕТ, назван писатель — форма роли или скрипт — и показано, что
  он умеет его произвести для каждой строки таблицы языков и раннеров (иначе `obligation_refs` для `.spec.ts`).
- Один параметризованный тест: строка = (поле, писатель, читатель). Красная строка называет пару.
- Правило на будущее: вход читателя в тесте строится писателем, не руками; число рукописных входов — счётчик,
  который только убывает.
- Ловит из прогона: FV1-1, FV1-14, FV1-19 (два дефекта из трёх), FV1-22 (поля приёмки). Поправка 13.11 по черновику
  П1-а: FV1-18 этим слоем не ловится (место — П1-б / П2-д), FV1-12 — не поле формы, а расхождение двух копий, ждёт
  своего узла.

### П1-б. Сухая стори: весь цикл драйвера на заглушках ролей, формы ВКЛЮЧЕНЫ (причины C, D, E)

- Драйвер проходит S0…S9 на маленькой синтетической стори; роли — заглушки, чьи выходы собраны из сегодняшних форм
  (тем же заполнителем, что в П1-а); дирижёр — детерминированная заглушка. Без модели, минуты на CI.
- Обход выходов: для каждого вида отказа, который код умеет выдать, и каждого вида вопроса с каждым закрытым вариантом
  ответа драйвер ставится в это состояние, и проверяется: у предложенного варианта есть исполнитель, после исполнения
  состояние ДРУГОЕ, слово человека снимает любой отказ (P13). Тот же вопрос в третий раз — красное.
- Виды отказов и вопросов берутся из кода перечислением (реестр), а не из списка в тесте.
- Ловит из прогона: FV1-2, FV1-6, FV1-7, FV1-8, FV1-13, петлю FV1-22, часть FV1-20.

### П1-в. Табло прогона: трение и сравнение меряет код (FR-55, P11)

Как должно работать в идеале:

1. Эталон: стенд MyBooks с известными багами (24 карточки, таблица правды) и 2–3 стори. Свободный агент проходит их
   один раз на версию модели (12 минут) — это планка.
2. Каждый живой прогон фабрики заканчивается табло, которое собирает КОД из файлов прогона, без ручной тетради:
   время по частям (роли, дирижёр, шаги кода, ожидание, вмешательства), доля первой попытки и переделок, возвраты по
   каждому гейту с временем модели после них, вопросы человеку, размеры брифов против потолка, а по качеству —
   найденные баги из известных, красные тесты на баги, ложные баги, «не удалось проверить».
3. Табло лежит в репозитории рядом с прошлыми (деньги — только в чате, P18) и сравнивается с планкой агента и с
   прошлой версией фабрики. Ухудшение строки — находка автоматически.
4. Нормы-бюджеты, которые только ужесточаются: доля переделок, возвраты на гейт, вопросы человеку, стена относительно
   агента. Гейт, чьи возвраты стоят дороже того, что он ловит, — дефект по имени (сегодня это `row-fields-missing`).
5. Те же счётчики печатают сухая стори и дымовой прогон стадии — трение видно до живого прогона.
6. Релиз в `QAFactory` требует табло последнего прогона без красных норм; калибровочная проверка читает его.

Что есть: данные уже пишутся в `driver-runs.jsonl`; скрипт замера t-357 — прототип. Чего нет: связи замера с каким-либо гейтом;
возвраты по гейтам записаны только свободным текстом. Поправка 13.11 (черновик П1-в, §0): `driver-timings.jsonl`
существует в живой папке состояния прогона — неполной была копия в репозитории, так что время шагов кода измеримо.

### П2-г. Дымовой прогон одной стадии на настоящей модели

- Одна стадия, настоящая роль (Sonnet), вход — записанный выход предыдущей стадии. Минуты и центы, не часы.
- Запускается перед релизом для стадий, чьи роль, бриф, форма или гейт менялись. Проверка: гейт выхода пройден с
  первой попытки, без возврата.
- Ловит то, чего не видят заглушки: что настоящая роль пишет по сегодняшней форме, раздутые брифы, критика без проб
  (FV1-20), пакет из 18 вопросов (FV1-9).
- Нужны деньги — решение владельца (вопрос 1).

### П2-д. Зоопарк стендов для проб среды

- Формы входа и ответа стенда — строки данных, снятые с настоящих стендов (NextAuth с csrf, форма с 405, health ok).
  Каждый сюрприз настоящего стенда — новая строка.
- Отрицательный факт пробы («вход кодом невозможен») без положительного контроля записывается как «не установлено»,
  а не как факт (FR-41, FR-59).
- Ловит: FV1-5, FV1-15, FV1-17, FV1-18, FV1-16.

## 5. Скорость (после блокеров)

Замер показывает: даже без единого возврата первая попытка ролей — 50 минут против 12 у агента. Значит, кроме
блокеров, дорога сама нарезка. Направления, каждое — отдельное решение после табло, не сейчас:

- возврат роли за полями формы заменить заполнением кодом (16 возвратов одного гейта — данные, не суждение, P27);
- ранний взгляд на стенд: агент половину времени исследует стенд, фабрика до S6 его не видит (вопрос владельца
  12.11 про S2 — «первый взгляд, смоук»);
- путь по размеру стори: маленькая стори не проходит всю лестницу бумаг;
- два зависших вызова (13 и 10,5 минуты) — разобрать отдельно.

Цель, которую проверяет табло: качество не ниже агента по каждой строке, стена первой попытки — не больше чем вдвое.

### A.4 Error direction of the reused functions, and inputs that must stay on the safe side

`handoff_paths`, `_in_folder`, `_real` and the moved loop `handoff_candidates` go from the WRITE gate into a LAUNCH gate,
a more consequential role (a refusal blocks the dispatch itself). Allowed error direction for WRONG_FOLDER and MANY:
**the launch check may PASS a dispatch whose writes the write gate will later refuse; it must never REFUSE a dispatch
whose write the write gate would accept.** The write gate stays the enforcement; the launch check only moves the same
refusal earlier.

NO_LINE and NO_PATH are a different case `[t-371 F-A3]`: they refuse a no-write critic/designer dispatch (a report
returned as the final message) that the write gate never sees. **This promotes R11-h (`CLAUDE.md:236`) from discipline to
a code gate, on the evidence of t-337 (root `dev1.jsonl:853,856`)** — a promotion on a logged leak, which rule 10(d)
allows. Its door is the `manifest-skip: handoff -- <reason>` line; the invariant it protects: a critic/designer dispatch
never goes out without either one report path or a recorded reason for having none.

Inputs that must stay on the safe side (each is a test row):
1. The same path in two spellings (case, `\` against `/`, a `..` segment): one candidate, pass (`handoff_candidates`
   dedups by `_real`, as `_gate` does).
2. A degraded cut (text over `md_regions.MAX_TEXT_CHARS`, or a scan that raises): pass with NOTE. An unknown is never a
   launch refusal; the declared safe default is the write gate (FR-59).
3. A `handoff_gate` import that fails: pass with NOTE.
4. A kind in another spelling (`" Critic "`): checked (normalized). A kind that is not exactly a gated word
   (`foo:critic`, `critic-2`): not checked, which matches the write gate (`handoff_gate.py:140-142`).
5. A path in a subfolder (`docs/tasks/specs/reviews/x.md` for a designer): refused; the write gate refuses it too.
6. A critic dispatch with an absolute `owns:`: checked anyway; the write gate gates a known critic regardless of owns
   (`handoff_gate.py:141`).

**What a band does and does not prevent `[t-371 C-3]`.** A band prevents a collision only after the writers know about
each other. On 13.11 the first round (t-347/t-348/t-349, lines 885-892) happened before either session knew, and is NOT
prevented by a band. The second round (lines 900-908) is: once S2 has opened a closed band at a distance from the main
sequence (C-1), S2 composes from its band while S1 stays on `max+1`, and there is no shared counter to race on between
reserving an id and writing the line. A RAISE-only band (the finding's `id_band_from`) does not serve two writers of one
file at all: after a raise, both sessions compute the same `max+1` again. The first round is what C-F6 (i) aims at: a
NOTE that tells each session the other exists (§C.3 step 7), with the residual stated in §C.5.

### C.2 The field

`id_band`, an optional string on ANY event (C-F1 (a)). Two forms, each end ASCII digits only, 3 to 9 of them
(`[t-371 C-4]`):
- closed `"t-A..t-B"`: reserves the ids A…B for the writer who declares it, issued in order A, A+1, … At most
  `BAND_MAX_SIZE = 1000` ids.
- open `"t-A.."`: raises the file's own sequence; its next brand-new id is `t-A` (the finding's `id_band_from`).

`top` = the maximum of every task id seen, every closed band's end, and every open band's `A-1`. Both forms: `A > top`,
and `A - top <= BAND_JUMP_MAX = 10000`. A closed band also needs `A >= top + BAND_GAP_MIN` with `BAND_GAP_MIN = 50`
`[t-371 C-1]`: a band protects only by DISTANCE from the main sequence — a band adjacent to `top` puts its first id where
the other writer's next `max+1` (composed before the band line lands) will fall, and the 13.11 race recurs at the band
start. The open form keeps `A > top` only (a raise has no other writer to keep away from).

### C.4 Refusal texts (FR-1/FR-2/P15)

- FORM (`band_not_string`, `band_not_form`): `{tag}: id_band = {v!r} is not "t-A..t-B" (a closed band: at most 1000 ids
  reserved for this writer) or "t-A.." (an open band: this journal's ids go on from t-A), each end 3 to 9 plain digits;
  write e.g. "t-450..t-499" -- fix the value, or leave the field out (it is optional) (rule 9e)`
- REVERSED: `{tag}: id_band = {v!r} ends below its start -- write the lower id first, e.g. "t-450..t-499" (rule 9e)`
- TOO_BIG: `{tag}: id_band = {v!r} holds {n} ids; a band holds at most 1000 -- declare a smaller band, and a new one when
  it is used up (rule 9e)`
- BELOW: `{tag}: id_band {v} starts at or below t-{top:03d}, the highest id or band already in this journal -- a band may
  only start above everything issued or reserved, or it could hand out an id twice; start it at t-{s:03d} (rule 9e)`
- NEAR `[t-371 C-1]`: `{tag}: id_band {v} starts {gap} ids above t-{top:03d}; a closed band starts at least 50 ids above,
  or the other writer's next id can land on its first id before this line is written -- start it at t-{s:03d} (rule 9e)`
- JUMP: `{tag}: id_band {v} starts {gap} ids above t-{top:03d}; at most 10000 -- start it nearer, at t-{s:03d} (rule 9e)`
- NOVELTY (replaces `:946-955`): `{tag}: task_id novelty violated -- got {task_id}; the next new id is t-{main:03d} (this
  journal's sequence)[ or t-{n:03d} (band t-A..t-B)]…[; band t-A..t-B is used up -- open a new band at t-{s:03d}] --
  re-read the tail right before writing (python tools/journal_keys.py where prints every next id); a second writer of
  this file opens its own band: id_band: "t-{s}..t-{s+49}" on its first line (rules 9a, 9e)`

`s` is `suggested_band(top)` in every text (one function).

### C.5 Edge behaviour, both worlds, invariants

Invariant of the door: **a band only raises or reserves ids above everything already issued or reserved. It never
lowers the counter, and it never makes an issued or reserved id issuable a second time.** Each edge below protects it.

- Before any band exists (both worlds, part 1): every journal and test with no `id_band` gives the SAME verdicts and the
  SAME `next free id` as today; the NOVELTY wording changes, its `t-NNN` value does not. `where` gains only its last
  `suggested band` line (step 1). The `t-499` filler of `dev2.jsonl:474` stays (history, never rewritten).
- After the first band (part 2): the field exists only on lines written from then on; the move that creates it is the
  first line a second writer appends with `id_band`.
- A band on the line whose own id is the band's `A` (the opening `delegated`): legal, the band applies first.
- A band on an accepted, rejected or decomposable line: legal; that line's own id is judged as today.
- The main sequence reaches a closed band: it jumps to `B+1`; adjacent bands are skipped in turn.
- An id inside a band used out of order (t-455 when the band's next is t-452): NOVELTY naming t-452.
- A band used up: NOVELTY carries the "used up" clause; the writer opens a new band at or above `s`. `where` stops
  printing a used-up band (F-C2).
- A band reserved and never used `[t-371 F-C2]`: the main sequence skips it forever (its ids are burned, harmless);
  `where` prints at most the 3 latest bands with a free id, so its output stays bounded however many bands were declared.
- Two closed bands of two writers declared one after the other: the second must start at least 50 above the first's end
  (BELOW/NEAR otherwise). Overlap is impossible by construction in one file.
- Residual — two writers who declare overlapping bands at the SAME moment `[t-371 F-C4]`: the second line meets BELOW or
  NEAR only after its dispatch already went out with a band id (the 13.11 class one level up). Door: renumber as today.
  It is rare because C-F6's NOTE has told both sessions about each other before either opens a band.
- Residual — the first round `[t-371 C-3]`: a band cannot prevent a collision between two sessions that do not yet know
  of each other. C-F6's NOTE turns it into a steer only when the peer's transcript was written within 10 minutes and the
  session reads the note before composing ids. Two sessions started in the same minute, both composing ids before either
  writes a journal line, can still collide on the first round; a peer opened in another checkout (another transcripts
  folder) is not seen; a session that ignores its band and takes `main` is not caught (no session field). These stay on
  discipline, counted by the detector (§C.7 (c)).
- The number parser is ASCII and bounded (3-9 digits) `[t-371 C-4]`: a fullwidth band (`"t-４００..t-４４９"`) is FORM, never
  the same numbers; a band of 10 or 5000 digits is FORM with no exception (`int()` is never reached on more than 9 digits).
- A malformed band on a NEW line: FORM (or REVERSED/TOO_BIG), and it does not enter the state. On an OLD line: ignored.
- A JSON `null` band: absent, no violation (as `node`).
- In a merge, each parent's form-valid bands are in the state of the tail. Independently declared bands can overlap;
  kept lines are not re-validated (`:1595-1596`); the collision WARN names the overlap (step 5).
- `--all --base` (CI) and `journal_echo`: the same `decide()`, the same verdicts; no separate code.
- Limits AT and BEYOND: size 1000 ok, 1001 TOO_BIG; jump 10000 ok, 10001 JUMP; gap 50 ok, 49 NEAR; 9 digits ok, 10 FORM;
  peer age 600 s noted, 601 s silent.
- C-F6 empty/absent: `transcript_path` absent or not a str, an unreadable folder, only the own file → no note; a folder
  with 1000 peer files → one note, 3 stems + "+997 more"; a path with spaces or Cyrillic → handled.

journal rule 9e: a band's next id is issuable only by a line that carries the band; PARALLEL SESSION note after /clear (F6-58 fix round, t-402 F1 F2 F4)

What: (F1) a closed band's next id may now be taken only by a journal line that carries that same band in its own `id_band` field (every line issued from a band declares it; repeating an already declared band is a reference, never BELOW). A new id that equals a band's next id but carries no such field is judged as a main-sequence id, so a session that took max+1 and landed on a band's id gets the novelty refusal with the main next id and one door clause: `t-451 lies in the id band t-450..t-499 of another writer; a line issued from a band carries "id_band":"t-450..t-499"`. The main next id already skips over a band that covers it. The one predicate is journal_keys.BandState.may_issue (the gate calls it; _is_issuable is gone); `where`, Journal.next_free_id and compact_snapshot keep reading BandState.issuable for the ids they print. A journal with no band behaves exactly as before; repeats (rules 9b/9d) on an existing id need no field. (F2) the 3-digit lower bound of the band form is pinned (`t-50..` is a form error). (F4) the PARALLEL SESSION note gains the suffix " (possibly this session before /clear)" when the SessionStart source is "clear" (the pre-clear transcript of the same person is then among the peers; no peer is dropped); the note's band clause now says "on every journal line you issue from it". journal_echo's repeat of the note is unchanged: its PostToolUse payload carries no `source`, so it cannot know a clear.

Why: critic t-402 found that after a band exists, a session taking max+1 lands on the band's next id and the gate passed it, so the band's owner and the main writer collided on the band's own id (13.11 race one level up); the band had to declare itself on every line it issues. A note that fires after every /clear teaches people to ignore it, so it says what it may be.

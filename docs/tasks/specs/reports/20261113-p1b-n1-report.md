## Decisions I had to take (spec gaps; Lead to confirm or return)

1. **Ratchet semantics.** The spec says "sum over group files against the base in the same files; a raise is a `raised_by` line". I read: `ratchet.<name>` is the base; rows counted = rows with that reach in the three driver-exits sections plus the walk rows (`stories/dry-1/exits`); count > base is red unless `raised_by` holds one named entry per excess row (then a NOTE); count < base is red (stale base, as `known_red.pin_problem`). `hook_layer` = number of scanned REGISTRY records (77), carried in `hooks.json` (a sixth group file, no rows); a walk row with reach `hook_layer` is red.
2. **Where the label ledger lives.** The spec does not name the file for P1-b's `known_red` section ("the file the consumer's spec names"). I put it at `fixtures/driver-exits/known_red.json` (`known_red: {}`, `pins.known_red: 0`), excluded from the group glob together with `classes.json`; `--check` reads it through `known_red.load` + `pin_problem`; `--judge` reconciles `{id: bool}` with it. If it should live elsewhere (e.g. beside the walk rows), that is a move of one file and one constant (`NOT_GROUP`, `known_red.json` default).
3. **"class unknown" is printed and counted, not red**, for the three `ask_person` routes `story_budget`, `executor`, `readiness`: spec E19 says red, the dispatch said printed and counted, and no carrier names their source (their texts come from `story_budget.py:263` / contract / waiver, not a registry id or a joint check; the registry has 25 operations and none is theirs). `class_of` returns `class unknown`; `check` prints `NOTE class unknown: 3 (...)`. QUESTION for Lead: name their `class_source`, or make E19 red and accept 3 discrepancies until named.
4. **Keyless kind rule** is the spec's literal "the same call" (`closed_question`/`priced_section` nested in the `Person(...)`/`site_seam_person(...)` arguments). Consequence: kinds whose text is built in a helper (`repair_limit`, `exit_limit`, `walk_*`, `data_change`, `s1_gap`, ...) are listed as keyless although a key exists in the helper. This errs toward more rows (red side). If Lead wants "key anywhere in the enclosing function", the rule is in `_PersonSites.visit_Call`.
5. **Groups of the rows.** Each route/joint/kind got a group by its stage (s0, s1-s4, s5, s6-s9); a subject spanning several groups (the exit_gate family, generic dispatch routes, `unmatched`, `known_false`) is in `gates`. All 87 rows are `unwalked` (N4 shrinks them to 0 per group).
6. **`same_ask` dispatch normalisation** keeps stage and role and drops the number (`S5-qa-automator-4` and `-5` are one ask; a different role is another): replacing the whole id by `<dispatch>` would merge roles.
7. **Stage joints reader.** `stage_joints.py` has no reader function of its own; its walker reads `null_outcomes.load_data(stage_joints.DATA)`, which is what `scan_joints` uses.

# t-925 — how GROUNDING works in the QA Factory package today (recon digest)

Scope: `ai-packages/qa-factory/` (P = that path), read-only. Nothing was run. "code gate" = a script refuses; "prompt only" = role/phase text, no refusal; "advisory" = code exists but cannot block.

## Summary for the owner (по-русски)

1. Реализацию (MR/diff) фабрика читает на S1 (скаут) и S2 (тестировщик требований); дальше S3–S9 диф сами не читают — только через регистр, план и кейсы.
2. Диф превращается в требования двумя путями: AC → строки регистра, и «производные» строки `derived`, которых нет в AC. Для производных, живущих только в диффе, есть настоящий кодовый гейт (P20): строка «было/стало» + вопрос человеку; пока он не ответил, ожидание в тесте открыто (`unresolved`).
3. Кодовых гейтов, что «каждый AC тикета есть строкой в регистре», НЕТ. Есть счётчик `by_source` и «строка регистра → строка плана → кейс → исход» (проверяется кодом), но от самих AC тикета до регистра цепочка держится на тексте роли.
4. Единственный кодовый гейт чтения диффа на S2 — «каждый НОВЫЙ production-файл диффа должен быть назван в строке `derived`» (`exit_gate.grounding_errors`); слабый: по имени файла, только новые файлы, правки существующих файлов не ловит.
5. Шаг «сверить MR с требованиями до тестов: неверный MR / рефакторинг сверх требований» как отдельная стадия или поле формы — ОТСУТСТВУЕТ. Ближайшие остатки: `judge_diff.py` (пометка hunk как `unrelated`; нигде не вызывается и по умолчанию выключен), AC/code-conflict halt скаута (prompt only), `diff_accounting` в передаче S2→S3 (строка на файл, содержимое не проверяется).
6. Риск, увиденный в коде, в план не попадает по форме: полей `hotspot`/«suspected defect» нет. Есть `derived_risk` (слово в форме передачи S2, код его не читает) и `defect hypothesis` строки плана (пишет стратег, диф ему не отдаётся целиком).
7. `diff_pass.py` — только нарезка диффа для скаута; `diff_scope.py` — «комментарий или код» для перепрогона критика. Ни один из них риска не оценивает.
8. FR-22 (расхождение с требованием без падающего теста → баг): дороги до `bugs/` нет; на гейте B фабрика лишь честно печатает «N расхождений, никто не завёл» (`gate_brief.py:2689`).
9. История: идея «до тестов сверить код с требованиями» жила как профиль `refactor-parity` + снимок «до», вынесенные в v1 решением 2026-09-11 (A4); вернулся только `baseline_contract` (доказательство «до» для одного кейса). Последний носитель — kb `06-roadmap` п.3 (дорожная карта, не сделано).
10. Подробности, строки и контроли — ниже; решений о том, что строить, здесь нет.

### Does ANY stage read the implementation and compare it with the requirements?

Reads the diff: S1 scout (`diff_pass.py`, bounded diff in the bundle `context_bundle.py:30`), S2 tester (must read every hunk: `s1-scout-to-tester.yaml:109`, `brief_pack` "read EVERY hunk", CHANGELOG 0.7.x line 954). Compares diff with requirements: only (a) S2 tester by judgement (contradiction matrix, behaviour claims, `derived` rows), (b) S1 scout's AC/code-conflict halt (prompt only). After S2 the implementation is exercised only through tests (S5–S6); no stage re-reads the MR against the register. S5 never mutates product code (red probe mutates the test assertion: `probe_by_code.py`).

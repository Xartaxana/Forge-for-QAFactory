## Decisions I made that the spec did not name (flagged for acceptance)

1. `linked_documents` itself is a non-goal and needs an existing `text_ref` file; a ref-less text has none. I wrote a sibling `linked_documents_of_texts`
   that reuses `_listable`, `path_candidates`, `declared_roots`, `contained` (no copy of the predicate) but has its own ~15-line loop (copy of the
   candidate loop shape). `_recorded_read_refs` repeats 4 lines of `linked_documents`. A shared core would touch `linked_documents` (non-goal): question 1.
2. Origin of a ref-less text's `linked_document` row = the key of the text as the existing scanners name it (`mention:description`, attachment name);
   the spec fixed the origin only for recorded documents (`mention:document:<ref>`). Question 2.
3. A name is tried against each root as `join(root, name)` (leading `/` dropped), kept only when it stays `contained` in THAT root (so `..` out of a root
   is no row even if the target lies in another root) and `_listable` accepts it. Nested roots (a code repo inside the project) give the same ref twice -> one row.
4. S0 texts scanned for links = exactly the texts `build_references` scans (summary, description, comments); acceptance criteria are not scanned (neither keys
   are by `build_references`). Question 3 (add AC?).
5. The cut for S0/attachments is said on stderr (`source_inventory: more than 500 names in <origin> (<n>): only the first 500 were checked for linked
   documents`), as A-3 says it; no listing is printed for these kinds (no role-facing output channel exists in those writers), rows are not capped beyond the 500 candidates (as A-3 F7).
6. A write happens in (a) only when `TL.references` returned a row (as A-3's `if found["rows"]`).
7. Nesting: like A-3, `path_candidates` is characters only, so a link inside a code fence or a quote IS a candidate (kept, a row covers it).

## A.3 Design (on the recommended options of F-A1..F-A3)

Owners (P27, AR-29). Code lists the documents at the places a config row names. That is data, a read of a folder. The
scout decides which document carries a requirement for the story (judgment) and records it with the existing
`record-source`. The S2 tester judges the requirements. Onboarding judges where documents live. The person is not asked
where docs are when they are on disk (P5, FR-50).

inside it. The kinds table decides which row gets a listing, through its capability key `route == "grep"` (a place on
disk). A kind name is never used for that (AR-1).

read by a file route), AR-8/FR-15 (paths handed, not searched), AR-21/FR-49 (a large doc shown with its size, never cut
silently), AR-26/P23 (docs are a requirement source like the ticket), AR-29 (code lists, the role judges relevance),

## A.5 Forks (Part A)

- **F-A1 — how the docs reach the story.** (a) RECOMMENDED: code lists the files at the config's document places in
  the scout's prompt (A-2). The scout reads them and records what can carry a requirement with the existing
  `record-source`. Links follow one rule for all texts (A-3). Evidence for (a): on the run the role DID read the one
  recorded document. The misses were the missing row and the links that were not followed. Neither is fixed by more
  code reading. Cost: two small nodes; no new inventory state. (b) Lead direction, strong form: code records every
  listed document into the inventory as a pending source. The scout must `assess` each one, and S1 cannot close with one
  pending. Cost: a new writer `record_document_pending` in source_inventory; `assess` must promote a text source to
  `read`; the S1 exit must count it; one assess call per file (25 files = 25 calls at S1). Gain: a document can never be
  silently skipped. Recommend (a) now. Take (b) as a later node if a live run shows a listed document read by nobody.
- **F-A2 — the two sinks rule (p1 :37 vs :41).** (a) RECOMMENDED: one document may feed both. What decides is what the
  sentences describe: product behaviour -> requirement source; how tests are written or run -> conventions. (b) Every
  human document goes only to conventions, and requirement sources hold only folders not read for conventions. (c) A
  config key `product_docs` separate from `requirements_sources`. Cost: a new key, a new reader, a migration (against
  one road: two keys for one action). Recommend (a).
- **F-A3 — configs onboarded before A-1 (TEMPORAL).** (a) RECOMMENDED: no migration. A-3 already makes the README's links
  readable in old configs, and a re-onboarding adds rows. (b) A readiness/doctor line where a `code_repos` entry has no
  `requirements_sources` row inside it (a join of two config keys, class `xref`, owner data). It informs and never
  refuses. Cost: one readiness row and a table row. Recommend (a), and (b) only on a second live-run miss.

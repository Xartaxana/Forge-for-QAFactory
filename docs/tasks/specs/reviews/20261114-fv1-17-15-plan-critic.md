## Key 5 — safety of the attempts

- Lockout: per road one submit (good), but nothing bounds the attempts ACROSS roads in one run, nor stops after the
  account was judged. With a wrong password a roads run can fail the same account at (a), (b) and (d), and the role is
  told to re-run roads after recording fields. Amendment: a `credentials_refused` answer ends every later road that
  sends the real secret (`not_tried`, why "the account was refused at road N; fix the account first"), a `throttled`
  answer ends the run, and the card states the per-run budget (at most one real-secret failure + the one junk-secret
  negative run) (B3).
- Secrets: `_who_answered` redacts only the `secrets` tuple it is handed. A form road holds three more secret
  values: the csrf token, the cookie values, and the session body (it echoes the user's email/name). The card says
  "never in a receipt" but names no enforcement point: every `answer_of`/`_who_answered` call of a form road passes
  `(user, secret, csrf value, every cookie value)` (A9). No credential is put in a URL (body only; csrf in the body;
  `_safe` strips userinfo/query from every printed url). Axis 5 "Redactor <-> secret guard": `stand_access._safe` is a
  named member of the safe-URL survivor; the roads output must print urls only through it — the card says "names
  only", it must say "urls through `_safe`" (A9).
- The negative control: the junk secret goes in through `values` -> the child env. A harness that loads its own `.env`
  with override would still see the real secret and pass -> `wrong_door` on a working road. The direction is safe
  (never `in`), but the word is wrong: see key 6/A4.

## Key 6 — direction of error, awkward host answers

Allowed direction (correct in the spec): a real `credentials_refused` or `in` may be read as a non-`in` failure; never
the reverse. Reading a real wrong door as `credentials_refused` sends the person to fix a good password forever; reading
a refused account as `wrong_door` costs a re-onboarding that then asks. So `wrong_door` is the allowed sink — but then
it is an UNKNOWN, and FV1-15 words it as a FACT ("is not a login endpoint", L0 remedy, the question sentence). FR-41/AR-28
breach (B5 covers the wording). Probe (in-process, `http_client.classify` on wave13):

| Host answer | classify kind | spec answer | correct? |
|---|---|---|---|
| 401, empty body, no headers (local_login seam) | `empty` | no H row -> catch-all `wrong_door` | a protected path AND a refused account both answer this: UNKNOWN; worded as "not a login endpoint" = false half the time; today it says "was refused" |
| 403 `{"message":"CSRF token missing"}` | `service` | H5 -> `credentials_refused` | WRONG direction: CSRF/role/IP refusals are not the account judged (B5) |
| 401 `{"detail":"Invalid credentials"}` | `service` | H4 `credentials_refused` | ok |
| 400 `{"error":"invalid_grant",...}` (OIDC wrong password) | `service` | H8b `credentials_refused` | ok |
| 200 HTML containing "token" | `page` | H15 `wrong_door` | ok (token_value parses JSON only) |
| 403 HTML with a JSON-looking title | `unclear` | H4p `wrong_door` | ok |
| 200 non-UTF-8 body | `ok` | no token -> `wrong_door` | ok |
| JSON `{"token": true}` / `{"token": [1]}` | — | `stand_access.token_value` returns `"True"` / `"[1]"` -> `in` | WRONG: `in` without a token (A3) |
| 302 to `...?error=CredentialsSignin` | `redirect` | H3 reads `refused_marker` in Location | infeasible as written: `Answer.location` has the query stripped (B4) |

Timeout / TLS / reset / DNS -> `no_answer` (the `no_answer` table already names them; reuse, B6). Huge body: cut JSON
does not parse -> never `in` (holds; the limit needs an AT row as well as BEYOND, key 12). Stalled 2xx body: `_open`
raises TimeoutError on `unreadable` 2xx; the new `_exchange` must keep that rule or H11 silently becomes `wrong_door`
(A8).

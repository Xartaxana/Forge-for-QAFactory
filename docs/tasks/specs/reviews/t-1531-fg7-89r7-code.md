**J1 (blocker, part of the one blocker): PowerShell takes a bare CR as a statement separator; the splitter does not.** Surface: the statement splitter `_SEP_RE = r"[;&|\n(){}]"` (:300). In PowerShell's tokenizer `\r` alone is a newline, so `echo x<CR><call>` is two statements, but the reader sees one statement with an `echo` head: a MENTION. No table row matches. EXECUTED (the call replaced by `Write-Output RAN..`):
  - `echo x\r<call>` (PowerShell, `-Command`): live deny, r7 PASS. Windows PowerShell printed `x`, then `RANPSCR`. The same text from a `.ps1` file printed `RANPSFILE`.
  - `powershell -Command 'echo x\r<call>'` (a nested payload): live deny, r7 PASS. Printed `RANPSP`.
  Neighbours walked on the same surface: NEL U+0085, U+2028, U+2029, VT and FF in PowerShell; CR, VT and FF in Bash. Each was executed: none splits, so each is a correct pass. CRLF denies.
  One case is not executed: Bash `echo x \<CR><LF><call>`. The reader's join `\\\r?\n` (:1393) makes it one `echo` statement, and r7 passes it. Git Bash here ignores the CR (it printed `x echo RANCRLF`, one statement), so the join is right on this host. On a stock Linux bash `\<CR>` quotes the CR, so the next line would run. That is unverified here: estimate, not verified.
  Fix, the wider form: any `\r` in the text is uncertifiable (one row). It covers both dialects, and its cost is a false deny only when the call is named, which equals live.

**J2 (blocker, part of the one blocker): PowerShell argument mode evaluates expressions inside a MENTION statement.** Surface: the MENTION certification of a PowerShell statement whose head is `echo` / `cat` / `select-string` / `write-output`. Its arguments can hold code the engine runs. The `{` is not split (it does not stand alone), and a method's string argument is masked as a quote. EXECUTED (live deny, r7 PASS each):
  - `echo {<call>}.Invoke()`: printed `RANSB` (also `Write-Output {..}.Invoke()` -> `RANSBW`, `.InvokeReturnAsIs()` -> `RANSBR`)
  - `echo @{a=<call>}` (a hashtable value is a pipeline): printed `RANHT`

  - `echo $ExecutionContext.InvokeCommand.InvokeScript('echo' + ' x;<call>')`: printed `RANIS`. After the `(` split, the argument statement's first word is the quoted `echo`, so it is read as a MENTION too.
  Neighbours walked: `echo (<call>)`, `echo @(<call>)`, `[scriptblock]::Create(...).Invoke()`, `NewScriptBlock(...).Invoke()` and `InvokeScript('echo x;<call>')`. All of these deny.
  Fix, the wider form: in PowerShell, a `{` or a member call (`.name(` / `::name(`) in the text is uncertifiable. The Lead may pick something wider, for example any `(` / `{` inside a PowerShell MENTION statement. One row per sub-class.

**J3 (blocker, part of the one blocker): a MENTION head that does not name the trusted program.** Surface: `_cmd_name` (:583-585) takes the basename, and the MENTION test (:1470) accepts `cmd in _MENTION_HEADS` after the assignment prefixes and the CHILD heads (`env`) are stripped.

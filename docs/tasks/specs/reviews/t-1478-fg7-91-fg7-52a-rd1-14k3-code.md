## Node 1: FG7-91 (origin/main...01ab362f), against d-1470 E1-E7 and the Round 2 E4

### Findings

**F1 (blocker): E6 counts a dispatch run of ANY ref as "a run for this head", so the default `start` (ref main) starts nothing.** The defect is in the run-lookup surface of `ci_read.py start` at `tools/ci_read.py:229`. That line filters on `head_sha` only. A workflow_dispatch run is always dispatched on ref `main` (`ci_read.py:300` body `{"ref": "main"}`; canon.yml:13 "head_branch of a dispatched run is always main"), so its `head_sha` is main's tip, whatever `inputs.ref` it canonises.
- Failing scenario: the Lead runs `start --ref worktree-agent-x`, which creates run 91 with head_sha = main@H. Later, while main is still at H, the Lead runs `start` (ref main). `commits/main` returns H. Then `runs?head_sha=H` returns run 91, and the tool prints `canon.yml already has a run for main at H: 91 ...; nothing started`. The main canon never starts, and the line names another branch's run.
- Probe: one row appended to a scratch copy of test_ci_read.py. It fails with `AssertionError: canon.yml already has a run for main at ab12cd34: 91 https://gh/runs/91; nothing started / assert 0 == 1`.
- The same fault hits any branch whose head equals main's head (a freshly cut agent branch), and a `--ref release` that is fast-forwarded to main.
- The neighbouring classes of this surface were walked. A failed lookup is handled (note plus start). Any `--var` skips the lookup. A sha ref works through `commits/<sha>`.
- Fix: keep only `r.get("event") == "push"` (and optionally `head_branch == ref`) at :229. Push runs exist only on `worktree-agent-**`, so main and release never match. Add a row to the E6 table: a `workflow_dispatch` run at the same head is dispatched.

The check "the id equals some closed band's next id" has nothing tying it to the line that issues it. It is a pair detector that is not scoped (critic rule 15). Sequence, run on the new code (probe S1, trail):
1. HEAD `delegated t-356`.
2. Session B: `delegated t-450 id_band "t-450..t-499"` (scout). Legal.
3. Session A follows today's CLAUDE.md text ("max(t-NNN)+1"), so max+1 = **t-451**: `delegated t-451` (builder). **PASS**, because 451 is the band's next id.
4. Session B, whose dispatch text already says t-451: `delegated t-451` (critic). **PASS** by rule 9b, a continuation by another agent (C-F5).
Result: the band's owner and the main writer collide on the band's own id, and the file is valid. The old gate refused step 3's twin in a world with no band. The same thing happens once the main sequence reaches a band edge: P10, a plain `delegated t-500` passes as band t-500..t-549's first id. §C.5 names only the mirror residual ("a session that ignores its band and takes main"). This one is not named, and it is the likelier one, because the habit and the current rule text are both max+1.
Cheap scoping that closes it: a line that takes a closed band's next id must carry that band in its own `id_band`, so each band line declares itself. A naive t-451 then gets NOVELTY "the next new id is t-357". The band rows j1/j2/j10/j11/j18/m2 would add the field to their band-issued lines. The other option: the Lead names the residual in §C.5, and the step-9 text plus the CLAUDE.md edit (AGENTS.md is regenerated by `tools/agents_md.py`, pre-commit `--check`) land in the SAME commit as the code, never after. Surface: "who may take which next id" (the issuable predicate). Neighbouring classes walked: open band (main only, raise: not affected); main reaching the band edge (P10: same class, covered by the same scoping); cross-agent reuse (9b, C-F5: queued by the spec, §D.2 item 2); overlapping bands after a merge (F3).

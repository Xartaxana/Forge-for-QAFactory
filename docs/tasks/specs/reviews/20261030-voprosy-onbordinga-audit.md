# Вопросы онбординга: что лишнее, что никто не читает, что фабрика может узнать сама

Lead (Fable), 30.10.2026. Вопрос владельца: «Посмотри все вопросы, которые задаёт онбординг: нет ли лишних? Все ли потом используются
фабрикой? Все ли не могут быть отвечены самой фабрикой? Например, вопрос, когда стори считается протестированной, — это используется дальше?
Вопрос про рисковые области — учитывается при написании кейсов?» Карта скаута — `reports/t-1621-onboarding-questions-audit.md` (t-1621,
43 вопроса, читатели file:line, принята по следу; выборочно проверены `sizing.py:498/:608`, заголовок реестра 12586 и
`work/sizing.json` с `area_match: null` ×14, отрицательное утверждение о читателях `dod` с контролем).

## 0. Ответ коротко

1. **Два названных примера — оба «не работают так, как обещано».**
   - **«Когда стори считается протестированной» (`dod`)**: кода-читателя нет. Ответ видит одна роль — стратег S3, прозой
     (`automation-candidacy.md:33`: «DoD один может задать `automate`»). Ответ стенда («тесты стори и регрессии зелёные, баги задокументированы,
     каждое требование проверено») ни слова об автоматизации не содержит — правило не срабатывает никогда; вердикт доставки
     (`check_delivery.py`) его не читает. Вдобавок ответ противоречит P21 (три исхода доставки) и P24 (регрессию фабрика не гоняет): у
     фабрики своё определение «протестировано», и оно в коде.
   - **Рисковые области**: текст вопроса обещает четыре эффекта (надбавка размера, план тянется к автоматизации, линза проверки требований,
     доставка не меняется). Работают два — линза S2 (`requirements-readiness.json` `aspects["cross-team integration"]`) и подсказка стратегу S3
     (план 12586 цитирует «P1 area»). **Надбавка размера мертва**: `sizing.py:498` и `:608` читают `row.get("requirement")`, а заголовок
     реестра — `Requirement (one verifiable statement)` (шаблон `templates/requirements-register.md:20`, реестр 12586 строка 11), ключ после
     `parse_register` — `requirement (one verifiable statement)` → пусто → `area_match: null` у всех требований всех стори (12586 ×14, 14857 ×8);
     тот же ключ убивает редьюсеры copy-only/logging-only. Селфтест зелёный, потому что его реестр озаглавлен просто `Requirement`.
     **При написании кейсов область не учитывается**: дизайнер, критик кейсов, автоматор и исполнитель не получают ни `test-strategy.md`, ни
     `aspect-profile.md` (`inject-map.json`); ни один кейс 12586/14857 область не упоминает (с контролем).
2. **Лишнее и мёртвое.** Из 43 вопросов: 6 ключей сохраняются и **никем не читаются** (`records_policy`, `format_all`, `default_environment`,
   `requirements_sources`, `test_data.seeds`, `test_data.generators`); ещё 4 читаются только как проза роли (`pre_commit_commands`,
   `format_changed`, `pii_and_masking`, `dod`); три факта спрашиваются дважды-трижды (место кейсов — Q4/Q25/Q29; источник требований —
   Q24/Q33; «можно ли ломать стенд» — Q6/Q14); карта классов ущерба подтверждается «остаётся» каждый раз.
3. **Что фабрика может узнать сама** (код уже есть): репозитории (`project_inventory.py`), схема доступа и `unauth_status` (`propose_access` +
   один неавторизованный запрос), `api_path`, расширения профилей (`runtime_probe --suggest`), команды профилей (`onboarding_probe.py`),
   команда установки (`project-dependencies.json`), конвенции git (p1 уже выводит), хост VCS (`git remote`), шаблон ключа тикета, тип
   аутентификации Jira / поле AC / тикет с вложением (`work/ticket-raw/field.json` уже скачан на S0), пре-коммит команды. На стенде из 19 тем
   первого онбординга содержательных ответов человека было меньше шести (репозитории, выбор стенда, тема риска, DoD, где требования, ветка);
   остальное — «да / оставить / сами». Цена: 7 ответов человека, ≈ 1 ч 16 мин, плюс 5 повторных «да» позже.

## 2. Два примера — решение

- **DoD**: вопрос снять. Единственный его потребитель — вход «DoD требует автоматизации» у стратега; его заменяет закрытый вопрос «требует ли
  команда автоматизировать проверки нового поведения: да / нет / по плану фабрики» (один ключ с читателем `automation-candidacy`). Что значит
  «протестировано» — определяет фабрика (P21, FR-21, `check_delivery`), не ответ команды; ответ стенда это и показал (регрессия «зелёная» —
  против P24).
- **Рисковые области**: (1) починить ключ в `sizing.py` + тест на НАСТОЯЩЕМ шаблоне реестра (не на `Requirement`); (2) сверка по 5-буквенным
  словам слаба — тема стенда («integration … different teams») совпала бы с 10 из 15 требований; надбавка должна идти по области продукта
  (путь/модуль/поверхность), а не по теме; вопрос p2 уже отвергает «класс ущерба как область» — отвергать и тему; (3) доставить область туда,
  где обещано: дизайнеру и критику кейсов — строкой в бриф («P1 areas: …», с требованиями, которые в неё попали, по `area_match`), иначе
  убрать обещание из текста вопроса (FR-37: обещанное — то, что делает код). Вместе с SC5-6 (размер стори от оценки; владелец 30.10: уже
  чинится в пачке большого релиза) — один носитель `sizing.py`, порядок `очередь:` ставит интегратор.

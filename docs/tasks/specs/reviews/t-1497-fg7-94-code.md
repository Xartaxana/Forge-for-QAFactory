## Findings

**F1 (fix, highest) -- a refresh deletes a tip that wave recorded while the refresh was reading CI; the merge then shows up as `direct` with no task.**
`tools/ci_read.py:708` takes `rows` (git log of origin/main) BEFORE the CI reads. Then `:717-737` (`mutate`, under the lock)
rebuilds `tips` from those old `rows` only and replaces the carrier's tips with `st.update(tips=tips, order=order, ...)`.
A tip recorded by `main_red_record` between the `git log` and the write is in `st["tips"]` but not in `rows`, so it is dropped.
Probe (`scratchpad/fg794_probe.py`, a stub `main_push_jobs` that, during the read, makes commit c2, moves origin/main to it and calls
`main_red_record(c2, task="t-777")`):
`after record, c2 task: t-777` -> `after refresh1, c2 in tips: False` -> `after refresh2, c2 task/kind: None direct`.
When it happens in practice: wave A releases `main-merge` and launches a refresh. Wave B pushes while that refresh is still reading
(one to three HTTP calls per non-final tip). B's launch is then throttled (`LAUNCH_MIN_S`), and no later refresh can get the task back.
The `preflight` list of F8 is lost the same way. This breaks the node's goal: "every red names the merges that could have brought it"
(§1, E17). The SessionStart line then prints `direct` where the task should be.
Fix: inside `mutate`, keep every `st["tips"]` entry that is newer than `rows[0]` and not in `rows`. Or run the `git log` again
under the lock. Add one refresh row for this race (see F3).

A neighbouring defect on the same input (this line's reason text): `error` is one field for the whole refresh. A transport failure
while reading ANY tip (`:713-714`) becomes the reason shown for the head. Fix: store the reason on the tip, or derive it from the
stored `runs` and the age the way the `pending` branch at `:776-779` already does.

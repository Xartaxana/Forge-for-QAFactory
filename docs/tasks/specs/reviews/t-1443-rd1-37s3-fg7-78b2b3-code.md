- Card D14 says: "receipt stays, note (as `probe()`), record already `intended_failure`". Instead the record still owes. If the critic repeats the call, a new `at` gives a new hash, so a second receipt file is written and the first one is orphaned.

Fix it in `publish_product_refs` itself: catch `(OSError, subprocess.SubprocessError)` and append a `manifest_put.py:` note. That fixes both callers. Error direction: nothing gets counted either way, so the risk is a dead-end door rather than a wrong count.

**F6 (B3, BLOCKS).** A failing tool exit never makes the job red.
- Where: `driver-golden.yml.proposed:48-51` and `:62-64`. Both steps run `python ... 2>&1 | tee <log>`, and the file sets no `shell:` (no `defaults.run.shell` and no step-level `shell`).
- Why: on ubuntu runners an unspecified shell runs as `bash -e {0}`, with **no pipefail**. Only an explicit `shell: bash` runs `bash --noprofile --norc -eo pipefail {0}`. That is from GitHub's workflow-syntax documentation for `steps[*].shell`; I did not fetch it in this session. The step's exit code is therefore `tee`'s, which is 0.
- Effect: a refused record (exit 2) does not stop the job, and compare runs against a missing golden. A compare difference (exit 1) also ends green. That breaks all three exit edges of the card: exit 2 must be red before compare, exit 1 must be red, and only exit 0 may be green.
- The report states the opposite ("bash default `-e -o pipefail`"), and no sibling workflow uses `tee`, so the repo has no precedent for this pattern.
- Proof (scratch, Git Bash, the step body verbatim with a stand-in exit-2 tool):
  - `bash -e step.sh` printed `REFUSED: x` / `after the pipe: the step went on` / `exit=0`.
  - `bash --noprofile --norc -eo pipefail step.sh` printed `REFUSED: x` / `exit=2`.
- Fix: add `defaults: run: shell: bash` to the job, or put `set -o pipefail` first in both steps. The explicit form is right even if the documentation reading were wrong.

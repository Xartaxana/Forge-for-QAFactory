## Правило

**Тест проверяет, что история проходит фабрику: исход стадии, вопрос человеку, то, что ушло дальше. Он не
проверяет каждую строку и каждую мелкую функцию. Покрыть тестами всё нельзя, и куча тестов «на скрипт» важного
не ловит** (слово владельца 10.11.2026, ночь, по пилоту TD-14: из 54 прочитанных файлов свернуть удалось один —
каждый оказался единственным тестом своей двери; `docs/tasks/test-diet.md`, «Итог пилота TD-14»).

### Что пишется — три слоя, и только они

1. **Сценарии на артефактах настоящих прогонов.** Сохранённые артефакты нескольких реальных историй
   (`fixtures/run-*`) проходят код стадий подряд; утверждается только исход: стадия принята или отказана и чем,
   какой вопрос задан человеку, что передано следующей стадии. Десяток историй, а не файл на скрипт. Сюда же —
   отказ на враждебный ввод СНАРУЖИ (тикет, слова человека, конфиг проекта, ответ хоста) строкой сценария.
2. **Стыки данных.** Поле, которое одна стадия пишет, а другая читает; строка реестра, у которой есть читатель;
   имя из файла данных, которое ждёт код. Проверки данных, без запуска драйвера. Реестр правил ролей (ниже) — этот слой.
3. **Таблица случаев для настоящей комбинаторики**: разбор идентификаторов, ключи и хэши записей, уже лежащих на
   диске проектов, деньги. Одна таблица на модуль; модуль попадает в этот слой по списку, который ведёт Lead, а не
   по желанию узла.

Чего больше нет: теста на функцию, ветку, ребро спеки или ключ DoD; нового тестового файла на новый скрипт вместо строки в историю (когда новый файл верен — «Бюджет / Файлы»);
«мини-батареи» на внутреннюю функцию. **Новый случай приходит из дефекта** — найденного живым прогоном, критиком или
CI (FR-32): одна строка в сценарий или таблицу, которая падала до правки. Свидетель билдера — прогон сценариев и
стыков, которые задевает его правка, а не новый файл. То, что тестом не ловится (суждение роли), доказывается
живым прогоном и приёмкой (FR-33, P27).

### Откуда берётся ожидаемое значение

Слово владельца 17.11.2026 («у нас в фордже и требований нет. Или вместо них у нас спека?» — да, спека). Требование к
тесту форджа — спека узла и её DoD, текст правила, которое исполняет код (`CLAUDE.md`, `PROJECT.md`, этот документ,
файл роли, FR-n), или слово владельца с носителем. Ожидаемое значение берётся оттуда, и спека
называет источник строкой `expected from:` («Строка теста в DoD», ниже). С вывода кода ожидание не списывается: тест,
чьё ожидание переписано из того, что код напечатал, может только пройти (для фабрики это P20 и FR-58). Спека молчит о
значении — билдер его не выбирает, а возвращает вопрос (`CLAUDE.md` правило 11: молчащий край — дефект диспетчера).
Ожиданием из кода НЕ считаются: дословный текст отказа, который дала сама спека; срез настоящего прогона как ВХОД
(исход на нём — всё равно из спеки); значение, выведенное из входа самого теста по правилу, которое называет спека
(N строк на входе — N на выходе, если спека так велит); поведение, которое спека велит сохранить, только когда она
называет само сохраняемое — значение или инвариант (что остаётся отказом, что печатается); «вывод остаётся как
сейчас» без названного значения — это снимок кода и тест «как раньше» из таблицы «Что не пишется», а не источник.

### Строка теста в DoD

Слово владельца 17.11.2026: «а это не сделает разработку в 2 раза медленнее?» — поэтому одна строка на пункт, и только
на пункт поведения. Пункт спеки билдеру, который меняет то, что видно через дверь (аргумент или выход CLI, вердикт хука
или гейта, поле или файл, который читает другой), несёт внутри DoD одну строку:

    test: <файл::таблица или строка> | expected from: <§ спеки, правило, слово владельца>

или `test: none -- <почему> | expected from: <источник>` (документ — свидетель по правилу 11 `CLAUDE.md` «DOC-DISPATCH
WITNESS»; суждение роли — живой прогон; внутренняя граница без своей двери). Строка называет МЕСТО строки теста
(существующая таблица, история или стык; новый файл — по цели «Бюджет / Файлы») и ИСТОЧНИК ожидания; самих значений
не повторяет — они в тексте пункта и его краёв. Пункт без поведения (перенос текста, переименование) строки не получает;
диспатч, где такого пункта нет вовсе, несёт одну строку `test: none -- поведения нет | expected from: <§ спеки>`.
Наличие и форму строки код пока не проверяет; хватает ли строк
и верен ли источник — судит критик (вопрос 5, `.claude/agents/critic.md` правило 22).

### Что запускать по своей правке

Слово владельца 21.10.2026 18:3x, D-0056 (замер: у фикс-раундов 69–85 % стены — ожидание прогонов, правки кода 1–4 %).
У билдера — только **точечные проверки своей правки**: файлы, которые печатает
`python -B ai-packages/qa-factory/scripts/tests/scenario_walk.py --witness-for <пути owns>` (истории и строки `keep` из
`scripts/tests/test-layers.json`, включая тест гейта; спека `docs/tasks/specs/td-15-scenarios-quarantine.md`, слово
владельца 10.11.2026). Строка «no scenario or keep row covers» — строка отчёта, а не повод писать тестовый файл.
С 18.11.2026 (FG7-63; слово владельца: «именно поэтому тесты гоняются в CI») команда печатает два блока: файлы для
локального прогона и блок `canon judges, do not run locally:` — файлы класса «судит канон» (ключи `files` в
`scripts/slow_tests.json` и маски `canon_only` в `test-layers.json`; одно определение — `selftest.canon_class`); последняя
строка — счёт `run locally: N file(s); canon judges: K file(s)`. Билдер гоняет только первый блок. Файл второго блока
проверяется узким вызовом изменённых функций (`файл.py::имя` либо импорт модуля и вызов функции по имени) и строкой отчёта
`not run locally: <файл>, canon judges`. Диспатч держит это кодом: `tools/dispatch_manifest.py` отказывает диспатчу
билдеру, чья команда `DoD:` гоняет файл этого класса целиком, гоняет каталог тестов пакета целиком, содержит
`--witness-for` или называет больше трёх тестовых файлов целиком — `DoD:` называет файлы свидетеля явно. Дверь — строка
`manifest-skip: dod-run -- <причина>`; нечитаемые данные класса — заметка, не отказ.
**Файл карантина билдер не запускает, не чинит и не правит.** К напечатанному добавляются только файлы, которые называют
строки `test:` DoD узла (путь вне пакета — тестовый файл, который его судит, правило 4 `COORDINATOR.md`); тронут
`story_run_common.py` — в отчёте строка «тронут story_run_common.py» (все `test_story_run_*.py` судит канон); `--limits
--lang` и `test_audit_rules.py` — только если правка их касается (лимит размера, правило аудита); так же по типу правки:

- `test_hooks_wiring.py` — хуки;
- `test_null_outcomes.py` — обязательный список, выход стадии или поле инструмента (реестр `references/null-outcomes.json`,
  t-305 N0);
- `test_gate_registry.py` — гейт, его ключ или слово-исход (реестр `references/gate-registry.json`, t-302 T1);
- `python -B scripts/tests/test_console_encoding.py` — добавлен или изменён скрипт, печатающий в консоль (B-413);
- `test_story_run_words.py` и `test_driver_layers.py` — правка `story_run.py` (Lead, 26.10.2026: `main` красный 16.10 и
  21.10, оба раза DoD их не называл).

Уровень пачки — **не регрессия, не соседи, не большие файлы**: импортёры, файлы из списка `SLOW_TESTS` (и `test_story_run_*`,
`test_controller_*`, `test_fixes_13797`, `test_story_step.py`, полный `selftest.py`), докер, храповики — билдер НЕ гоняет и
не ждёт: «судит канон пачки» (критерий — список, а не длительность) (прежний п. 7 «`lint_ratchet --check` + the console
scan» разделён: храповики — уровень пачки, сканирование консоли — по типу правки, выше); «сверх списка» — строка отчёта,
не прогон. Билдер **CI не запускает и не ждёт** — ни пайплайн ветки, ни канон (слово владельца 14.11.2026). **Набор
мутаций** билдер не прогоняет и не перечисляет (слово владельца 28.10 и 10.11.2026), и канон пачки его не гоняет; проба
«тест может упасть» у билдера одна — строка дефекта, красная до правки (раздел «Тест может упасть» ниже, слово владельца
17.11.2026). **Всё это делается один раз на пачку**, не на каждое изменение: после схождения веток пачки (или на границе
стадии, если пачка живёт дни) координатор запускает один прогон BATCH CANON — соседи, большие файлы, храповики и аудит идут
в пайплайне CI на ветке пачки (как его запустить и прочитать — `docs/RUNBOOK.md` §7); красное на каноне — `defect_found`
против узла (правило 4 COORDINATOR.md). CI на каждом MR остаётся регрессией за бесплатно. Тест из `SLOW_TESTS` идёт только в
полном уровне CI (быстрый его пропускает), поэтому зелёный свидетель с Windows его не доказывает: Linux отдаёт другой errno
(`Path.unlink(missing_ok=True)` под путём, где папка — файл, на Linux `NotADirectoryError`, на Windows проглоченный
`FileNotFoundError`; релиз 0.9.0 нашёл красный `test_probe_by_code_copy.py` лишь при пуше), CI идёт под root, хук,
записанный тестом, требует `chmod 0o755`. Такой файл — и тест `tools/`, чей результат зависит от платформы (F6-28), —
доказывает пайплайн ветки (канон в CI, образ python:3.12), не билдер; Lead в списке передачи называет затронутые
`SLOW_TESTS`-файлы и читает ночной `package-full` в начале каждого дня.

**Канон — в CI, не на этой машине** (слово владельца 03.11.2026): что интегратор гоняет локально — `docs/RUNBOOK.md` §7;
соседи, большие файлы, `selftest.py`, `pytest tools/` целиком и докер идут пайплайном на ветке, его запускает координатор.
Пайплайн `main` читают только интегратор волны и билдер, чинящий красный `main` (слово владельца 14.11.2026). Диспатч,
требующий большего локально, — дефект координатора: интегратор пишет это строкой отчёта и не гоняет.

- Полный `selftest.py` и `install_smoke.py` на машине не гоняет никто — их судит CI (D-0059, `docs/RUNBOOK.md` §7).
  Красный тест вне своих файлов от чужой недоделки — отметить и не чинить.

`--witness-for` отвечает, ЧТО ЗАПУСТИТЬ по пути пакета; `python -B tools/owns_readers.py` — что НЕЛЬЗЯ СЛОМАТЬ или править
(читатели, карантин, медленные, наличие); как билдер читает его блок — правило 12 `.claude/agents/builder.md`.

### Тест может упасть: одна проба, а не набор мутаций

Слово владельца 17.11.2026: «надо исправить, но не вернуться к куче мутантов, которые шли дольше написания кода». Набор
мутаций не пишется и не гоняется никем: список снят 10.11.2026, канон пачки мутаций не гоняет. Вместо него две пробы с
потолком:
- **Билдер, пункт-дефект** (пункт чинит дефект, найденный живым прогоном, критиком или CI): строка, которая его ловит,
  пишется ДО правки кода и прогоняется один раз — только узкий файл этой строки; вывод идёт в свидетель строкой
  `red-before: <команда> -> <хвост вывода>`, затем правка и обычный свидетель. Красным считается падение на утверждении
  строки; падение на импорте или сборе (двери ещё нет) — не красное: тогда `red-before: not runnable -- <почему>`.
  Строка в медленном или карантинном файле — `red-before: not run -- <файл> судит канон`. Цена — один узкий прогон.
- **Критик, дифф с новым поведением**: может ли тест упасть, судит по вопросу 5 (а) и
  правилу 21 `.claude/agents/critic.md`; как и чем он это проверяет, написано только там.

### Карантин старых тестов

Слово владельца 10.11.2026 (ночь): «карантин» — и система оповещения, по которой видно, когда всё из карантина
можно удалить. Тест, не входящий в три слоя и не названный гейтом, переводится в карантин: файл остаётся в
репозитории, в каноне не запускается, не чинится и не правится. Перевод — после того, как слой сценариев собран и
зелёный. Что в карантине, с какого дня и какого релиза, когда и по какому сигналу его можно удалить, кто и где это
видит — спека `docs/tasks/specs/td-15-scenarios-quarantine.md` (узел TD-15). Из карантина тест не возвращается:
если он показал настоящий дефект, его случай уходит строкой в сценарий или таблицу.

Где это записано и чем читается:

- **Носитель** — `ai-packages/qa-factory/scripts/tests/test-layers.json`: раздел `keep` (файл → слой и причина; слои
  `scenario`, `data_join`, `register`, `table`, `gate_named`, `detector`), `pin_holds` (файл держится, пока его правило
  роли не принято реестром `design/role-rules.json`; идёт в каноне), `quarantine` и `cohorts` (пишет только
  `python tools/test_quarantine.py enter`). Канон (`selftest.py`) гоняет всё, кроме `quarantine`; после перевода файл,
  не записанный ни в один раздел, красит канон строкой `unlisted:` с дверью.
- **Истории** — `scripts/tests/fixtures/stories/<id>/` (срез настоящего прогона синтетической задачи, вычищенный
  `tools/story_capture.py`), обходчик `scripts/tests/scenario_walk.py`, тест истории `test_scenario_<id>.py`. Новый
  случай — строка `variants.json` истории.
- **Что запускать по своей правке** — раздел «Что запускать по своей правке» выше.
- **Наблюдатель** — задача CI `quarantine-watch` гоняет карантин два раза в неделю и после смены версии пакета;
  красное разбирает роль (`python tools/test_quarantine.py judge`), настоящий улов переносится строкой в сценарий или
  таблицу (`land`) и сразу сообщается владельцу.
- **Оповещение** — строка `TEST QUARANTINE …` в начале каждой сессии и `python tools/test_quarantine.py status`:
  сколько файлов, с какого релиза, что не разобрано; `READY TO DELETE` — прошёл полный прогон на втором релизе после
  входа и всё разобрано. Удаление — `purge`, только по слову владельца.

### Что не пишется, а найденное — удаляется

| Вид | Признак | Почему | Что вместо |
|---|---|---|---|
| Пин текста роли отдельным тестом | свой тестовый файл или проверка «фраза дословно стоит в `agents/*.md`, `phases/*.md`, `references/*.md`, SKILL» | дословная фраза краснеет от любой редакции; полсотни файлов с одним и тем же приёмом | правило роли охраняется от потери ОДНИМ реестром (ниже); если фразу ЧИТАЕТ код — тест на этот код |
| Пин исходника | `read_text()` своего `.py`, `inspect.getsource`, подсчёт вхождений регулярки в коде | закрепляет устройство, а не результат; ломается рефакторингом | структурный инвариант — одна строка в общем храповике (`dup_ratchet`, `lint_ratchet`, `test_driver_layers`), не свой тест на узел |
| Пин измеренной константы | точные байты, секунды, число строк, «сейчас 17» | плывёт с каждой правкой (потолки `brief_pack`, `slow_tests.json`, фазы `run_suite_mine`) | потолок с запасом в одном реестре данных, обновляемый командой; время стены не утверждается никогда (FR-31) |
| Квитанция на ключ | по проверке на каждый ключ DoD, каждое ребро таблицы E-nn, каждую мутацию | дублирует тест поведения, удваивает дифф | ключи и рёбра — строки одной параметризованной таблицы |
| «Как раньше» | тест, что помощник ведёт себя как код, который он заменил | закрепляет случайное | ничего |
| Отрицательный контроль внутри теста | копия файла без ключа должна провалить проверку | тест проверяет сам себя | ничего |
| Тест документа рабочего процесса | наличие строк в CHANGELOG, пачке, карточке, отчёте | это содержание, а не код | проверка формы — в `piles.py check` и подобных, один раз |

### Правила ролей не теряются: один реестр вместо пинов

Слово владельца 10.11.2026: текст роли несёт правила работы; если правило случайно вырежут, чтобы файл влез в
потолок размера, оно потеряется молча. Эта охрана нужна, и пин её даёт — но плохо: дословная фраза, свой файл на
каждую правку, отрицательный контроль. Замена — реестр обязательных правил ролей `design/role-rules.json`
(узел TD-5): строка = id правила, файл-носитель, короткий якорь (2–6 слов или метка, не предложение), откуда правило
(слово владельца, находка). Один тест читает реестр и проверяет, что якорь стоит в носителе. Убрать правило из текста
можно только вместе со строкой реестра — в диффе это видно критику как удаление правила, а не как редактура.
**Пока реестр не принял правило, его старый пин не удаляется**; файлы-пины правил ролей уходят только тем же
коммитом, что переносит их ключи в реестр. Пины текстов, которые правилами ролей не являются (строки CHANGELOG,
пачек, отчётов, долга), удаляются сразу.

### Бюджет

- **Объём**: в ветке узла строк теста не больше, чем строк кода и текста продукта. Бюджет билдер знает ДО первого теста
  (слово владельца 18.11.2026: «билдер должен знать заранее», иначе билдер тратит время на тесты, а критик и Lead — на их
  разбор и удаление): диспатч перечисляет строки тестов по убыванию силы, билдер пишет их сверху вниз, пока строк теста не
  станет столько же, сколько кода; строку, которая не поместилась, он НЕ пишет, а называет в отчёте —
  `tests not written: <строка> -- over budget`. Диспатч, где строк названо больше, чем вмещает бюджет, билдер возвращает
  вопросом до работы. Двери у билдера нет: ветку, где тестов больше, `tools/wave.py merge` не сливает, пока Lead не назовёт
  причину (`--tests-over "<причина>"`, она попадает в коммит слияния; узел FG7-65 — до его слияния ту же сверку Lead делает
  при приёмке по `git diff --numstat origin/main...<ветка>`). Строка `tests-over: <причина>` в сообщении коммита остаётся
  только у прямого коммита Lead (хук commit-msg без неё предупреждает, не отказывает). Дизайнер не пишет в спеке оценку
  «~300 строк тестов».
- **Файлы**: решает цель, а не запрет и не слово владельца (слово владельца 17.11.2026: «не хочу что бы написание
  тестов зависило от моего слова. Какая была цель у сокращения количества файлов? Вот этой цели и надо придерживаться
  когда решаем нужен отдельный фаил или нет»). Цель — та, что меряет «Замер» выше: время прогона (файлы дольше 10 с),
  уход (правки тестовых файлов в коммитах, где не менялись ни код, ни текст правил) и файл на скрипт вместо истории.
  Поэтому случай по умолчанию — строка в существующую историю, стык или таблицу своего слоя. Новый файл верен, когда
  случай не ложится ни в одну из них, не выведя тот файл за его бюджет (10 с, часть разрезанного — 60 с в CI) и не дав
  ему чужую дверь (дверь случая — не та, что файл уже гоняет; предмет файла назван в его docstring или истории); новый
  файл укладывается в 10 с, строит мир один раз и держит одну параметризованную таблицу (и строки стыков). Время — хвост
  `python -m pytest <файл> -q` (`in N.NNs`) или замер прогона скрипта, в отчёте билдера. Уход меряется задним числом по
  окну коммитов: это мера цели, а не довод в одном случае. Место называет дизайнер в строке `test:` DoD («Строка теста в
  DoD»); выбор судит критик (вопрос 5, `.claude/agents/critic.md` правило 22). Строка `keep` в `test-layers.json` — учёт
  файла пакета (без неё канон красит `unlisted:`), а не разрешение его создать; у тестов форджа строки `keep` нет. Свой
  файл `tools/test_<x>.py` у нового инструмента форджа `tools/<x>.py` — случай этого же правила, не исключение.
  Файл по имени тикета, пачки или находки (`test_fixes_13797`, `test_integration_batch_*`) не создаётся.
  Части разрезанного оставленного файла — не новый тестовый файл: каждая часть наследует строку `keep` исходного
  (слой, причину, `named_by`: каждый унаследованный носитель называет часть рядом с её соседями, иначе `check` и
  селфтест красные; `covers` сужается по своим импортам, но вместе части покрывают всё, что покрывал
  исходный), а исходная строка уходит командой `tools/test_quarantine.py split-keep`. Правило «10 с на новый файл»
  к частям не применяется: их цель — до 60 с в каноне CI (спека `docs/tasks/specs/td-11c-test-split.md`; владелец,
  11.11.2026).
- **Время**: новый тестовый файл укладывается в 10 с. Тест, которому нужен драйвер или контроллер, строит мир
  ОДИН раз на файл и снимает с него все проверки; запуск подпроцесса на каждую проверку — дефект теста.
  Исключение сухой истории (слово владельца 14.11.2026, спека `docs/tasks/specs/20261113-p1b-dry-story-spec.md`, §4.3):
  драйвер запускается процессом на строку обхода, на копии снимка («создавать `Driver` в процессе теста» в рецепте
  запрещено; время строки ограничено капом на строку, E6); лимит — потолок набора, не 10 с; другие файлы под правило.
- **Потолки набора** (цель чистки, не гейт): быстрый уровень CI — до 10 минут, полный — до 30 минут счёта.

### Как писать эффективный тест на нашем проекте

Раздел ничего не добавляет к правилам выше — он собирает их в порядок работы билдера.

1. **Сначала найти, где поведение уже проверяется.** Пакет: `scenario_walk.py --witness-for <пути owns>` печатает
   истории и строки `keep`, которые покрывают правку. Фордж (`tools/`): тестовый файл инструмента. Новый случай — строка:
   `variants.json` истории, строка таблицы, строка стыка; новый файл — только по цели «Бюджет / Файлы».
2. **Случай приходит из дефекта.** Одна строка, которая падала до правки (FR-32): найденного живым прогоном, критиком или
   CI. Не «по проверке на каждый ключ DoD».
3. **Один параметризованный тест на поведение.** Id параметра называет случай, по красной строке видно, какой случай и
   какая ветка упали (P16). Ввод −1, 0, 1.5, «абв» с одним исходом — один тест с параметрами.
4. **Утверждать исход, не устройство.** Стадия принята или отказана и чем, какой вопрос задан человеку, что ушло дальше.
   Ни пина текста роли, ни пина исходника, ни измеренной константы (таблица «Что не пишется»).
5. **Данные — из настоящих прогонов.** Срезы `fixtures/stories/<id>/`, `fixtures/run-*`; не выдуманный словарь из трёх
   ключей, который код никогда не увидит.
6. **Мир — один раз на файл**, проверки снимаются с него («Бюджет», «Время»; открытый вопрос об исключении сухой истории —
   находка `plans/piles/forge/findings/20261114-testing-md-podprocess-na-proverku-protiv-suhoj-istorii.md`, ждёт слова
   владельца).
7. **Враждебный ввод — только снаружи.** Тикет, слова человека, конфиг проекта, ответ хоста, аргументы CLI, полезная
   нагрузка хука: размер, вложенность, кодировка, пустое и битое, каждый предел — на нём и за ним; строкой сценария или
   таблицы. Внутренняя граница теста не получает.
8. **Цена.** Объём — «Бюджет / Объём» (строка сверх бюджета не пишется, а называется в отчёте); новый файл (часть
   разрезанного — до 60 с в CI) укладывается в 10 с; тест, покрасневший второй раз без дефекта, удаляется («Когда тест
   покраснел»).

Плохо: файл по имени тикета (`test_fixes_<тикет>.py`, «Бюджет / Файлы») с проверкой «фраза стоит в
`agents/qa-automator.md`» и копией файла без ключа, которая должна упасть. Хорошо: строка `variants.json` истории, где ответ человека «нет» на гейте A даёт тот вопрос и ту стадию, что ждёт
требование, и которая была красной до правки.

### Когда тест покраснел

1. Поведение изменено намеренно — тест переписывается или удаляется в том же узле; узел ищет такие тесты
   `grep`-ом по старому поведению до сдачи (находка `conductor/findings/20261010-ci-krasnyj-test-no-real-claude-pin-do-c1-1.md`).
2. Покраснел пин из таблицы выше — удаляется, не чинится. Строка в отчёте: файл, вид пина.
3. Тест покраснел второй раз без настоящего дефекта за ним — удаляется, даже если это тест поведения: он
   стоит дороже, чем ловит. Запись — в `docs/tasks/test-diet.md`.
4. Удаляя тестовый файл, убери его имя из реестров, которые его называют (`grep` по имени файла: `plans/features.json`,
   `slow_tests.json`, `CONTRACT_TESTS`/`TEST_TIMEOUTS` в `selftest.py`, `gate-registry.json`, `stage-joints.json`,
   `driver-layers.json`, `.gitlab-ci.yml`, `judgment-census.json`); файл, который называет гейт, не удаляется — только
   чистится.
5. Правка не ослабляет проверку, которая остаётся: утверждение теста, которое переживает правку, не смягчается
   (формулировка старого брифа диеты тестов: «No weakening of an assertion that stays»).

### Кто что делает

- **Дизайнер**: DoD называет поведения и стык, а не число проверок; ребро спеки — строка таблицы теста; на
  пункт поведения — строка `test:` («Строка теста в DoD»); место новой строки, в том числе новый файл, — по цели
  «Бюджет / Файлы».
- **Билдер**: пишет по этому документу; что запускает — «Что запускать по своей правке».
- **Критик**: вопрос 5 (`.claude/agents/critic.md` правило 22) и правило 21 там же.
- **Lead**: удаление по этому документу — узлы `docs/tasks/test-diet.md`.

Детектор: калибровочная проверка 33 читает отношение «тесты : продукт» по принятым узлам и число чистых починок
тестов за окно; код-гейта нет — на дисциплине, утечку показывает замер выше, повторяемый той же командой; строки `test:`, пробы критика и `red-before:` — калибровочная
проверка «Forge test discipline» (`PROCESS/WEEKLY_CALIBRATION_PROTOCOL.md`).

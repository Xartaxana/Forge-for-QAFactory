## 4. Гигиена релиза и общего дерева

- **Перед релизом**: `git fetch`, сравнить HEAD с origin, `git status`. Однажды две сессии работали в одном
  дереве, и параллельная закоммитила релиз прямо в него: обе шапки CHANGELOG получили один номер.
- **Копия пакета в релиз — с удалением исчезнувших файлов, а не поверх.** Файл, убранный из
  `ai-packages/qa-factory/` здесь, должен исчезнуть и в релизной копии (клон `QAFactory`, его
  папка — `release_repo_root` из `tools/dev.config.yaml`; старый ключ `public_skills_root` пока читается, с одним WARN, GM1-2). 30.09.2026
  `scripts/tests/test_story_run.py` разбит на `story_run_common.py` и одиннадцать `test_story_run_*.py`:
  если старый файл останется в релизной копии, `selftest.py` подберёт его по маске `test_*.py`, а
  отдельного лимита в 900 с у него больше нет — он упадёт по таймауту 300 с. Перед релизом сверить
  `git status` целевого репозитория на удаления.
- **`git fetch` не цепляется `&&` к `git commit`**: при отвале сети коммит не делается. Коммитить отдельно от
  fetch и push.
- **Новые файлы: `git add -N` до `selftest.py --hygiene`.** Проверка падает, если в каталоге пакета есть
  что-то, чего нет в `git ls-files`; до `git add -N` этим «лишним» выглядят свежие тесты.
  Запуск из `ai-packages/qa-factory`: `python -B scripts/selftest.py --hygiene`.
- **Отпечаток релиза (CL1-8, D-0052 (3)).** В релизной копии, из её `qa-factory/`, после копирования пакета и
  сборки CHANGELOG: `git add -A .` всего пакета (не `git add -N`: файл, добавленный только намерением, в коммит не попадёт,
  а в карту попадёт — каждая установка из git прочтёт `yes`), затем `python -B scripts/release_fingerprint.py --write`.
  **Последним шагом, после любого `git add` и любой правки, прямо перед коммитом релизной копии** —
  `python -B scripts/release_fingerprint.py --check`: выход 0 — файл совпал с деревом; 1 — дерево разошлось с файлом
  (файлы названы; правка пакета после `--write` требует снова `--write`, затем снова `--check`); 2 — ответа нет (`unknown`:
  файла нет, он не читается или не того вида, другой версии или рецепта, файл пакета не читается; причина названа) и в
  клоне — файлы рецепта вне индекса (названы). `--write` отказывает (выход 2, файл назван), если в папке-клоне лежит
  неотслеживаемый, игнорируемый, добавленный только намерением (`git add -N`) или правленный после `git add` файл рецепта, или
  git не смог составить список: установка из git его не получит и прочтёт `yes` для каждого пользователя релиза.
  `references/release-fingerprint.json` коммитится только в релизный репозиторий; в этом репозитории его нет, и в
  собственный отпечаток он не входит. Забытый шаг даёт `unknown / no_release_file`, не `yes`.
- **Прогон тестов переписывает трекнутую фикстуру** `scripts/tests/fixtures/*/ledger.json` (меняется только
  поле `generated`): откатить перед коммитом.
- **Описание PR** — файлом, не аргументом: `gh pr edit <номер> --body-file <файл>` (при создании — `gh pr create --body-file <файл>`).
- **`C:\Users\dev1\work` в Python-докстринге** `"""..."""` ломает парсер (`\U` начинает unicode escape). То же
  с `\n` в bash-heredoc: скрипты с путями Windows писать файлом, пути собирать через `/`.
- **Длинные пути Windows**: клонировать и читать чужие ветки как `git -c core.longpaths=true clone ...`.

## 5. Коммиты в целевом проекте

Файл, который проект отслеживает git по наследию (на прежнем стенде — `.env` харнесса), `.gitignore` не защищает. Инцидент 01.09: `git add` каталогом смёл `.env`, `state/cost/`, журнал и артефакты живой задачи; коммит пришлось пересобрать.

Правило: в целевом проекте коммитить **только явным списком путей** (`git add <путь1> <путь2>`), никогда каталогом. Чужие незакоммиченные файлы (`.env`, журнал, артефакты живой сессии) не трогать.

## 6. Обновление установленного плагина

Три разные сущности, путать нельзя:

1. **Канон**: пакет `ai-packages/qa-factory` в этом репозитории (`main`); только здесь правят саму
   фабрику. Релизы уходят копией каталога в `Xartaxana/QAFactory`, это канал релизов, а не место
   разработки.
2. **Установленный плагин**: копия `~/.claude/plugins/cache/qafactory/qa-factory/<version>`, ставится из
   маркетплейса `qafactory`. Правки в ней теряются при переустановке; руками её не править.
   Маркетплейс с источником-каталогом копирует папку как есть, мимо `.gitignore`, поэтому грязь в
   каталоге пакета уезжает в установку (отсюда проверка `--hygiene`, раздел 4).
3. **Проектное состояние**: `<project>/qa-factory/` (конфиг, стратегия, артефакты прогонов, `records/`,
   `state/`). Принадлежит проекту, версионируется в его репозитории; руками не удалять: переустановка сама
   переносит `records/`, а `state/` (машинное, в `.gitignore`) пересоздаёт.

**Под живой стори плагин не обновлять.** Хуки перечитываются на каждый вызов, а тело скилла остаётся
старым до компакта: сессия поедет по двум версиям канона сразу. Аудит A14 покажет дрейф потом, но задачу
уже не спасёт.

**Признаки живой стори** в проектах: свежее mtime у `qa-factory/records/journal.jsonl`
(`state/` при переустановке пересоздаётся, журнал в `records/` переживает её), `state/cost/*.json` и `state/<task>/pipeline.json`. Если стори идёт, раскатку отложить и сказать об этом
явно.

Сам цикл (`uninstall`, `marketplace update`, `install` в том же scope, перезапуск, `/qa-factory:qa-doctor`,
затем ре-онбординг при необходимости) описан в
[ai-packages/qa-factory/UPGRADE.md](../ai-packages/qa-factory/UPGRADE.md), раздел «Plugin»: здесь он не
повторяется. Простая переустановка поверх той же версии кэш не обновляет, нужен полный цикл.

## 7. CI на GitHub и BATCH CANON

CI форжа — GitHub Actions репозитория `Xartaxana/Forge-for-QAFactory` (`main` защищена, обязательная проверка `forge-check`; защита настраивается на шаге D1 плана переезда).
Что гоняет каждый workflow — шапки `.github/workflows/forge-check.yml`, `nightly.yml`, `canon.yml`; здесь — как ими пользоваться.
`forge-check` идёт на push в `main` и на каждый PR; пуш ветки без PR ничего не запускает.

**Прогнать ветку.** Запушить ветку, затем `python tools/ci_read.py start --ref <ветка>` (запускает `canon.yml`; то же —
`gh workflow run canon.yml -f ref=<ветка>`). Токен: имя переменной — `github_token_env` в `tools/dev.config.yaml` (читает
`tools/dev_config.py`; без файла — `GITHUB_TOKEN`); значение не печатается и не пишется. Результат — `python tools/ci_read.py
pipelines`, затем `jobs <run_id>`, красное — `log <job_id>`, файлы — `artifact <run_id> <имя>/<путь>`.

**BATCH CANON — пайплайн CI на ветке пачки** (слово владельца 03.11.2026: «Канон всегда на CI»; слово 28.10.2026: «Когда всё
реализовано, конечные проверки пачки должны занимать не больше часа и всё что возможно идти в CI»). Канон пачки и канон релиза —
один и тот же ход: для релиза из нескольких пачек — один раз по всему релизу и последним (узлы → кучки → `main` → публикация →
канон), не гейт ни на PR, ни на публикации (слово владельца 27.10.2026). После схождения веток интегратор прогоняет ветку, как
выше. Последний шаг `canon.yml` (`tools/canon_clock.py`) печатает `canon wall time: …`; норма — 60 минут, в первую неделю на
GitHub её мерят (FK-4), дверь — строка `canon-over-hour: <причина>` в
сообщении головного коммита ветки (проходы считает калибровка, проверка 40). Свидетель канона — id пайплайна, статусы задач и
строка `canon wall time`, дописанные в `witness` последнего `accepted` пачки с меткой BATCH CANON (правило 4 `CLAUDE.md`). Что
канон покрывает — `plans/builder-rules.md` п. 7b.

**Что остаётся локально и почему.** (1) Мутационный проход по спискам мутаций узлов — каждая своим узким файлом (D-0056 (3)):
список мутантов живёт в отчётах узлов, CI его не знает. (2) Локальный прогон (докер) — запасной путь,
только когда CI недоступен или красный по причине раннера, а не кода (слово владельца 03.11.2026: канон — на CI). Тогда исходники — клон ветки без перевода
строк (`git -c core.autocrlf=false clone --branch <ветка> <репозиторий> <папка>`; рецепт архива и `eol` — узел F6-43),
смонтированный ТОЛЬКО на чтение и скопированный ВНУТРЬ контейнера: bind mount Windows → Linux медленнее в 5+ раз и даёт ложные
таймауты (замер 28.10, `plans/piles/onboarding-forge/findings/20261028-kanon-pachki-ne-dolshe-chasa-v-ci.md`):
`MSYS_NO_PATHCONV=1 docker run --rm -v "<папка>:/src:ro" python:3.12 bash -c "cp -a /src/. /repo && cd /repo && git config --global user.name forge-ci && git config --global user.email forge-ci@invalid.example && git config core.hooksPath .githooks && pip install -q pytest pyflakes==3.2.0 pyyaml openpyxl && python -m pytest tools/ -q; cd ai-packages/qa-factory && python -B scripts/selftest.py --jobs 4; python -B scripts/install_smoke.py"`
(рецепт ещё не прогонялся: первый запуск — его проверка; `cd` здесь — внутри контейнера, не в шелле сессии).

## 8. Версия сборки стенда: OCI-метка образа

Стенд со своей сборкой образа (пример прежнего стенда: сервис UI в `docker-compose.yaml`) несёт
`build.labels: org.opencontainers.image.revision: ${UI_GIT_SHA:-unknown}`. Метку проставляет команда сборки:

```sh
UI_GIT_SHA=$(git -C <репозиторий UI> rev-parse HEAD) docker compose --profile uitest up -d --build <сервис UI>
```

Прочитать метку:

```sh
docker image inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' <image>
```

Фабрика читает метку сама, по лестнице идентичности стенда (спека t-300, `records/stand-identity.json`, способ
`oci_label`): реестр, затем источники, затем OCI-метка, затем файл с sha сборки, затем «неизвестно» и вопрос
человеку. Без `UI_GIT_SHA` метка равна `unknown`, и фабрика спросит, как узнать сборку.

### 9.1. Мандат ночного агента

Стоячее поручение сессии, которая ведёт прогон. Оно действует внутри правил этого репозитория (`CLAUDE.md`:
маршрутизация, журнал, гигиена команд; `PROJECT.md`) и ничего из них не отменяет. Мандат в силе, когда владелец
поручил сессии вести ночной прогон по этому разделу.

1. **(a) Отвечает на вопросы фабрики сам.** Источники ответа, по порядку: тикет и то, что стори уже собрала по нему
   (снимок тикета, связанные задачи, комментарии, вложения в `qa-factory/artifacts/<ТИКЕТ>/`; тикет читается
   кодом фабрики, а не через LLM-агента, P5); документы целевого проекта; заготовленные файлы
   `experiments/<эксп>/answers/` (для сравнительных прогонов правило «ответ прогону = дословно тот же»). Вопрос, на который не отвечает ни один источник, — не повод
   остановиться: ночной агент берёт **самое консервативное прочтение, которое не останавливает прогон**, пишет его
   в журнал вопросов и ответов тетради с пометкой «мои» и причиной, чтобы владелец утром проверил. Он никогда не
   выдаёт свой ответ за слово владельца и нигде, кроме тетради эксперимента, его не пишет. Ожидаемое значение
   теста, которого не дают требования, консервативно оставляется открытым (`unresolved`) и записывается пробелом,
   а не берётся из кода (P20). Слово «мои», которым пройден гейт или блок, записывается как проход (P13) с той же
   пометкой.
2. **(b) Чинит блокеры фабрики.** Блокер фабрики — падение драйвера (выход 1), отказ без двери (FR-2, FR-57),
   дефект пакета. Разбор: хвост лога и `.err`, `qa-factory/artifacts/<ТИКЕТ>/state/driver-runs.jsonl`,
   `state/driver-question.md`. Починка идёт **в пакете этого репозитория**, а не в копии проекта и не обходом:
   корень причины, тест, проверка по `plans/builder-rules.md` п. 7b, проход по затронутым
   разделам `design/factory-rules.md` (`PROJECT.md`, «Как принимается изменение пакета», п. 1-3), строка `B-nnn` в
   `plans/BACKLOG.md`. Если пакет на время прогона заморожен копией, исправленный пакет синхронизируется в копию
   только на остановке драйвера и после зелёных тестов (п. 9.2.2). Затем драйвер перезапускается (п. 9.4).
3. **(c) Чинит блокеры среды, которой ему можно касаться.** Окружение копии (повторить установку, доказать импорт
   и сбор тестов), устаревший артефакт (отодвинуть переименованием, не удалять), умерший процесс (запустить ту же
   команду), контейнеры стенда, если это разрешает runbook проекта. Чекауты стенда принадлежат владельцу: в них
   сессия не делает `git checkout` и `git stash`.
4. **(d) Все остальные проблемы записывает и идёт дальше.** Тетрадь эксперимента, раздел «Ход прогона»: время, что
   остановило, что сделано, чьими словами; плюс строка `B-nnn` в `plans/BACKLOG.md`. Ничего в тикет-систему проекта,
   ни MR, ни комментариев (P8).
5. **(e) Останавливается, только когда без владельца не двинуться.** Это: стенд надо переключить на другую ветку
   (чекауты стенда владельца); нужен доступ или секрет, который ночной агент не вводит никогда; решение по продукту
   или процессу, на которое нет безопасного прочтения. Граница между (a) и (e) (владелец/Lead, 02.10): «нет
   безопасного прочтения» — это когда ЛЮБОЙ ответ либо пишет что-то вне копии и тетради (тикет-система, MR,
   публикация), либо вводит секрет, либо меняет стенд владельца, либо выбирает между поведениями продукта там,
   где тикет, AC и документы молчат; последнее по P20 закрывается не выбором, а записью пробела
   (`unresolved`) — и это (a), прогон едет. Всё остальное — (a). Тогда вопрос пишется в тетрадь под заголовком «Утром
   владельцу», а всё, что от него не зависит, продолжается: разбор лога, строки бэклога, утренний отчёт.
6. **(f) Ждёт прогон, а не человека.** Фоновый цикл `until` по `driver-runs.jsonl` и хвосту лога, с потолком
   инструмента не больше 10 минут на вызов, повторяемый, либо инструмент Monitor (форма цикла не взята из
   тетрадей: **не проверено на живом прогоне**). Сообщений владельцу ночью нет.
7. **(g) Своё состояние переживает сжатие контекста.** Носитель — тетрадь: pid, номер текущего лога, что ждёт и
   что уже решено, записываются в неё сразу. Хук PreCompact (`tools/compact_snapshot.py`, файлы в
   `docs/tasks/compact-snapshots/`) сохраняет только факты репозитория (незакоммиченные файлы, открытые диспатчи,
   следующий id, хвост журнала), а не рассказ; после сжатия читать новейший снимок и хвост тетради.
   Правило о сжатии (что и когда писать владельцу, снимок перед строкой) — `PROJECT.md`, «Прогоны и эксперименты».
8. **(h) Утренний отчёт**: докуда добралась стори (строка `[progress]` в хвосте лога), на какие вопросы ответили
   «мои» и почему, какие починки сделаны (файлы, коммиты), какие дефекты записаны (`B-nnn`), где были остановки,
   цена (дашборд и `driver-runs.jsonl`, источники должны сходиться, P18). Отчёт лежит в тетради под «Утром
   владельцу»; цена называется владельцу в ответе, а не пишется в файлы репозитория.
9. **(i) Держит параллель полной** — правило очереди и предел писателей: host-адаптация 6 `CLAUDE.md` (не больше 6 пишущих
   билдеров одновременно; дизайнеры, критики и скауты слотов не занимают). На каждом ожидании — завершился воркер, принят
   отчёт, прогон стоит на вопросе — ночной агент сверяется с планом (тетрадь, `experiments/dev-speed/next-steps-*.md` (в бандле истории), спеки
   узлов) и запускает всё, у чего готова спека, нет пересечения `owns` с живыми воркерами (правило 4 `CLAUDE.md`) и нет
   зависимости от невыполненного. Исключение одно: интеграционный прогон (`selftest.py` полный, `install_smoke.py`) идёт без
   параллельных правок пакета — на его время билдеры в пакете не стартуют, а дизайнеры, критики и скауты стартуют.
   Утренний отчёт (h) называет, сколько воркеров шло одновременно и где параллель простаивала.

### 9.2. Перед уходом

1. **Стенд (окружение) поднят и стоит на ревизии, которая нужна стори.** Как проверить, решает runbook проекта.
   Чекауты стенда принадлежат **владельцу**: сессия в них не делает `git checkout` и `git stash` (классификатор их
   закрывает). Нужна другая ветка стенда: попросить владельца переключить его до прогона, а не ночью. Просьба называет
   точный коммит или ветку и говорит, какая локальная правка стенда должна пережить переключение. Копии проекта для прогона
   делает `experiments/measurers/prepare_copy.py` (git worktree), живое дерево не правят.
2. **Поколение пакета в копии равно этому репозиторию (B-014).** Драйвер берёт пакет из `--plugin-dir`. Пакет на
   время прогона замораживают копией и синхронизируют только на остановке драйвера (выход 3) после зелёных тестов:
   прогон не ловит промежуточные правки соседних сессий. Для ночи с мандатом (п. 9.1) заморозка нужна, потому что
   ночной агент сам правит пакет в репозитории (9.1(b)): без заморозки такая правка вместе с недописанными
   правками соседних сессий попала бы в идущий прогон сразу. Без заморозки пакет в репозитории ночью не правят.
3. **Копия готова**: рабочее дерево целевого проекта на нужном коммите, с окружением, которое доказано (импорт
   пакета проекта, сбор тестов), и без артефактов прошлого прогона этого тикета (иначе стори с `pipeline.json`
   пропускает S0). Имя копии уникально для эксперимента; живое дерево проекта не трогается.
4. **Ответы на вопросы драйвера лежат готовыми** в `experiments/<эксп>/answers/`: один файл на вид вопроса.
   Для сравнительных прогонов ответы даются теми же словами каждый прогон. Вопрос, которого раньше не было, ночной
   агент закрывает сам по п. 9.1(a).
5. **Тетрадь эксперимента**: файл `experiments/<эксп>/<эксп>.md` по образцу тетрадей прежних прогонов (бандл истории);
   разделы «Подготовка», «Команда»,
   «Ход прогона», «Журнал вопросов и ответов», «Утром владельцу». В «Подготовку» записать стенд, коммит копии, пакет, судью.

### 9.3. Старт

1. Драйвер запускается **отдельным процессом**, не фоновым вызовом инструмента сессии: у фонового вызова потолок
   10 минут (так было на прогоне cmp1 проекта Test Project 1). Тот же класс — любой процесс, который должен пережить
   вызов инструмента или git-хук: его отцепляют от задания (job) сессии так, как это делает `tools/worktree_sweep.py`
   (`spawn_detached`: `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB`, повтор без последнего флага
   при `OSError`; замер 03.11.2026 — процесс жил 15 минут после возврата хука, спека t-1738 §5). `Start-Process` ниже даёт то
   же для PowerShell. Рабочая папка задаётся `-WorkingDirectory` (никогда `cd … &&`): драйвер надо запускать из
   корня проекта в копии, где лежит `qa-factory/config.json`, иначе `story_run: no qa-factory/config.json` (или
   передать `--project`).
2. stdout и stderr уходят в файлы `experiments/<эксп>/runs/<имя>-<N>.log` и `.err`; `N` растёт на каждый запуск
   драйвера. Вывод в файл без `PYTHONUNBUFFERED=1` пишется блоками: лог пуст часами, а процесс при этом жив или
   тихо умер (B-178). Поэтому переменная обязательна.

   ```powershell
   $env:PYTHONUNBUFFERED = "1"
   Start-Process -FilePath python -WorkingDirectory "<корень проекта в копии>" `
     -ArgumentList "<корень этого репозитория>/ai-packages/qa-factory/scripts/story_run.py","--task","<ТИКЕТ>","--env","<стенд>","--model","sonnet","--no-trace","--plugin-dir","<пакет>" `
     -RedirectStandardOutput "<корень этого репозитория>\experiments\<эксп>\runs\<имя>-1.log" `
     -RedirectStandardError "<корень этого репозитория>\experiments\<эксп>\runs\<имя>-1.err" -PassThru
   ```

   Аргументы драйвера (`--task`, `--env`, `--model`, `--no-trace`, `--plugin-dir`, дальше по стори `--mr`,
   `--skip-sources <файл>`) взяты из строк «Команда» в тетрадях наших прогонов на Test Project 1 (cmp1.md, cmp2.md). Точная
   форма `Start-Process` с редиректом по этим тетрадям не восстановима (в них записано только «`Start-Process`, pid …, лог …/.err»):
   **не проверено на живом прогоне**. `-PassThru` печатает pid: он нужен для строки старта.
3. Записать в тетрадь эксперимента строку старта: время, «`Start-Process`, pid N, лог `runs/<имя>-1.log` / `.err`»,
   поколение пакета (пример — cmp2.md, 01:40).
4. Перед уходом — один контрольный взгляд через пару минут: pid жив, `.err` пуст или без трейсбека. Сухой прогон
   без запуска ролей: тот же вызов с `--dry-run` печатает, что драйвер сделал бы в текущем состоянии.

### 9.4. Ночной цикл: остановки, ответы, починки, перезапуск

Драйвер выходит, а не ждёт (`design/driver.md`, «Exit codes»; в тетрадях прогонов Test Project 1 выходы 3/5 записаны в «Команде»). Каждый
выход разбирает ночной агент, не владелец:

| выход драйвера | что делает ночной агент |
|---|---|
| 0: стори закрыта, достигнут `--until`, остановка `pipeline.stop_after` или пауза `--max-boundaries` | закрыта или достигнут `--until`: перейти к утреннему отчёту (п. 9.5). Пауза по `--max-boundaries`: запустить ту же команду снова |
| **3**: нужен человек, вопрос в `qa-factory/artifacts/<ТИКЕТ>/state/driver-question.md` | прочитать вид вопроса (`kind:`, `stage:`) и ответить по 9.1(a): записать слова в файл `answers/…` и запустить ту же команду с `"--answer","<файл>"` и следующим номером лога (`<имя>-2.log`); строку записать в журнал вопросов тетради (чьи слова: заготовка, тикет или «мои»). Вопрос вида `package` — закрытый набор слов, они названы в самом вопросе. Вопрос, который по 9.1(e) только владельца, — под «Утром владельцу», прогон стоит, остальное делается |
| 4: дирижёр сдался, причина в том же `driver-question.md` | прочитать причину. Блокер фабрики (пример Test Project 1, cmp2 №14: честный отказ без строки драйвера) — починить по 9.1(b); висящий вопрос отодвинуть переименованием (не удалять), пакет синхронизировать, запустить **без** `--answer`: драйвер снова входит в тот же шаг (пример Test Project 1, cmp2 №15). Не блокер фабрики — ответить как при выходе 3 |
| 5: сбой под `claude -p` (вход, лимит, битый ответ) | повторить ту же команду: сообщение драйвера называет причину и команду продолжения. Если причина не уходит после трёх повторов с паузой не меньше 5 минут (число выбрано Lead 02.10, не из тетрадей): записать в тетрадь, вход ночью не вводить и лимит не обходить (9.1(e), «Утром владельцу»), заняться остальным (9.1(d)) |
| 1: ошибка самого драйвера (нет проекта, нет `claude`, пустой файл ответа) | прочитать сообщение: неверная рабочая папка, `--project` или пустой файл ответа — исправить вызов и запустить снова; дефект драйвера — 9.1(b) |
| процесс умер без выхода (в `driver-runs.jsonl` нет новых строк, лог молчит) | запустить ту же команду со следующим номером лога: ожидание из репетиции (шаг 9′) — драйвер подхватит диспатч в состоянии `running` без записанной сессии (`dispatch_liveness`/`recover`); **не проверено на живом прогоне**. Проверка, жив ли процесс: `Get-Process -Id <pid>` (общая команда PowerShell, не из тетрадей; **не проверено на живом прогоне**) |

Драйвер, запущенный заново без `--answer`, печатает тот же вопрос; после правки пакета это нужный способ
продолжить (пример Test Project 1, cmp2 №15/№16). Новая остановка с новым вопросом — снова круг по таблице; номер лога растёт на каждый
запуск, строка запуска (время, pid, лог, поколение пакета) каждый раз попадает в «Ход прогона». Между запусками
ночной агент ждёт по 9.1(f), а не пишет владельцу.

### 9.6. Правила

- **P8**: следов в целевом проекте нет: ни MR, ни комментариев и сабтасков в тикет-системе, баги только в md или в
  чате. Ночной агент не пишет в тикет-систему никогда, включая «починил» и «вопрос» (9.1(d)).
- **Сессия ничего не удаляет.** Ненужная копия отодвигается (переименовывается), не удаляется; удаляет только
  владелец. Из каталога `experiments/` и логов прогонов ничего не стирается. Устаревший артефакт и висящий вопрос
  отодвигаются переименованием.
- **Одна копия на эксперимент**: со своим именем; живое дерево проекта не трогается.
- **Цена**: читается с дашборда и из `driver-runs.jsonl`, источники должны сходиться (P18); расхождение печатается
  диапазоном и записывается находкой. Деньги в файлы репозитория (отчёт, тетрадь) не пишутся.
- **Стенд** переключает владелец (п. 9.2.1): сессия не делает `git checkout`/`git stash` в его чекаутах. Нужна
  другая ветка ночью — вопрос под «Утром владельцу» (9.1(e)).
- **Слово владельца не присваивается.** Ответ ночного агента помечен «мои» с причиной и живёт только в тетради
  эксперимента; слова владельца в журнале помечены «владельца» (так в тетради cmp2, пример Test Project 1).
- **Починка пакета ночью — настоящая починка**: корень причины, тест, проверка по `plans/builder-rules.md` п. 7b, строка `B-nnn`
  (`PROJECT.md`, «Как принимается изменение пакета»); никогда не заплатка в копии проекта.
- Каждый вызов без `cd … &&` и без ` 2>&1` (раздел 4 и `CLAUDE.md`, гигиена команд).

Что уже известно из прошлых прогонов (урок «код, который вместо двери выдаёт вопрос, делает роль дороже», замеры по

### 9.8. Фоновые ожидания

Фоновый цикл ожидания (`until grep -q DONE <файл>; do sleep 20; done`) не кончается, если воркер, которого он ждёт, умер: 16.10.2026
после потери сети два таких цикла шли три часа, пока владелец не заметила («опять задачи зависли»). Причина: у цикла нет
предела и нет хозяина после сжатия контекста, а harness держит его в списке фоновых задач. Правила: предпочитать разовую
проверку или уведомление harness; цикл — только ограниченный (`for i in $(seq 1 30)`), с названным файлом и концом ожидания
(builder-rules п. 13). После смерти воркера или потери сети СНАЧАЛА просмотреть список фоновых задач и остановить зависшие
(инструмент `TaskStop`); id устаревшей задачи без контекста находится по времени создания её файла `.output` в папке `tasks/`
сессии (пустой — у молчащего цикла).

### 9.9. После слияния

Слово владельца 20.10.2026: после каждого слияния узла и пуша проверить, что воркеры ничего не оставили. В тот день она
нашла «кучу зависших процессов»: одиннадцать пар bash от воркеров, закончивших часами раньше (их циклы `until … sleep` и
снимки оболочки), жили рядом с процессами живых воркеров. Шаг сразу после `git push`: перечислить процессы `bash|sh|python|sleep|docker`
старше отчёта воркера и убить их деревья; НЕ трогать процессы воркера, который ещё работает (сверять путь его worktree в командной
строке), и контейнеры стенда владельца (неделями «Up»: `<stand container>`; реальные имена — в compose-файле стенда MyBooks). Число убитых — в дополнение к снимку.

`claude-sonnet-5-5`; отношения — из `ai-packages/qa-factory/references/model-rates.json`, деньги в файлы не пишутся, P18).
Инструмент: `q9_cache_ttl.py` лежит в бандле истории (`experiments/run-sinks-12586/` до переезда); метод — ниже (правило перестройки то же, что в `q4c.py`: записано больше
половины контекста и контекст больше 50 000 токенов; зазор — время между первыми записями двух соседних ответов: в него
входят задержка API и повторы запроса, а простой до первой попытки виден по записям `api-request` в транскрипте, которые
инструмент не читает; зазор с повторами бывает длинным при живом кэше — `qa-test-strategist` S3 w2, запросы 21 и 24).

    (из бандла истории) python -I experiments/run-sinks-12586/q9_cache_ttl.py [--trace] [--until <ISO UTC>] [путь-к-сессии-без-.jsonl ...]

Без аргументов меряет две сессии из констант в начале файла. По источнику (дирижёр, роли) печатает суммы записи кэша по TTL
(`usage.cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`; нет поля — `n/a`, не 0), перестройки с
зазорами, каждый зазор больше 300 с и три сценария на наблюдённых перестройках: статус-кво (5m), TTL 1h, поддержание
(`floor(зазор/240)` дешёвых запросов вместо перестройки, бюджет `KEEPALIVE_MAX_POLLS = floor(1.25 / чтение)` = 12; точная
безубыточность — n опросов плюс первое чтение = (n + 1) x чтение против одной записи 1.25x, то есть n ≤ 11, бюджет 12 на
один опрос щедрее). Сценарии — оценка на данных, не переигровка: вся перестроенная запись считается чтением (верхняя граница
выигрыша 1h; приращение запроса остаётся записью — в среднем около 2 тысяч токенов на перестройку, цена 1h занижена примерно
на 0,5 %). Источник без запросов с `usage`, поле, которого нет ни в одной записи, и модель, для которой в каталоге нет
ставок кэша (Terra, модель судьи), печатаются `n/a` с причиной, не нулём и не падением; ИТОГО считается только по источникам одной
модели, иначе `n/a (mixed models)`.

### 10.6. Правило

**Ожидание дольше TTL маршрута = перестройка.** На гейтвее сегодня TTL 5 минут: любая пауза дирижёра дольше 300 с (роль в фоне,
вопрос человеку, ожидание ответа) стоит записи всего контекста заново — 0.2–0.7 млн токенов по 1.25x ставки входа в прогоне
12586. На маршруте с часовым TTL перестройка случается только после простоя дольше 3600 с, и поддерживать кэш опросами
(`story_step.py wait`, не строится: слово владельца 27.10) не нужно: опрос стоит чтение всего контекста (0.1x), и поддержание
окупается, только пока (n + 1) x 0.1 ≤ 1.25, то есть при n ≤ 11 опросов за простой (измерено: на 12586 ни один простой не
дал n = 12; бюджет `floor(1.25 / 0.1) = 12` из замысла B1 на один опрос щедрее точной границы).

2. A hand-back can be LOST from the transcript (the critic t-572's report arrived as a message but

3. A resume of a finished worktree agent fails "worktree could not be verified" about half the time — retry up

4. Two worktree creations in one second fail: one launch per turn; the orphan is removed with
   `git worktree remove -f -f` + `branch -D` + `prune`.
7. A builder's hand-off written to BOTH the worktree and the main path leaves an untracked copy on main that blocks the
   merge («untracked working tree files would be overwritten») — move the copy aside, then merge; if the branch did NOT
   track it, move it back after the merge (t-856).
8. The Agent tool often gives a builder NO worktree («launched in the primary checkout») — the dispatch text must carry the
   `git worktree add <path> -b <branch> <sha>` fallback, and the branch then lives in the main repo.
9. `git merge` refuses while the INDEX holds staged changes — even to files the merge does not touch: commit the staged part
   first, or `git stash push --staged`, merge, `stash pop`, re-`add`. The parallel cap counts a worker whose transcript was
   written in the last 10 minutes; a resume by `SendMessage` is not gated. A scout has NO Bash: a dispatch that needs a run or
   a bisect goes to a builder (t-878). Docker from Git Bash needs `MSYS_NO_PATHCONV=1` before `docker run … -v X:/repo -w /repo`.
10. The dispatch gate's path check reads prose too: a branch-only path named anywhere in the text needs
    `manifest-skip: given, owns -- <reason>` (both words when the path appears in both roles).

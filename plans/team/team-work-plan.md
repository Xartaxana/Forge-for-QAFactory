## 2. Принципы организации (что меняется для людей)

1. **Кучка (pile) = тема.** Папка `plans/piles/<slug>/`. У кучки — карточка для людей (`README.md`, один
   экран: зачем, что изменится для пользователя фабрики, зона файлов, пачки с размером/статусом/кто),
   пачки (`batch-N-<slug>.md`, граф узлов в форме `pre-release-0.9.md`), входящие находки
   (`findings/<yyyymmdd>-<slug>.md`, по файлу на находку).
2. **Пачка (batch) = единица, которую берёт один разработчик** с его Lead и воркерами, на своей ветке
   `pile/<slug>/batch-N`, от `origin/main`, с MR в `main`. Размер — с pre-release-0.9: 10–20 строк,
   ≤ 15 кодовых узлов, порядка суток. Пачка несёт всё для агентов: узлы, «пишет в», «зависит от»,
   общий бриф дизайнерам, DoD узлов, скоуп свидетеля, список живых доказательств (FR-33) и кому они.
3. **Взятая пачка замораживается.** Со статусом «в работе» в файл пачки пишет только взявший (ход,
   статусы узлов). Новое по теме идёт в `findings/` кучки и собирается в следующую пачку интегратором.
   Так один файл — один писатель, и слияние не конфликтует.
4. **Зоны файлов не пересекаются между пачками «в работе».** Кучки нарезаны по `plans/features.json`
   (globs фич) — файлы пакета уже привязаны к фичам, значит кучки по фичам почти не делят файлы.
   Горячие файлы (`story_run.py`, `hooklib.py`, `stage_guard.py`, `gate_preflight.py`,
   `install_smoke.py`, `controller.py`) — у двух пачек одновременно только с явной очерёдностью
   интегратора, как в 0.9 («билдеры по общим файлам идут последовательно»). Проверяет код (§3.2).
5. **Общие файлы — один писатель.** BACKLOG.md замораживается (архив + указатель на кучки); журнал —
   файл на разработчика; CURRENT_CONTEXT.md — только состояние `main` (≤ 10 КБ), ход пачки — в файле
   пачки; DECISIONS.md пишет только Lead владельца (другие — предложения в findings); CHANGELOG —
   фрагменты по пачкам, собираются при релизе.
6. **Обзор собирается кодом.** `plans/PILES.md` — генерируемая страница: кучки, описание, пачки, кто,
   ветка, статус, размер, стенд нужен/нет. Правится через карточки, не руками.
7. **Назначение и вопросы людей** — сначала в карточке (строка «взял: кто, дата, ветка»); зеркало в
   GitLab issues (issue на пачку, label на кучку, assignee) — по слову владельца, кодом по API с тем же
   проектным токеном, что читает CI (развилка §7.3).
8. **Интегратор один** — Lead владельца на `main`: раздаёт B-id находкам при сборке пачки (поэтому
   у находок до пачки id нет — нет коллизий номеров), сливает MR (`--no-ff`, канон-прогон, CI),
   делает релиз. Остальные разработчики — Lead своей пачки.
9. **Живые доказательства** (FR-33) — отдельная кучка, видимая людям: что и на каком стенде надо
   прогнать; у пачки стоит «стенд: нужен / не нужен», чтобы разработчик без стенда брал пачки,
   доказуемые CI.
10. **Слово владельца — только от владельца** (D-0025): в карточке и пачке решения подписываются
    «владелец, дата» или «Lead пачки, дата»; детектор — калибровка 13.

### 3.1 Раскладка

```
plans/
  PILES.md                         — обзор, генерируется (п. 3.2)
  piles/
    <slug>/
      README.md                    — карточка для людей (шаблон: plans/piles/_template/README.md)
      batch-1-<slug>.md            — пачка для агентов (шаблон: _template/batch.md)
      findings/
        20261008-<slug>.md         — находка (шаблон: _template/finding.md): что, где, свидетель,
                                     источник (кто, дата), FR/P, «кандидат наверх» — для B-229
  team/
    team-work-plan.md              — этот план
    backlog-inventory-2026-10-08.md
  BACKLOG.md                       — заморожен: шапка «закрыт 08.10, строки разложены по plans/piles/»,
                                     раздел «Закрыто» живёт дальше (интегратор переносит туда закрытое)
logs/
  journal/<dev>.jsonl              — журнал на разработчика (п. 3.4); routing-log.jsonl — история до 08.10
```

Карточка кучки (README): название; «зачем» для пользователя фабрики (3–5 строк, без id); зона
файлов (globs из features.json + явные исключения); стенд нужен/нет; таблица пачек: № | что меняется
для пользователя (одна строка) | строки | размер (S/M/L по сумме узлов) | статус | взял | ветка | MR.
Входящие: число находок и дата последней.

Файл пачки: шапка как у `pre-release-0.9.md` (правило готовности, решения владельца, порядок по общим
файлам, скоуп свидетеля), таблица узлов (Узел | Что | Исполнитель | Пишет в | Зависит от | Статус),
раздел «Ход» (журнал передачи Lead пачки — вместо CURRENT_CONTEXT), раздел «Живые доказательства»
(что, где, кто, сделано/нет), раздел «Остатки» (что ушло в findings).

### 3.2 Код: `tools/piles.py` (один инструмент, четыре команды, тест `tools/test_piles.py`)

- `split` — один раз: читает `plans/BACKLOG.md`, раскладывает открытые строки по кучкам правилом
  §4.0 (F-tag → кучка; без тега — по разделу и путям; спорные — список для Lead), пишет README-таблицы
  «кандидаты» и `findings/` из строк, не вошедших в первые пачки (строка бэклога → файл-находка с
  тем же B-id — id уже выдан, он сохраняется). Печатает отчёт: по кучкам и «нераспределено».
- `board` — собирает `plans/PILES.md` из карточек и файлов пачек (статусы, «взял», ветки, MR —
  из таблиц; число findings — из папок) **и оглавление всех B-id** (id → кучка → пачка / findings-файл /
  закрыто с хэшем; слово владельца 08.10: единый носитель оглавления обязателен). Запускается pre-commit
  хуком при изменении `plans/piles/` или `plans/BACKLOG.md` и падает, если PILES.md не пересобран (как
  `agents_md.py`).
- `check` — гейт commit-msg (сообщение коммита с дверью видит только он — критик t-587 Р2; `board --check` — в pre-commit, pre-merge-commit и CI): (а) каждый открытый B-id — ровно в одной кучке (в пачке или в findings);
  (б) пачки «в работе» не пересекаются по «пишет в» без строки «очередь: A → B» в обеих; (в) файл
  пачки «в работе» меняет только раздел «Ход» и колонку «Статус» (замороженность — сравнение с
  `origin/main` по строкам таблицы узлов); (г) в BACKLOG.md не добавилось строк `| B-` (заморозка);
  (д) у каждого узла пачки есть «пишет в» и исполнитель. Красный — отказ с названием пункта и дверью
  (строка `piles-skip: <пункт> -- <причина>` в сообщении коммита).
- `take <slug> <N> --who <имя>` — ставит «в работе / взял / ветка» в карточке и пачке и печатает
  команду создания ветки от `origin/main`; `close <slug> <N>` (бывший `release`) — закрывает пачку, переносит строки
  в «Закрыто» BACKLOG с хэшем MR.

Четыре вопроса механизма — в коммите узла. Детектор: калибровка, новая проверка 18 «кучки»: все
пачки «в работе» имеют взявшего и ветку; findings старше 14 дней без пачки; BACKLOG.md без новых строк.

### 3.3 Формат находки (= формат «входящих» для B-229)

Единственный носитель формата — шаблон `plans/piles/_template/finding.md` (заголовок; строка
`id: … | кучка: … | от: … | приоритет: … | кандидат наверх: …`; что не так; свидетель; принципы и
правила; «Решение владельца нужно»). Здесь он не повторяется, чтобы не расходиться (08.10 расходился:
этот раздел не знал `id`, `приоритет` и «Решение владельца нужно»). Имя файла `yyyymmdd-<slug>.md`
(`B-nnn-<slug>.md` — у перенесённых из бэклога); имя и строку-шапку проверяет код —
`tools/piles.py parse_finding`, ошибки видны в `piles.py check` и `board`. Куда класть и чего не трогать —
PROJECT.md «Командная работа» п. 2 и 5, README «Getting started» пп. 5–6.

Отчёт проекта (B-229) — набор таких файлов плюс статистика; раскладывается командой
`piles.py inbox <папка>` без перевода (команды ещё нет — часть постановки B-229 вместе с правилом
приёма чужих находок: кто принимает, кто назначает кучку, когда находка попадает в пачку).

### 3.4 Журнал на разработчика

`logs/journal/<dev>.jsonl`, `<dev>` — слаг разработчика из `delegation.config.yaml` (новое поле
`developer:`), ids `t-NNN` внутри файла, идентичность `<id>@<dev>` — та же модель, что сегменты B-402
(метка = разработчик, не ветка). `logs/routing-log.jsonl` — история до переключения, метка `main`.
Один загрузчик `tools/journal_keys.load_all()` отдаёт строки всех файлов с ключами; читатели
(`session_context`, `forge_metrics`, `calibration_counts`, `journal_echo`, `compact_snapshot`,
`dispatch_gate`, `agent_budget`, валидатор в pre-commit) идут через него — это и есть остаток B-454,
закрывается тем же узлом. Валидатор проверяет свой файл; слияние журналов перестаёт быть событием.
Запасной путь, если владелец хочет стартовать потоки раньше узла 3.4: один файл, слияние union +
сегменты по ветке — работает сегодня, цена — ручные строки идентичности при коллизиях id.

## 4. Кучки

### 4.0 Правило раскладки (для `piles.py split`)

1. Строка с меткой `[Fnn]` → кучка этой фичи (таблица ниже; две метки — первая).
2. Без метки: раздел 2 → «роли и контекст»; 3 → «драйвер и контроллер»; 4 → «текст человеку и
   гейты»; 5 → «деньги и дашборд»; 6 → «живые прогоны и новые проекты»; 7 и 0 → по путям в строке
   (tools/, plans/, docs/, .gitlab-ci.yml, experiments/ → Forge; пути пакета → фича файла по globs
   features.json); 8 → «роли и контекст» (джев, F20); 10 → по путям; 1 → «живые прогоны».
3. Строки, чей текст говорит «сделано / = другой строке» (B-420, B-299 → B-418, B-337 ↔ B-373,
   B-259 = B-364, B-309 (а)(в)) — список интегратору на закрытие словом, не в кучки.
4. Строки «ждёт слова владельца / решение владельца» — в карточку кучки раздел «вопросы владельцу»,
   не в пачку.
5. Спорная строка (пути из двух фич) — туда, где её главный файл; код печатает список для Lead.

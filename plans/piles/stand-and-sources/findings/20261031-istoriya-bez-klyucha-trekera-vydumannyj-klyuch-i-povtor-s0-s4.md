## Класс

У истории без ключа трекера нет своего пути: ключ «из головы» дирижёра не обязан быть допустимой формой, а форма ключа вшита в адаптер, id кейса, папки и закрепление. Допустимость выясняется на S4, через четыре стадии после выбора. Класс фабрики: значение, которое все стадии используют как идентичность (AR-4, AR-13), выдаёт один выдумывающий исполнитель без проверки формы при выдаче (FR-16: идентификатор разрешается через инструмент, который его производит, в момент записи).

## Слово владельца 31.10.2026

На фразу Lead «такой ключ не закрепляется формой Jira-ключа»: «Так как фабрика будет работать на разных проектах, то джира вообще не
должна быть определением, может быть тест реил, ишью гитхаба или ещё что. И поиск по родителям, привязанным/упомянутым тикетам,
комментариям и т.д. должен работать везде, вне зависимости от треккера» (владелец, 31.10.2026).

Что из этого следует для узла (Lead, 31.10.2026):
- форма ключа истории — свойство трекера проекта (строка данных вида трекера: Jira, TestRail, GitHub Issues, местный текст), а не
  форма Jira по умолчанию; местный ключ — такой же вид трекера, как остальные (AR-1, AR-5);
- обход источников — родитель, связанные и упомянутые задачи, комментарии, вложения — один механизм над адаптером трекера, а не
  код Jira: каждый адаптер отвечает на одни и те же вопросы («родитель», «связи», «упоминания в тексте», «комментарии»), а
  обход и глубина — общие (AR-6, P5). Для местного текста обход идёт по ссылкам и ключам, найденным в тексте, через адаптер того
  трекера, которому они принадлежат (в CART-1: ссылка на XPANBFLFA — Jira-адаптер). Связь: OH3-39 (`requirements_sources`), SS1-10.
- тест: фикстуры двух видов трекера (Jira и GitHub Issues) и местного текста со ссылкой — обход возвращает родителя, связанные
  задачи и комментарии в одной форме для всех трёх.

## Что именно менять

Направление выбрано по рекомендации Lead пачки и уточнено словом владельца 31.10.2026 (раздел выше): форма ключа — данные вида
трекера, не Jira.

1. **Один производитель местного ключа.** Новая команда рядом со снимком тикета в S0 (место — `scripts/ticket_adapter.py`; точное имя и подкоманду выбирает дизайнер узла) выдаёт ключ историй без трекера формы, которую принимает `adapter_forms.key_form` для вида трекера проекта; префикс и счётчик — данные (`references/adapter-forms.json`, строка вида `local`, AR-1), не литерал в коде. Если ключ уже занят файлом `qa-factory/tickets/<ключ>.md` — следующий номер. Дирижёр ключ НЕ придумывает: `skills/qa-story/phases/s0.md` на случае «ответ человека: тикета нет, есть текст» велит вызвать команду и записывает её вывод. Тест: фикстура проекта с `kind: jira` — выданный ключ проходит `adapter_forms.key_form(cfg).pattern`, второй вызов даёт другой номер.
2. **Проверка формы при записи ключа.** `story_step`/S0 при закреплении ключа (место записи `pipeline.json` — найти по коду) сверяет ключ с `adapter_forms.key_form` и отказывает по FR-1 с дверью «ключ не по форме трекера; выдайте местный ключ командой …» (FR-2: дверь, доступная дирижёру). Тест: ключ `ADD-TO-CART` отказан в S0 с названной формой и командой; ключ `CART-1` проходит.
3. **Вариант вопроса с исполнителем.** Вариант «расширить `key_pattern`» не предлагается, пока `key_form` для вида трекера игнорирует поле (`key_pattern_ignored`): текст вопроса собирается кодом из `adapter_forms` (FR-9, FR-13), а не пишется дирижёром по памяти. Тест: вопрос о форме ключа для `kind: jira` не содержит варианта `key_pattern`.
4. **Пробел для места чтения.** `case_versions.py --verify`, видя 0 найденных кейсов при непустой папке кейсов, не отвечает `verified: true` (FR-59, AR-28); сейчас комментарий в `case_versions.discover_cases` называет класс известным — если исправление уже в узле другой кучки, узел только ссылается (проверить по `plans/piles/*/batch-*.md`). Тест: папка кейсов с именами вне формы — `verified: false` и причина.

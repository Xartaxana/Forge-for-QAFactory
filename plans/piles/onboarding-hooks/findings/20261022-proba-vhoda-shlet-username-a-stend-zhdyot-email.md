# Проба входа фабрики шлёт `{username, password}` любому стенду; Test Project 1 ждёт `email` — 422, и онбординг записал это в бэклог проекта

перенос: hotfix-12586/batch-1 (узел HF1-4; слово владельца 23.10.2026 — срочная отдельная пачка; узел OH3-10 здесь закрывается её хэшем)

Слово владельца 22.10.2026: «надо отправлять то, что ждёт стенд».

Что не так: `scripts/stand_access.py` `_local_login` (строка 188) собирает тело входа литералом
`json.dumps({"username": user, "password": secret})` — для любого проекта с `access.kind: local_login`. Бэкенд Test Project 1
(`POST /v1/local-auth/login`) ждёт `email`: проба получила 422, а с `email` вход проходит с 200. Онбординг записал это строкой FB-3 в
`factory-backlog.md` **проекта**, хотя дефект — фабрики; стенд при этом рабочий. Сам проект знает правильную форму: SDK харнесса входит через
`testproject1_sdk/auth/credentials.py` `get_token` (`requests.post(...)` на тот же URL) — это и есть место вызова входа, которое P1 уже находит
(`project_inventory.py --access`).

Почему это дефект: имена полей тела входа — открытое разнообразие проектов (`username`/`email`/`login`/`user`, JSON или форма); литерал в
коде — закрытый список из одного элемента (AR-1, AR-2, P2, FR-13). P1 находит место вызова входа, но в `access` не попадает форма тела,
поэтому проба шлёт свою, а не проектную (AR-22: поле, нужное читателю, без производителя). И неверный хозяин: ошибка своей пробы записана
как пункт проекта (FR-19, AR-27).

Что сделать: (1) P1 читает форму тела из места вызова входа (ключи словаря/JSON, `data=` vs `json=`) и пишет её в `access` (например
`access.body: {"email": "<user_key>", "password": "<secret_key>"}` — имена переменных, не значения), с источником файл:строка; не прочитал —
строка вопроса о проекте не нужна: проба пробует известные формы из файла данных (`username`, `email`, `login`), берёт ту, что дала 2xx, и
записывает её как установленную пробой (FR-50: сначала все маршруты); (2) `_local_login` берёт форму из `access.body`, литерала нет;
(3) при 4xx проба читает ответ стенда (у 422 — имя отсутствующего поля) и называет его в квитанции, а не только код; (4) ошибка пробы
фабрики пишется в бэклог фабрики (находкой), не в бэклог проекта; (5) сиблинги по карте: `_oidc_password` (строка 227, форма OAuth2
стандартна — проверить, что её поля действительно фиксированы стандартом), `manual_capture.py` (рецепт полей формы входа UI — уже из
рецепта, сверить), другие пробы, где тело запроса к стенду собрано литералом.

backend ждёт `email`; с `email` вход проходит с 200»); `scripts/stand_access.py:176-199`;

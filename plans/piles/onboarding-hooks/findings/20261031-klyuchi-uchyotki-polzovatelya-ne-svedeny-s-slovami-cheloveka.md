Спека узла начинает с этих трёх чтений.

## Класс

Фабрика знает учётку роли в ТРЁХ видах, которые не сходятся: слова человека («используй такие-то переменные»), примечание в конфиге и файл значений, который читает бегун. Какая пара ключей ведёт к роли, — открытое разнообразие проектов (AR-2): назвать пару может человек, а запись роли в конфиг делает дирижёр, не код. Дыры: слова человека не доходят до записи роли (AR-24), гейт ищет значения не там, куда указывает конфиг (AR-3), а роль, которую нельзя войти, молча подменяется другой учёткой (AR-28).

## Что именно менять

Направление выбрано по рекомендации Lead пачки (до слова владельца; отменяется словом). Дизайнер узла находит точные функции; ниже — что и тест на каждый пункт.

1. **Гейт A ищет значения там, куда указывает конфиг.** `gate_preflight._stand_account` (и `_env_names`) берут список env-файлов бегуна из ключа конфига, который называет `.env.local` (имя ключа — найти по коду, см. «Не проверено»), а в карточке называют тот файл, где ключ искали и не нашли; если файл конфига не существует — карточка говорит «файл не найден» и называет путь, а не «не заполнено». Тест: фикстура, где `credentials_by_role.user` называет `USER_EMAIL/USER_PASSWORD`, значения лежат в `.env.local`, а конфиг на него указывает, — роль `met`; тот же конфиг без файла — `unmet` с названием файла.
2. **Слова человека о ключах доходят до записи роли дирижёром, у него есть дверь.** Ключи в свободных словах читает дирижёр, не код (P22, FR-12): новая команда (рядом с `config_set` или аналогом; существует ли — проверить) записывает пару ключей роли в `environments[].credentials_by_role.<роль>` и пишет находку «записано по слову человека». После записи `account_keys(примечание)` отдаёт именно эту пару. Гейт A при несовпадении «в слове человека пара X, в записи роли пара Y» не гадает, а задаёт один закрытый вопрос «какую пару использовать для роли `user`» с обоими вариантами (FR-9). Тест: запись пары командой — `account_keys` и `resolve_actor(cfg, stand, "user")` отдают новые ключи; вход `--as user` берёт их.
3. **Роль без собственной учётки не подменяется молча.** Когда у плана есть роль `user`, а автоматор или runner получили только пару админа, это строка в brief и в отчёт «роль `user` проверена под админом: пара для `user` не записана» (FR-41, AR-28); никакого тихого `--as default`. Тест: бриф S5 для плана с ролью `user` и без пары для неё несёт эту строку.
4. **Онбординг спрашивает пару один раз и пишет роль.** Фаза P2 онбординга (`skills/qa-onboarding/phases/p2-interview.md`) для каждой роли, которой нет в примечаниях, спрашивает «какие переменные хранят логин и пароль роли …» с вариантами из имён, найденных в env-файлах проекта (имена — только как кандидаты; выбирает человек, AR-2), и пишет примечание. Тест: eval онбординга на проекте с `.env.local` — вопрос один, пара записана. Узел согласуется с OH3-35 (диета вопросов): вопрос заменяет, а не добавляет, пять повторных «да» стенда.

# Доктор: «API GitLab отвечает „не авторизован“ (токен `glab` 401)» — не говорит, что токен есть, но от другого хоста, и что делать

id: — | кучка: `onboarding-hooks` | от: владелец, 22.10.2026 (доктор 0.10.0 на `testproject1-dev-010/testproject1-sdk/test-harness`) | приоритет: П2 | кандидат наверх: нет

Что не так: строка доктора человеку: «vcs_api missing owner: user — API GitLab отвечает „не авторизован“ (DD-1, токен `glab` 401). Git по
SSH работает (ls-remote проверен). Блокирует только операции с API: метаданные и обсуждения MR». Владелец прочитал это как «фабрика
не видит мой токен» — а токен есть. Измерено 22.10: `glab auth status` — вход только в `git.example.com` токеном из переменной `GITLAB_TOKEN`
(проектный бот `project_100001_bot_…`, токен репозитория разработки фабрики); проект testproject1-sdk живёт на `git.example`
(`git remote get-url origin`); `glab api --hostname git.example projects/tp1-group%2Ftestproject1-sdk` → `401 Unauthorized`, тот же вызов на
`git.example.com` → 200. Вдобавок `glab` пишет, что `GITLAB_TOKEN` из окружения перебивает токены всех хостов: даже после `glab auth login
--hostname git.example` вызов уйдёт с чужим токеном.

Почему это дефект: строка с `remedy.owner: user` обязана сказать человеку, что сделать, и где взять то, чего у него нет, с минимальными
правами (`skills/qa-doctor/SKILL.md`, «Rules of printing»: «A step needing something the person does not hold says where to get it, with the
minimal rights»). Здесь шага нет вовсе, а причина названа кодом ответа и внутренними метками (`DD-1`, `vcs_api`), без хоста. Фабрика
знает всё, чтобы сказать по делу: хост проекта (из `origin`), хост, для которого есть токен (из `glab auth status`), и источник токена
(переменная окружения).

Что сделать: (1) проба `vcs_api` различает случаи: нет токена вовсе / токен есть, но для другого хоста / токен этого хоста отвергнут
(просрочен, нет прав) / переменная окружения перебивает токен хоста — и пишет это в квитанцию; (2) доктор печатает человеку шаг по случаю,
языком действий, например: «У вас есть токен GitLab для git.example.com, а проект на git.example. Создайте на githost персональный токен с
правом `read_api` (для записи в MR — `api`) и выполните `glab auth login --hostname git.example`. Переменная `GITLAB_TOKEN` в окружении
перебивает его — уберите её или переименуйте»; без `DD-1`, `vcs_api`, `missing`; (3) эвал доктора: 401 при токене другого хоста → шаг с
хостом и правами. Сиблинги: остальные строки `owner: user` в отчёте доктора и `adapters.*` в readiness — каждая называет, где взять
недостающее.

Свидетель: скриншот владельца 22.10; `glab auth status` и два вызова `glab api` из сессии Lead 22.10.

# Упавший файл канона прячет дальнейшие красные: читать stderr, не только последнюю строку

id: — | кучка: `onboarding-forge` | от: Lead, 28.10.2026 | приоритет: П2 | кандидат наверх: нет

Источник: строка диспатча t-1437; дополнительных подробностей в репозитории не найдено.

Что не так: тестовый файл BATCH CANON, который падает с исключением (а не красными ключами), обрывает свой прогон: ключи после падения не выполняются, и сводка канона показывает один красный файл, хотя за ним могут стоять ещё красные. Последняя строка вывода называет только последнюю ошибку; причина и соседи видны в stderr. Читающий канон по последней строке (или по сводке «N/M ok») принимает один красный за все.

Что сделать: читатель вывода канона (интегратор; рецепт канона F6-34, `tools/batch_canon.py`, если он взят) читает stderr упавшего файла целиком, перечисляет причину падения и число не выполненных ключей, а сводка помечает файл как «упал, ключи не выполнены: N» (не «1 красный»); правило в `docs/RUNBOOK.md` рядом с рецептом канона.

Края: файл упал на импорте (ни одного ключа) — «не выполнено: все»; пустой stderr при ненулевом выходе — отдельная строка «упал без вывода» (см. находку про warn_once, она в той же пачке).

Свидетель: слово Lead 28.10.2026 (строка диспатча t-1437); конкретный прогон канона не назван, при разборе узла приложить вывод, где красные вскрылись после починки первого.

Принципы и правила: FR-26, FR-41, FR-55.

Решение владельца нужно: нет.

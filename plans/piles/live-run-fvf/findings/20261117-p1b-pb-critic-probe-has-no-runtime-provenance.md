# У окна критика кода нет производителя записи среды выполнения: `handoff_check.window_runtime_record` читает только блоки запусков

id: — | кучка: `live-run-fvf` | от: Lead, 17.11.2026 (вердикт t-1070, узел P-b) | приоритет: П1 | кандидат наверх: нет

Что не так: `handoff_check.window_runtime_record` (`handoff_check.py:525-580`) берёт происхождение среды выполнения только из блоков
запусков `work/run-blocks/` своего диспатча. Проба критика кода (`red_probe`) блока запуска не пишет (`build_run_block` возвращает
`None` для `purpose == "red_probe"`, `run_suite.py:470-473`), поэтому у поля `probes.runtime_provenance` контракта
`s5-critic-to-automator` нет производителя, а выход S5 критика отказывает по полю, которое ему нечем заполнить. Текст отказа
`_RECORD_PRODUCER` (`:522`) называет дорогу («когда `run_suite` запускает тесты этого диспатча»), которой у критика нет (FR-2).
Класс фабрики: вывод поля (deriver), чьего входа нет на контракте, который это поле перечисляет; тот же класс — любой читатель,
требующий состояние, которое ничто на дороге роли не производит.

Что сделать (направление выбрано Lead, 17.11.2026, по рекомендации критика t-1070, до слова владельца): запасной источник — в
`window_runtime_record`, когда ни один блок запуска диспатча не несёт записи, читать `runtime_provenance.evidence_refs[0]`
НОВЕЙШЕГО запроса `red_probe` ЭТОГО диспатча в `work/probe-requests/`, разрешая путь тем же правилом «внутри стори»
(`handoff_check.py:567-580`); блок запуска сохраняет приоритет (для автоматора и раннера результат байт в байт прежний, запрос пробы
никогда не перекрывает собственный блок диспатча); в том же ходе переписать `_RECORD_PRODUCER` так, чтобы он называл пробу как
дверь, которую критику выдают. Строки таблицы `test_handoff.py`: запрос пробы своего диспатча с существующим файлом доказательства —
заполнено; только запрос чужого диспатча — пусто; `evidence_refs` пуст или называет отсутствующий файл — пусто с названной
причиной. Карточка в работе: `docs/tasks/specs/20261117-p1b-pb-runtime-provenance-card.md` (дизайнер t-1072). Узел меняет СМЫСЛ
источника вывода: дизайнер, затем критик на план до билдера (PROJECT.md, п. 6 «Как принимается изменение пакета»). Альтернатива
(`run_suite` пишет блок для `red_probe`) не рекомендована: `run_suite.py:470-473` держит мутированные красные вне реестра нарочно.

Свидетель: `docs/tasks/specs/reviews/t-1070-p1b-main-s5-residue-diagnosis.md:72` («`window_runtime_record` (`handoff_check.py:525-580`)
reads only `work/run-blocks/` blocks whose `dispatch_id` is this dispatch») и `:70` («`build_run_block` returns `None` for
`purpose == "red_probe"` (`run_suite.py:470-473`)»); раздел K3 и узел P-b (`:91-100`). После правки сухой основной проход
(`--part main`) проходит S5 или печатает следующую остановку дословно.

Принципы и правила: FR-11, FR-5, AR-22 (также FR-2, AR-13).

# Доктор и readiness видят стенд «живым», когда `stand_health` говорит «down, сломан путь фронтенда к API»

id: — | кучка: `driver-hosts` | от: дизайнер t-1422 (RH1-7), критик на план t-1422 (ответ 6), Lead, 28.10.2026 | приоритет: П3 | кандидат наверх: нет

Что не так / что сделать: после RH1-7 `stand_health.py --probe` знает цепочку стенда (сеть → API → фронтенд → путь фронтенда к API) и называет мёртвую часть. `env_probe.probe` (строка `liveness` доктора, readiness, онбординга) по-прежнему спрашивает только собственный адрес API (`env_probe.py:538-545`): у `env_probe` нет цепочки фронтенда. При живом API и сломанном прокси фронтенда (B-163) доктор печатает `liveness: alive`, а `stand_health` — `down, frontend_proxy`: два взгляда на один стенд расходятся. RH1-7 только называет это в тексте доктора (N6).

Решение спеки: либо `env_probe` получает отдельную строку «frontend: …» по той же таблице `references/stand-answers.json` и тому же порядку (без изменения вердикта `liveness`, который решает, пробовать ли вход, `env_probe.py:567`, и кода выхода readiness), либо доктор вызывает `stand_health --probe` и показывает его `diagnosis`. Радиус поражения другой, чем у RH1-7 (вход и выход readiness), поэтому отдельный узел.

Свидетель: спека `docs/tasks/specs/t-1422-rh1-7-stand-health-and-login-record.md` §8 ось 5 и §13; ревью `docs/tasks/specs/reviews/t-1422-rh1-7-plan-critic.md`, ответ 6.

Принципы и правила: FR-10, FR-41, AR-19, AR-28.

Решение владельца нужно: нет.

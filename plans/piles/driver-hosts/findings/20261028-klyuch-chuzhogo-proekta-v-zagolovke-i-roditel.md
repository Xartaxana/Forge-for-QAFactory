# Ключ чужого проекта в заголовке тикета (TP6-n) читается как тикет и даёт 404; родитель берётся, хотя стори не о нём

id: — | кучка: `driver-hosts` | от: отзыв пользователя Dev6 (TP2-2702), плагин 0.10.x, 28.10.2026 (разбор t-1553) | приоритет: П2 | кандидат наверх: нет

## Что наблюдалось

Слова пользователя, как написаны: «When I gave it jira ticket, it took it perfectly, but was confused with the TP6-xxx part of the title in the ticket, and the scout read it as if it was a separate ticket key and tried to fetch it, which gave HTTP 404. Then later, it took the parent ticket as well. I had to explain that we are not working on the parent ticket and explain that TP6-xxx is not a separate ticket.»

Два случая одного класса: фабрика берёт источник по формальному признаку (форма ключа в тексте; поле `parent` в снимке), не спрашивая, относится ли он к стори. Человеку пришлось объяснять оба раза.

## Где в коде

Из разбора t-1553 (`docs/tasks/handoffs/t-1553-feedback-sara-recon.md`, пункт 1; пути от `ai-packages/qa-factory/`; номера строк проверить по коду при взятии):
- Форма ключа — одно определение, `scripts/ticket_light.py:50-53` (`KEY_RE`, форма Jira по умолчанию, данные `references/adapter-forms.json`). `TP6-123` в заголовке подходит.
- Заголовок и описание сканируются как «упоминания»: `scripts/source_inventory.py:1111`, затем `ticket_light.references()` (`ticket_light.py:1040-1070`): каждый найденный ключ — строка `not_fetched`, с пометкой `other_project`, если префикс не свой.
- Является ли чужой префикс трекером: `source_inventory.py:1714-1745` `_project_prefix_status`; 404 даёт `not_tracker` только когда доступ уже доказан другим читаемым тикетом, иначе `unproven` и ключ остаётся кандидатом. Кандидата скаут «подглядывает» (`peek`, `agents/qa-scout.md:33-37`); 404 на этом шаге — вероятный источник ошибки пользователя (вывод из кода, не наблюдение).
- Список префиксов-не-трекеров — данные: `references/jira-fields.json` `not_tracker_prefixes` (`source_inventory.py:154-163`); унаследованного префикса проекта там нет.
- Родитель: поле берётся кодом (`ticket_light.py:736-743`, ключ снимка `parent`), а читать ли его — политика текста роли: `agents/qa-scout.md:31` («Required sources are the task, named subject, immediate parent/feature…»), `references/coverage-design.md:9-10`. То есть чтение родителя задумано, а не ошибка; ошибка в том, что родитель читается как область работы, а не как контекст.
- Дверь человека есть, но не была предложена вовремя: список исключений `scripts/source_exclusions.py` (до прогона) и «первая остановка» скаута (`qa-scout.md:41-44`).

Ограничение вывода: прогона TP2-2702 в руках не было, причина выведена из кода.

## Класс

Источник, найденный по форме, а не по связи: ключ в тексте и родитель — «кандидаты по форме». Тот же класс, что чужой 404 на чтении тикета (B-450, SS1-1), и тот же принцип P5/FR-50 (получать данные всеми способами, но не придумывать источники). Ошибка по такому кандидату — запись `unavailable`/`not_relevant`, а не ошибка, которую человек должен объяснять. Не блокер: двери есть.

## Решения владельца

Владелец, 28.10.2026: «не в 0.10.5, в пачки». Правило (что считать источником) — решение замысла: ключ другого проекта трекера из текста — источник только если тикет его связывает; роль родителя — контекст, не область; человеку — дверь «это не источник / это источник». Решение владельца нужно: да — по правилу ключей из текста и роли родителя (узел SS1-10).

Принципы и правила: P2, P5, FR-1, FR-13, FR-50, FR-59, AR-1, AR-6.

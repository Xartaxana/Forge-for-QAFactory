## Почему

1. Дирижёр без драйвера — исполнитель команд (P3 нарушен по построению): на каждый диспатч 3–4 вызова `story_step`, на каждый отказ — разбор.
2. Всё, что вернули роли и гейты, остаётся в контексте одной сессии на весь прогон (S0–S9, 6 ч 51 мин), сжатия или смены дирижёра на
   границе стадий нет.
3. Возобновление агентов `SendMessage` вместо хода контроллера (HF8-15) — лишние круги через дирижёра.
4. Ручной исполнитель получает три кейса подряд, а не по одному; засев данных Given пишет сам (готового засева кейса нет); API и хелперы
   ищет grep'ом; проба рантайма делается в S6, а не до неё (EP1-24).

## Что нужно

1. Один вызов на шаг диспатча: `story_step` делает start+bind одним ходом при запуске агента и finish+проверку формы при его возврате (хук
   `SubagentStop`), дирижёр зовётся только на отказ (P3, P22).
2. Дирижёр на стадию: на границе стадии — свёрнутое состояние из `controller.json` и свежая сессия (или сжатие), в контекст попадают только
   дайджесты ролей, не их отчёты.
3. S6 manual-agent — окно на кейс (как окна S5), параллельно, где кейсы не делят данные.
4. Засев Given — скрипт кейса (S4 пишет, S6 исполняет), бриф S6 несёт API-методы и хелперы харнесса затронутой области (карта репо);
   проба рантайма — до S5 (EP1-24).
5. Детектор: дашборд помечает марафон (ход > N или контекст > 300K) и называет причину по классам вызовов — не только «max 299».

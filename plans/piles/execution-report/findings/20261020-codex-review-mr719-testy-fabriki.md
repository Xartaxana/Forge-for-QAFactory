# TC-008 — Visual Diff и основной редактор
Сценарий проверяет, что при открытом Visual Diff команды Delete, Undo, Duplicate и попытка перетаскивания не меняют ни diff, ни скрытый workflow. Перед открытием popup выполняется положительный контроль Delete/Undo; затем сравниваются состояние diff и YAML редактора.
## Проблема 1. Сравнение YAML может пропустить изменение буфера
Контекст. TC-008 сохраняет YAML до открытия Visual Diff и сравнивает его с содержимым после закрытия popup.
Приоритет: P1 · потенциальный false positive
Файлы:
base_workflow_form_page.py:266–273 — новый read_editor_yaml()
test_workflow_visual_diff_shortcuts.py:78, 103–106 — два вызова и сравнение
workflow_config_panel.py:334–376 — существующий get_yaml_content()
Проблема. Новый метод читает Ace через yaml_editor_text_layer.inner_text(). Сопоставление с существующим get_yaml_content() показывает, что framework уже читает содержимое через editor.getValue(); комментарий к нему прямо предупреждает о неполноте и потере форматирования при чтении отображаемого текста.
Последствия. Два совпадающих неполных представления могут дать PASS, хотя невидимая часть YAML изменилась.
Рекомендация. Использовать чтение Ace session через editor.getValue() без strip() и удаления meta_states: здесь проверяется точное равенство исходного буфера.
Статус. Недостаток подтверждён по коду; фактический false positive не воспроизводился.
## Проблема 2. Delete и Undo могут взаимно скрыть дефект
Контекст. TC-008 должен доказать, что каждый shortcut не воздействует на скрытый редактор.
Приоритет: P1 · потенциальный false positive
Файлы:
workflow_version_history_popup.py:165–170 — press_canvas_shortcuts()
test_workflow_visual_diff_shortcuts.py:80–106 — вызов и итоговые проверки
Проблема. Delete, ControlOrMeta+z и ControlOrMeta+d выполняются подряд; состояние редактора проверяется только после всей последовательности. Положительный контроль с закрытым popup предусмотрен, но промежуточных assertions нет.
Последствия. Если Delete ошибочно удалит узел скрытого редактора, а Undo восстановит его, итоговое сравнение может пройти.
Рекомендация. Проверять инварианты после каждого shortcut независимо; сохранять положительный контроль.
Статус. Логическая слабость подтверждена; реальное прохождение ошибочных событий в скрытый редактор не воспроизводилось.
## Потенциальный риск — геометрия Visual Diff
Контекст. В TC-008 после попытки drag координаты узлов сравниваются с исходными.
Приоритет: P2 · неподтверждённая гипотеза
Файлы:
workflow_version_history_popup.py:152–163 — diff_snapshot()
test_workflow_visual_diff_shortcuts.py:80–96 — сравнение bounding_box()
base_workflow_form_page.py:339–377 — существующий подход для проверки перемещения
Наблюдение. diff_snapshot() ждёт появления первого узла и затем считывает bounding_box() всех узлов. Сравнение точное, без допуска. Если ReactFlow продолжает размещение графа после появления первого узла, возможен FAIL без фактического перемещения.
Оценка. Прямого подтверждения нарушения подходов framework или дефекта не обнаружено. Асинхронное изменение координат конкретного Visual Diff не проверено. При необходимости стоит проверить стабильность layout без пользовательских действий; до этого требовать исправления оснований нет.
# TC-014 — права доступа к /validate
Сценарий проверяет отказ в валидации workflow для пользователя вне проекта и пользователя без WRITE permission; сохранённый workflow не должен измениться.
## Проблема 3. Любой HTTP 4xx засчитывается как отказ по правам
Контекст. В тест передаются TC014_OUTSIDE_USER_TOKEN и TC014_READONLY_USER_TOKEN из внешней конфигурации.
Приоритет: P2 · потенциальный false positive
Файлы:
test_workflow_validate_endpoint.py:238–268 — проверка ответа
test_user_role_permissions.py:151–186 — пример существующего permission-теста
Проблема. Используется is_in(range(400, 500)) с комментарием exact code oracle_unknown. Сопоставление с существующим test_provider_management_denied показывает более точную проверку: успешный GET для подтверждения доступа пользователя, затем 403 и код причины отказа для запрещённых операций. В TC-014 подлинность и роли токенов предварительно не подтверждаются; при отсутствии токенов тест пропускается.
Последствия. 401 из-за недействительного токена, 400 из-за запроса или 404 из-за отсутствия ресурса могут дать PASS без проверки требуемого ограничения доступа.
Рекомендация. Установить контракт /validate; проверить действительность токенов и ожидаемые права, затем конкретный статус и, если доступен, стабильный код причины отказа. Skips учитывать как пробел покрытия.
Статус. Слабость oracle подтверждена; контракт endpoint и реальные права пользователей не проверены.
# API /validate — тестовые данные
Сценарии endpoint используют fixture own_workflow для создания независимых workflow с заданным YAML.
## Проблема 4. Имена тестовых workflow не совместимы с session cleanup
Контекст. Fixture создаёт имена вида TC010-<uuid> и не содержит teardown.
Приоритет: P2 · управление тестовыми данными
Файлы:
test_workflow_validate_endpoint.py:59–75 — fixture own_workflow
tests/__init__.py; tests/utils/base_utils.py — autotest_entity_prefix
tests/ui/workflows/conftest.py:157–187 — fixture с teardown
tests/conftest.py — отключённый pytest_sessionfinish и фильтрация по prefix
Проблема. Существующий framework применяет autotest_entity_prefix для идентификации тестовых сущностей. В отключённом session cleanup workflow отбираются по наличию prefix в имени. Новый код использует только локальный префикс TC и UUID, поэтому эти ресурсы не будут найдены указанным фильтром. Отключение session cleanup из-за HTTP 500 (TP1-13156) — ранее существовавшее ограничение.
Последствия. Workflow могут накапливаться и останутся вне prefix-based очистки даже после её восстановления. Отдельные механизмы удаления существуют; утверждение о невозможности любой очистки не делается.
Рекомендация. Добавить autotest_entity_prefix и учёт созданных ID для последующей очистки. При реализации teardown учитывать текущую ошибку удаления.
Статус. Несоответствие именования и отсутствие teardown подтверждены; runtime-удаление не проверялось.

## Предложения по улучшению
Единый способ чтения YAML. Для сценариев, проверяющих точное содержимое редактора, использовать существующий get_yaml_content() на основе Ace API, а не создавать второй способ чтения через DOM. Это уменьшит расхождение поведения helpers.
Независимые проверки действий. В сценариях с последовательностью shortcuts делать assertions после каждого действия, а не только после всей цепочки. Положительный контроль сохранить; это улучшает диагностику и локализацию ошибки.
Явные контракты UI. Для проверок переименованных элементов указывать подтверждённый источник UI-контракта рядом с тестом или в связанной спецификации, не дублируя длинные объяснения в каждом Page Object. Актуальность источника в этом review не подтверждена.

# `calibration_counts.py` по умолчанию читает только `routing-log.jsonl` и не знает ветку `replaces_worker`

id: — | кучка: `forge` | от: Lead, 14.10.2026 08:00 (первая недельная калибровка, проверка 3) | приоритет: П2 | кандидат наверх: нет

Что не так: (1) `python tools/calibration_counts.py --window-start … --window-end …` без `--journal` считает только
`logs/routing-log.jsonl` (история до 08.10): 186 событий в окне, а в `logs/journal/dev1.jsonl` — 326; карта t-740
говорила «все журналы через journal_keys» — неверно, флаг `--journal` надо передавать дважды. С D-0036 журнал — файл
на разработчика, и инструмент калибровки обязан брать их все сам (`journal_keys` — один загрузчик). (2) Раздел «Repeated
delegated by task_id» классифицирует повторы `delegated` только как critic-entry / retry; замена мёртвого воркера с
бареным токеном `replaces_worker:<ref>` (валидатор её принимает, D-0038) выходит как «other — anomalous repeat, needs a
human verdict»: 12 строк в dev1.jsonl (t-597, t-614, t-620, t-658, t-676, t-687 ×2, t-691 ×2, t-733, t-740, t-741) и
3 в routing-log (t-505, t-575, t-585). Детектор проверки 3 кричит на законную ветку — шум, за которым потеряется
настоящий дефект.

Что сделать: загрузка по умолчанию — все журналы через `journal_keys` (как у `session_context`/`forge_metrics`),
`--journal` остаётся переопределением; ветка `replaces_worker` в классификаторе повторов с проверкой, что ref совпадает
с `worker_ref` более ранней строки той же задачи (та же логика, что в `journal_validator`, — импортировать, не копировать:
дублирование запрещено рамкой критика). Тест: журнал с заменой → строка классифицирована `replacement`; ref без пары →
`other`. Детектор: калибровочная проверка 3 (счёт «other» в выводе инструмента должен быть 0 при чистом журнале).

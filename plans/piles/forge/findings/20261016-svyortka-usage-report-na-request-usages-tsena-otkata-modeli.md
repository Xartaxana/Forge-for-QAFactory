# Свёртка `usage_report.iter_assistant_turns` на `transcripts.request_usages` меняет цену запроса с откатом модели: оба читателя считают его неверно

## Что

Свёртка (ось 14, один читатель транскриптов) на реальных 1968 файлах даёт те же 123 835 строк и те же суммы токенов, но ОДНА
строка (`cb6de03f…:req_011CeTQm…`, 27.08) меняет цену $0.0588 → $0.1298 (итог $5934.39 → $5934.46). Причина — запрос с откатом
модели: его строки несут разные модели и разные usage. Старый читатель склеивал токены первой строки с ценой последней;
новый берёт MAX токенов и цену первой модели. Правила для такого запроса нет ни у одного — оба «не правы» (FR-41/FR-25: две
записи одной величины расходятся, а отчёт не называет верную). Побочно: в свёртке неверный тип usage роняет первый `next()`
(нужен гард), а строка без `requestId` и `uuid` держит ключ `session:None` (старый недосчёт).

## Чинить

(1) Правило цены запроса с откатом модели — в `transcripts.request_usages` одним местом: каждая строка запроса оценивается своей
моделью и суммируется (или названное иное правило — решение Lead по замеру на этой строке); (2) свёртка из ветки
`t-861-f6-15-fold` поверх правила, с гардом на неверный тип usage и с ключом для строк без `requestId`/`uuid`; (3) пин: та самая
строка 27.08 как фикстура с ожидаемой ценой по правилу; `--days 1` итоги до/после равны в закрытом окне (15.10). Детектор:
калибровочная проверка 11/34 (расхождение итогов двух читателей при одной выборке).

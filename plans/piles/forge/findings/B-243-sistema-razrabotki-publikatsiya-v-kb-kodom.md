# Система разработки: публикация в КБ кодом по REST с персональным токеном

id: B-243 | кучка: `forge` | от: новое, 01.10 — после эксперимента владельца | приоритет: — | кандидат наверх: нет

Что не так / что сделать: **Система разработки: публикация в КБ кодом по REST с персональным токеном.** Сегодня kb.example.com за SSO пишется XHR-ом из вкладки Chrome: кусками по 4000 Б gzip+base64, вкладка виснет, шесть страниц — «десятки минут» (RUNBOOK §3). У DMtools Confluence — обычный REST-клиент с токеном (`Confluence.java`: POST `content` storage, PUT `content/<id>` version+1, multipart вложения, дети `child/page`), без браузера. **Сначала один эксперимент владельца** (`CLAUDE.md` п. 6а): создать PAT в профиле kb.example.com (Confluence Data Center поддерживает Bearer-токены) и выполнить самой одну команду `curl -H "Authorization: Bearer <PAT>" https://kb.example.com/rest/api/content/2921309391?expand=version`; 200 → `tools/kb_publish.py (removed at the move)`: из `kb/*.xhtml` PUT version+1 с проверкой числа `<ac:image` (RUNBOOK §3 п. 5), вложения multipart с заменой по имени, dry-run с диффом, без удалений, токен только из переменной окружения; путь через Chrome остаётся запасным. 401/403 → пункт закрывается «нельзя» с выводом команды. Цена: ноль LLM; экономия — минуты вместо десятков минут на каждую публикацию.

Свидетель: Владелец 01.10 («обновление КБ сложно, долго и дорого»); карта §4 п. 1.

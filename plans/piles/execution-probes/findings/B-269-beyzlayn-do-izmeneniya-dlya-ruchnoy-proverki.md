Сценарии: (A) изменение существующего поведения («было X → стало Y», P20 — человек подтверждает намеренность); (B) багфикс — «до» = воспроизведение из бага (вложения, шаги); (C) новая поверхность — «до» нет, показываем «как реализовано сейчас» + `absent`; (D) стори тестируется ДО реализации — «до» = текущий main, он же на стенде; снятое становится бейзлайном для «после»; (E) визуальные/UX-изменения (15045: visual diff) — заявка из кода слаба, нужен снимок; (F) регрессия вокруг изменения — список регресса человека (P21). Лестница добычи (дешёвое первым, FR-50): 1) требования и тикет (AC «было/стало», вложения, связанный баг); 2) код базовой ревизии (сегодняшнее `before_change`); 3) стенд, на котором ещё крутится версия без изменения — тот же dev-стенд ДО деплоя (снять «до», потом попросить владельца развернуть — порядок: идентичность стенда t-300 говорит, что на нём база → блок «до» идёт раньше S5, по кейсам плана с меткой «нужен бейзлайн») или другая среда (stage/prod — только чтение и только с разрешения); 4) собственная вторая сборка базовой ревизии (дорого, только по слову); 5) история версий внутри продукта (15045 хранит версии workflow); 6) вопрос человеку: «где увидеть „до“: стенд/ревизия, скрин, или сравните сами» (сегодняшний текст S8). Нужны: метка кейса в плане S3 «comparative: нужен бейзлайн» (стратег), шаг в S0/S3 «бейзлайн доступен? какой ступенью?», порядок стадий (блок «до» до переключения стенда), запись в отчёте «до/после» парой с источником каждой стороны.

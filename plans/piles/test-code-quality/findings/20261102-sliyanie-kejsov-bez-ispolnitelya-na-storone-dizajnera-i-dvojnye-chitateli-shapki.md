## Что наблюдалось

TQ1-27 (`release-next/1`) велит критику кейсов S4 писать для пар с общим требованием строку `merge_candidates[]`; по решению Lead слияние едет в S5 как `approve_with_concerns` с `parametrise into one test: <ids>` (маршрут без `Archived`). Привязанный до конца ход «дизайнер сам складывает кейсы» не построен:

- Состояние `status: Archived` читает ОДИН потребитель — `case_stamp.py:535` (пропуск штампа). Всё остальное перечисляет кейсы через `contract.case_files` (`contract.py:3024`, без фильтра по статусу) → `contract.case_index` (`:3303-3338`, поля статуса нет). Проба на копии фикстуры с TC-003 `Archived`: `index has TC-003: True TS-3 status Archived`, 13 записей.
- Следствия: `check_delivery._completeness` (`:637-649`): TS-3 `automate`, TC-003 назван, но не в `tests[]` и не в `unresolved[]` → причина `factory_record`, доставка `no`; при УДАЛЁННОМ кейсе (`:644`) — «plan TS-3 is `automate` but no case names it as its plan row», и на гейте A `controller.py:2625` «no case names this plan row…». Читатели `case_index` (traceability, `coverage_contract:454`, ledger, `delivery_summary`, `s5_precheck`) видят архивный кейс.
- Две лишние читалки заголовка таблицы (критик t-756): m-5 — `_has_note_column` перечитывает шапку кругового опроса, которую уже разрешает `parse_rollcall` (`note_at`, `critic_rollcall.py:115`); m-6 — `parse_merge_candidates` — третий читатель «колонка по имени» с сообщением о пропавшей колонке (рядом `parse_rollcall`, `_table_rows`); t-736 m-5 принял `md_table`, общий помощник — очередь класса.

## Класс

Решение без исполнителя и состояние без читателей (FR-9, FR-40; AR-25): записанное «слить» нельзя исполнить, потому что исполнитель не знает правила, а доставка засчитывает слитый кейс как непокрытый; и три читателя одной шапки (AR-13).

## Что именно менять

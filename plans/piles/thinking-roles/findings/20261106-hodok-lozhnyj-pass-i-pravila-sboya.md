## Что наблюдалось

- Карточки 3 и 23 — ложный pass. Ходок ввёл «1» и «2» двумя вызовами `type`; каждый вызов сам ставит фокус в поле, поэтому «2» попала в поле, которое приложение уже покинуло. Человек так ввести не может; простой агент баг «12 нельзя ввести» увидел. Рекордер при этом сам написал `no focus already at the reading after character 1`.
- Карточки 9, 15, 16 остались без вердикта: рекордер отказал закрывающему снимку из-за правила подмены запроса, которое уже снято `restore_request` и ни разу не совпало. Память о таком правиле перешла из кейса в кейс внутри дорожки (карточка 16 правил не ставила; карточка 9 получила отказы за правила карточек 7 и 8).
- Карточки 5 и 6: шаблон `*/api/...` (одна звёздочка) не совпал ни с одним запросом, рекордер записал `requests failed: 0` только при снятии правила, а ходок сделал вывод «страница этот запрос не читает».
- Карточка 14 невыполнима: в словаре шагов нет шага, который заканчивает сессию пользователя (удаляет cookie).

## Что именно менять

### TR1-1. `type` не возвращает фокус, который приложение забрало

- Где: `scripts/manual_capture.py`, `_keyboard_step` (строки 1791–1804: `element.focus()` на каждый вызов), `type_chars` (1806–1829); текст-подсказка шага `type` в `references/manual-capture-steps.json`; хартия обхода `references/walk-charter.md`.
- Поведение: первый `type` по полю ставит фокус (человек кликает в поле). Следующий подряд `type` по ТОМУ ЖЕ полю без действия между ними — продолжение набора (пассивные шаги `read`, `look`, `wait` и подобные — список данных `keeps_run` — набор не прерывают: человек, который набрал «1», посмотрел и набирает «2», заново не кликает; действие или `click` прерывает; решение координатора по критику t-2055 B1): фокус не ставится заново; если поле фокус потеряло, клавиши уходят туда, где фокус сейчас, шаг завершается исходом «не ok» с фактом `focus lost before the call: keys went to <что в фокусе>` и строкой `surprise:`. Явный новый клик человека — отдельный шаг `click`.
- Хартия (опыт, не процедура): строка, которую человек набирает подряд, набирается одним вызовом; наблюдение рекордера о потере фокуса — это находка, а не шум, и вердикт pass поверх него не ставится.
- Тесты: два вызова `type 1`, `type 2` на странице, которая снимает фокус после первого символа, → значение поля «1», второй шаг не ok, есть `surprise:`; один вызов `type 12` там же → запись «focus lost after character 1» (как сейчас); два вызова на странице, которая фокус держит, → «12», ok; `type` после `click` по тому же полю → фокус есть, ok.
- Не делать: возврат фокуса «для надёжности»; новый флаг шага.

### TR1-2. Снятое правило сбоя забыто; правило без совпадений видно сразу

- Где: `scripts/manual_capture.py` — `restore_request` (1880–1887: ставит `active = False`, запись остаётся), ветка `capture post_action` в `_run_step` (4200–4208: `idle` не смотрит на `active`), `_fail_problem` (929–937), `_store_failure` (3887); `scripts/walk_session.py` — начало нового пункта (929–951: новый `Attempt`, тот же backend).
- Поведение: (1) `restore_request` записывает итог правила (`requests failed: N`) и убирает его из набора, который проверяет закрывающий снимок; отказ `failure_unmet` касается только правил, активных в момент снимка. (2) На границе пунктов сессии ходока все правила предыдущего пункта сняты и забыты (их итог записан в улики того пункта). (3) Правило, снятое с нулём совпадений, даёт строку `surprise: fail_request <glob> matched no request` в ответе шага `restore_request` и первого же шага `look`/`read` после действия, на котором ожидался сбой. (4) Шаблон без `**` и без схемы, у которого путь начинается с одной `*`, получает в ответе `fail_request` строку-подсказку «`*` не пересекает `/`; для любого хоста пишут `**/api/x`» (подсказка, не отказ).
- Тесты: правило без совпадений → `restore_request` → `capture post_action` проходит; активное правило без совпадений → отказ как сейчас; два пункта одной сессии, правило первого не снято → второй пункт его не видит, в уликах первого есть итог; `*/api/cart` → подсказка в ответе шага; `**/api/cart` → без подсказки.

### TR1-3. Шаг «закончить сессию пользователя»

- Где: словарь шагов — данные `references/manual-capture-steps.json` (`steps`, строки 7–23), разбор `parse_steps` (`manual_capture.py` 1001–1095), метод backend рядом с `restore_request`; карточка шагов ходока в `references/role-commands.json`.
- Поведение: шаг `end-session` удаляет cookie контекста браузера текущего актора (страница остаётся открытой, как у человека, у которого сессия истекла); ответ шага называет, сколько cookie удалено. Шаг доступен в `ui` и в сессии ходока; на устройстве (`app_steps`) его нет — пустой исход записан в данных.
- Тесты: после входа `end-session` → следующий запрос страницы идёт без cookie сессии; шаг без входа → ok, «0 cookies»; шаг в списке устройства → отказ словаря с названием доступных шагов.

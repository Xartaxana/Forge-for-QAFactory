Стенд сброшен 28.10 (архив `D:/ws1/archive\testproject1-dev-010-run-12586-20261028`), конфиг проекта — тот же, что до прошлого прогона
(`config.json.worktree` архива и текущий совпадают по `environments[].credentials_by_role`). Всё, что прошлый прогон узнал от человека о
стенде, жило в стори и пропало с ней. Носители ниже — стенд, `test-harness/qa-factory/`.

## W-1. Учётки: фабрика спросила про админа, хотя основной пользователь записан

`config.json`: `environments[0].credentials_by_role = {"default user": "AUTH_USERNAME / AUTH_PASSWORD …"}` — одна роль без указания, что
это администратор; `.env` держит ещё `QA_SECOND_USER_EMAIL` / `QA_SECOND_USER_PASSWORD`, которых конфиг не называет. Кейс TC-008
требует админа и второго пользователя → вопрос человеку. В прошлом прогоне то же: ранние версии кейсов — `check: none` «a person says
whether a second account exists», после ответа — `check: {env: QA_SECOND_USER_EMAIL}` (архив, TC-014). Класс: ответ человека о стенде
(роли учёток) не записывается в конфиг проекта, а онбординг не сопоставляет найденные в `.env` учётки с ролями (FR-7, AR-3, AR-24).
Направление: ответ о ролях учёток пишется в `credentials_by_role` проекта (с подтверждением человека, без значений); онбординг предлагает
роли для найденных пар `*_EMAIL/*_USERNAME` + `*_PASSWORD`; роль «администратор» — именованная, а не вывод из «default user».

## W-2. Адрес UI не найден, хотя `FRONTEND_URL` в `.env`

`testproject1_test_harness/.env` содержит `FRONTEND_URL`; в `config.json` нет ни `environments[0].frontend.url`, ни `environment.frontend.url_key`
→ `env_probe.frontend_of` возвращает пусто («Для стенда не настроен frontend URL»). `_frontend_hint` знает такие ключи, но только
подсказывает. Тот же класс, что W-1: факт стенда, выясненный в прошлой стори, не дожил до проекта; онбординг не связал ключ.
Направление: онбординг (и ответ человека на гейте) пишет `environment.frontend.url_key`; ключ ровно один с http-адресом и именем
`FRONTEND*`/`UI*` — предложение по умолчанию, человек подтверждает. Сосед — HF5-1…HF5-6 пачки 5 («один читатель адреса фронтенда»).

## W-3. Jira: ключи Server есть, проверка требует ключей Cloud

`.env`: `JIRA_URL`, `JIRA_TOKEN`, `JIRA_PROJECT_KEY` (Jira Server — на них прошлый прогон строил интеграцию с тестовым проектом; ими
пользуются тесты харнесса). Онбординг сложил в одну группу `environment.integrations[6] jira-integration` семь ключей — и Cloud
(`JIRA_CLOUD_*`), и Server (`JIRA_*`). `gate_preflight.py` (`s5_integrations`, `_integration_question`) считает группу неполной при любом
отсутствующем ключе → «нет `JIRA_CLOUD_*`», вопрос TC-009 и ещё 13 непривязанных вопросов по группам (Confluence — вероятно, тот же
случай). Направление: группа интеграции держит альтернативные наборы (`any_of`), проверка удовлетворена, если задан любой набор целиком;
онбординг раскладывает варианты `*_CLOUD_*` / без суффикса в отдельные наборы; непривязанная к кейсам группа — строка отчёта, не вопрос.

## W-4. «MR API не проверен» — а скаут уже прочитал пять MR по API

`state/readiness.json`: `vcs_api: unknown` («Run readiness.py --probe-vcs …»). В той же стори `work/sources/mr/*.json` — пять MR со
`status: read`, `api_authenticated: true`. Успешное чтение — доказательство доступа, но его никто не засчитывает (FR-18 наоборот: факт
есть, квитанции нет). Направление: удачный `api_authenticated` fetch MR пишет квитанцию `vcs_api: ok` (один писатель, тот же формат,
что `--probe-vcs`); предупреждение показывается только если MR не читались и проба не делалась.

## W-5. «Контекст host hooks не проверен»

`readiness.json`: `host_hooks: unknown` — «role-context delivery not yet verified. Dispatch the read-only qa_factory_context_probe
diagnostic now…, then run host_probe.py --check». Живые allow/deny проверены доктором, а проверка доставки контекста ролям ждёт ручного
диспатча, который никто не делает; при этом роли этой стори уже получили контекст (их квитанции есть). Направление: доставка
контекста засчитывается по первому реальному диспатчу роли со своей квитанцией (или проба делается кодом в доктора/S0), без
поручения человеку или дирижёру (P3, FR-48).

## W-6. «Баги пишутся в markdown и в трекер не уходят»

`readiness.json`: `tracker_write: not_configured` — «bugs stay in the repository by the project's own choice (external_writes.bugs =
markdown)». Выбор проекта показан как предупреждение на каждом гейте (FR-3, FR-4: решённое не подаётся как проблема). Чей это выбор на
стенде — проверить (онбординг по умолчанию или слово человека); если человек хочет баги в трекере — онбординг даёт этот выбор и его
маршрут. Решение владельца 29.10.2026: «оставить в маркдаун и это был мой выбор при онбординге» — выбор человека, записанный при онбординге, на гейтах не показывается предупреждением.

## W-7. `s5_reporter-1`: «не нашла существующий тест, на котором доказать, что профиль `api` пишет читаемый отчёт»

`gate_preflight.check_s5_reporter` берёт ОДИН существующий тест профиля (кэш `check_s5_toolchain`, `gate_preflight.py:1767`), гоняет его
и читает отчёт. В харнессе сотни API-тестов, но выбор вернул пусто → вопрос человеку. Прошлый прогон этот шаг проходил. Направление:
найти, почему выбор пуст на 0.10.5 (сбор тестов профиля `api`, фильтр маркеров/путей), выбор — любой собранный тест профиля без
внешних зависимостей; пусто — только когда сбор действительно пуст, и тогда в тексте — что собрано и чем отфильтровано.

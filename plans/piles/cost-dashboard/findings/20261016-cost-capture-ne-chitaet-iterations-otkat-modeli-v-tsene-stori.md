## Что

F6-23 (t-882, слито `485904ce`) установил правило для инструментов разработки: запрос, у которого строка транскрипта несёт
`usage.iterations` с двумя и более записями (откат модели — Fable → Opus), ценится ПО ЗАПИСЯМ — каждая часть по своей модели,
запрос = сумма (запись провайдера — оракул, P20); иначе — MAX по модели по снимкам. В реальных транскриптах 6 строк из 206 847
несут ≥ 2 записей — два запроса, цена одного 0.0588 → 0.21261, другого (все строки помечены opus) 0.1251 → 0.4277.

`cost_capture.py:950` (цена стори, P18/FR-24) читает ту же `usage` по одной модели строки — тот же недосчёт в цене задачи для
проекта. Что сделать: тот же носитель и то же правило (одна функция чтения частей запроса; `tools/transcripts.request_parts` —
образец, но пакет не импортирует `tools/` — своя копия правила в пакете с тестом на те же два запроса-фикстуры); FR-25: пока
правила два, отчёт называет авторитетный; контрольные значения руками в тесте.

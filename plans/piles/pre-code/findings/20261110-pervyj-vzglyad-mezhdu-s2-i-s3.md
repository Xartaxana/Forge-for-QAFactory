## Решения владельца (10.11.2026)

1. Место прохода — между S2 и S3 (вариант A): реестр требований уже есть, план ещё не оплачен.
2. Один проход — четыре читателя: стратег (что красное и что недостижимо), автор кейсов (реальный путь), автоматор (локаторы, данные,
   вход), S6 (ширину не повторяет).
3. Фича мертва → вопрос человеку (закрытый, по `human-questions.md`), два исхода:
   - **«остановить»** — стори паркуется; при следующем запуске фабрики на этой же стори она смотрит изменения в КОДЕ, а не только в
     требованиях (дорога прихода кода, как у ждущей стори t-2181 §3: `--branch/--mr/--commit`);
   - **«продолжаем»** — тесты пишутся на ожидаемое поведение и остаются красными, пока реализацию не починят.
4. **Плохо написанный код моками не заменяется** (уточнение владельца 10.11.2026, вторым ответом): «тут не тот случай, когда код к нам
   может и не прийти; тут реальный баг — мы ожидаем одно, а по факту другое». На настоящей стороне подмен нет: ни `side_substitute`, ни
   `assumed_contract`; правило заземления t-2181 §2.2 («строка допущения только когда сторона не `real`») НЕ расширяется. Недостижимое
   требование — наблюдение «ожидали / по факту» с уликой, которое идёт аналитику как кандидат в баг (FR-22, FR-34), и красный тест,
   где его можно написать. Тест, который проходит на подмене, скрыл бы, что цель недостижима, — это и запрещено.
5. **Порог вопроса — 30 %** (владелец, тем же ответом): вопрос «продолжать или остановить» задаётся, когда достижимо меньше 30 %
   требований реестра, а не только когда недостижимы все. Решает человек; после переделки могут измениться и достижимые сегодня.

## Что именно менять

### FL-0. Спека первого взгляда (designer, затем критик на план — меняет схему стадий)

Бриф замысла для дизайнера:

- **Проход.** Свежий агент, короткий и широкий: один путь на требование реестра, без техник тест-дизайна (глубина остаётся S6). Каждый
  шаг — через рекордер ручного прохода (спека `docs/tasks/specs/t-1957-fast-manual-walker.md`; P26): улики пишет код, строки `surprise:`.
  Для тикета без интерфейса — те же короткие вызовы API. Нет стенда или доступа — строка-пробел, без вопроса (P5, D-0043).
- **Выход — один YAML в передаче S2→S3** (P4, FR-49, AR-21), две части: (а) по каждому требованию `confirms | contradicts | missing |
  unreachable` со ссылкой на улику; (б) карта пути: адреса, шаги до экрана, локаторы, нужные данные и роли, требования к стенду.
  Пустой исход объявлен (AR-23).
- **Не оракул** (P20, FR-58): проход записывает наблюдения; ожидания по-прежнему из реестра. `contradicts` — наблюдение аналитику
  («баг или нет») и «было / стало» человеку, не вердикт.
- **Суждение — роли** (P27, AR-29): «фича мертва» говорит роль с уликами; код только несёт её вывод к дирижёру (AR-17), дирижёр задаёт
  вопрос с ценой по вариантам (P22).
- **Исход «остановить».** Переиспользовать парковку и дорогу прихода t-2181 §3 (узлы PC-6, PC-7), а не новое состояние рядом;
  у состояния есть выход (FR-40, AR-25).
- **Исход «продолжаем».** Красный тест на настоящей стороне — баг (FR-34), в отличие от стори без кода, где тест только собирается.
  Подмен нет (решение 4). Тест обязан падать там, где цель недостижима, и по красной строке должно быть видно, какое требование.
- **Порог** (решение 5). Долю считает код по статусам YAML прохода (данные, AR-29); число 30 — ключ конфига проекта со значением по
  умолчанию (AR-3). Статус каждого требования ставит роль.
- **Цена** (FR-51, P11): стадия оправдана, если S4–S6 дешевеют больше, чем она стоит; мерить `experiments/measurers/stage_compare.py`
  на одной стори с проходом и без.

Узлы реализации открывает спека; до неё в пачке один узел FL-0.

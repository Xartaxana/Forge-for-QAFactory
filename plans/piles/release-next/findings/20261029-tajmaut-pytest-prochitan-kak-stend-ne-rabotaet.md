# Тест убит таймаутом pytest проекта, а фабрика сказала человеку «индексация на стенде не завершается»

id: — | кучка: `release-next` | от: прогон TP1-14857 на 0.10.5, `testproject1-dev-010`, 29.10.2026 ~21:34–21:48 UTC, S5 окно 1; разбор Lead по вопросу владельца «там проблема с индексацией стенда»; слово владельца 29.10.2026 — в 0.10.7 | приоритет: П1 (0.10.7, слово владельца) | кандидат наверх: нет

## Что наблюдалось

- TC-001 (`test_reindex_last_indexed_is_trigger_time_code_datasource`) дважды: автоматор вернул `blocked_by_env` — «code datasource never reached
  Completed (120s, then 600s); run broke, no stamp assertion ran». Дирижёр понёс человеку: «That points at the stand's code-indexing path …
  You check the stand», с вариантом «идти дальше с пробелом стенда».
- Факт: лог прогона (`evidence/runs/09e2c485…/repair_verify-…-20261029-223441.log`) — `timeout: 300.0s` (pytest-timeout проекта,
  `pyproject.toml:110` `timeout = 300`), строка 17 `+++ Timeout +++` внутри второго `wait_for_indexing` (после переиндексации); запись
  прогона: `exit_code 1`, `"no_junitxml": "nothing to parse — read the raw log"`, длительность 461 с.
- Стенд источник проиндексировал: `testproject1.index_info` — `completed=t`, `error=f`, `current_state 167 / complete_state 167`, обновлён
  21:39:05 UTC; в логах приложения у источника `autotest-amq_…` дважды `IndexDatasource. Finished` (21:37:20, 21:39:05). Репозиторий
  человека (167 файлов) индексируется 1,5–2 мин; тест индексирует дважды и ждёт дважды — дольше 300 с.
- Тест сам себе поставил ожидания 600 + 180 + 180 с при таймауте проекта 300 с на тест; у проекта есть прецедент длинных тестов —
  `@pytest.mark.timeout(1500)` в `tests/budgets/*`.

## Класс

Вердикт «среда» без свидетельства среды (FR-18, FR-41, FR-58: причина выведена из того, что тест не дождался, а не из состояния стенда;
AR-28 — неизвестное стало фактом о стенде). Три звена: (а) `run_suite` не узнаёт убийство теста pytest-timeout (нет junit — «read the raw
log»), хотя в словаре исходов есть `timeout` (`run_suite.py:1056-1060`); (б) автоматор и дирижёр ставят `blocked_by_env` без пробы
состояния стенда; (в) таймаут проекта на тест не доходит до автоматора до работы (FR-38, AR-10) — тест написан длиннее, чем ему разрешено.

## Что нужно

1. `run_suite`: маркер pytest-timeout в логе (`+++ Timeout +++` / `Timeout` в `--timeout` строке шапки) → исход `timeout` с именем теста и
   лимитом проекта, не «read the raw log»; строка для автоматора: «тест убит таймаутом проекта N с — не среда».
2. `blocked_by_env` принимается только со свидетельством среды (проба состояния ресурса, ошибка стенда в ответе); иначе — дефект теста
   (`TEST_BUG`), автоматор чинит; дирижёр не несёт человеку «проверьте стенд» без такого свидетельства.
3. Бриф автоматора S5 несёт таймаут проекта на тест (из `pyproject.toml`/`pytest.ini`/`setup.cfg`, читатель конфигурации тестов) и
   прецедент маркера, если он есть в проекте.

Решение владельца нужно: нет (слово владельца дано: в 0.10.7).

# `qa-explore` на MyBooks обязан сам найти три бага корзины, которые пропустил обычный прогон CART-1

id: — | кучка: `release-next` | от: прогон CART-1 (MyBooks), 31.10.2026 | приоритет: П1 | кандидат наверх: да

Слово владельца (владелец, 31.10.2026): «Проблемы фабрики складывай по кучкам. Плюс подумай, что надо сделать, чтобы фабрика сама нашла все
эти 3 бага. Так же есть кучка эксплораторного тестинга, туда тоже добавь, что надо, чтобы при запуске этого скилла фабрика нашла как
минимум эти 3 бага».

## Что наблюдалось

Обычный прогон CART-1 (пайплайн S0–S8) не нашёл ни одного бага продукта (свод `experiments/mybooks/cart-1-run-problems.md`, раздел 1: «0 багов»).
Три бага Lead проверил на стенде `http://localhost:3000`, MyBooks `a25b080`, 31.10.2026. Ниже шаги, по которым их воспроизводит слабая модель,
и оракул, по которому видно, что это баг. Скилл `qa-explore` (узлы XT1-1…XT1-8, XT2-2) принимается по ним.

### Б-1. В поле количества на странице корзины нельзя набрать «12»

- Предусловие: в корзине есть строка с книгой (например «1984», количество 2); страница `/cart`.
- Шаги: выделить поле `cart-item-quantity-{id}` целиком, нажать клавишу «1», затем «2» — по символу, как с клавиатуры (не `fill`).
- Что на стенде: после «1» уходит `PUT /api/cart/{id}` с `{"quantity":1}`, страница перерисовывается скелетоном, поле размонтируется, фокус
  теряется, «2» никуда не попадает; в корзине итог 1 вместо 12. Код: `MyBooks/src/components/pages/CartPage.tsx:69` (после успеха `loadCart()`),
  `:29` (`setLoading(true)`), `:106-113` (скелетон вместо страницы), `:183` (`onChange` шлёт PUT на каждую цифру).
- Оракул: введённое значение сохраняется целиком, фокус не теряется (набор многозначного числа возможен).
- Родственный Б-3 (спорно): очистить поле — уходит `PUT {"quantity":null}` → 400, тост «Valid quantity is required» (`:59,65,183`, `parseInt('')`).
  Перехват того же возмущения «ввод с клавиатуры: пусто»; вердикт — вопрос человеку, не обязательный для приёмки.

### Б-2. `GET /api/books/{id}` → 500 валит всю страницу корзины

- Предусловие: в корзине есть строка; открыта `/cart`.
- Шаги: подменить в браузере ответ `GET /api/books/{id}` на 500 (`page.route('**/api/books/*', route => route.fulfill({status: 500, ...}))`),
  перезагрузить `/cart`.
- Что на стенде: вся страница — «Something went wrong. Please try again», корзины нет. Код: `CartPage.tsx:30-38` — `fetch` книги и `.json()` без
  проверки `response.ok`; разведка `docs/tasks/specs/reports/t-1634-mybooks-cart-bug-hypotheses.md`, H2 c.
- Оракул: страница жива (остальные строки корзины видны), человек узнал об ошибке по-человечески, данные не потеряны молча.

### Б-4. `POST /api/cart/merge` → 500 при входе: гостевая корзина пропадает молча

- Предусловие: аккаунт существует; гость с книгой в корзине (например «Dune» ×2, cookie `bookstore_session_id` от первого `POST /api/cart`).
- Шаги: подменить ответ `POST /api/cart/merge` на 500, войти на `/login` под аккаунтом.
- Что на стенде: вход проходит, тост «Successfully logged in!», корзина после входа пуста, гостевые книги пропали, сообщений нет. Код:
  `MyBooks/src/components/pages/LoginPage.tsx:36-39` — `catch (mergeError) { console.error(...) }`.
- Оракул: человек узнаёт, что гостевая корзина не перенесена (или перенос повторён); молчаливая потеря данных — дефект. Формально вопрос к
  требованиям (эталон Q3), но правило владельца Q1 гейта A «код не даёт сделать задуманное — баг» его решает.

## Класс

Исследовательский прогон по функции не находит ошибки зависимости и ввода, потому что (а) карта функции не знает запросов страницы и потока,
(б) нет возмущений, которые эти ошибки вызывают, (в) руки агента умеют проверять заранее придуманный кейс, но не «сломать каждый запрос по
очереди» и не «набирать с клавиатуры». Класс — «сбой зависимости на пути пользователя и ввод с клавиатуры не исследуются» на любом проекте
с веб-интерфейсом; рамка мобильных/десктоп-проектов — `EP1-41`. Не правило MyBooks.

## Что именно менять

Узел XT2-2 (пачка `exploratory/2`). Направление выбрано (Lead пачки, до слова владельца); дизайнер доводит до файлов и тестов.

1. Карта функции знает запросы (F-а). `references/feature-map-form.json` и проверка карты (XT1-6) получают в записи точки входа поле
   `requests[]` — `{method, url_template, source: code|network}`: сеть собирается пробой страницы в браузере (запросы при загрузке и при
   действии потока), код — из ханков вызовов `fetch`/клиента (XT1-5, `git grep`). Для корзины карта обязана содержать `GET /api/cart`,
   `GET /api/books/{id}`, `PUT /api/cart/{id}`, `POST /api/cart/merge` (вход). Пустой `requests[]` у точки входа с UI-действием — не «нет
   запросов», а «не измерено: <причина>» (FR-41). Тест: карта корзины на фикстуре HAR/ответов содержит четыре запроса; пустая — строка «не измерено».
2. Возмущение «отказ каждого запроса потока по очереди» (F-б). Закрытый список возмущений — данные (`references/perturbations.json`, зерно:
   10 осей предложения `plans/exploratory-charters-proposal.md` + новые, FR-13, AR-1); новая ось `request_failure`: для каждого запроса из
   `requests[]` потока по очереди — ответ 500, затем таймаут (ручная проверка `ui`, шаг `fail_request`: `page.route` по шаблону URL; шаг
   строит кучка `execution-probes`, Н-5 свода CART-1). Оракул оси (данные оси): «страница жива, человек узнал об ошибке, данные не
   потеряны молча». Чартер берёт клетку «запрос × отказ», пока не исчерпаны все запросы потока; нарушенный оракул — находка исследования с
   шагами и скрином (`scripts/exploratory_findings.py`). Тест: на фикстуре потока из трёх запросов чартеры порождены на каждый, порядок
   стабилен, оракул оси доходит до чартера.
3. Возмущение «ввод с клавиатуры в каждое поле» (F-в). Ось `keyboard_input` в том же файле: для каждого поля ввода потока — многозначное число
   (набор по символу, не `fill`), пусто, вставка, значение за пределом (0, отрицательное, 1000 при потолке 999). Шаг ручной проверки `type`
   с записью промежуточного значения поля и фокуса после каждого символа (Н-4 свода, `execution-probes`). Оракул: «введённое значение
   сохраняется целиком, фокус не теряется, ошибка понятна». Тест: на фикстуре страницы с перерисовкой после первой цифры шаг `type` фиксирует
   потерю фокуса; та же страница без перерисовки — нет находки (отрицательный контроль).
4. Приёмка скилла — живой прогон (F-г). `/qa-factory:qa-explore "добавление в корзину"` на MyBooks `a25b080` (`docs/RUNBOOK.md` §11) находит
   как минимум Б-1, Б-2 и Б-4 по шагам и оракулам выше: каждый с шагами воспроизведения и скрином в отчёте исследования. Это живое доказательство
   пачки (FR-33): без трёх найденных багов узел не «принят». Прогон не оставляет следов в проекте (P8: баги — в отчёт и чат, не в Jira); стенд —
   копия, чекауты стенда принадлежат владельцу. Дополнительно (не условие приёмки): Б-3 как вопрос человеку.

Зависимости: XT1-5 и XT1-6 (поиск кода и форма карты), XT1-8 (скилл), чартеры и исследование приложения (E4–E5 — узлы пачки 2, которые дизайнер
добавит), шаги `type` и `fail_request` (Н-4, Н-5 свода; кучка `execution-probes`, узлы по этой находке ещё не названы — не проверено). Связь по
классу: `grounding`, Н-3 (`findings/20261031-catch-i-fetch-bez-ok-ne-stanovyatsya-trebovaniem.md`) — тот же класс, со стороны кода.

Тесты узла: новый `scripts/tests/test_exploration_perturbations.py` (пункты 1–3, края: нет запросов в карте, поток из одного запроса, поле без
фокуса, таймаут вместо 500); п. 4 — живой прогон, свидетель — отчёт исследования с тремя находками. Критик на план: да (новый формат данных и
скилл); свидетель билдера — точечный, живой прогон — интегратор/Lead.

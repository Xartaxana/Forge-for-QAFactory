## Почему так (по коду, разведка t-1667, факты проверены Lead)

1. **`coverage_contract_revision` пишет роль, хотя значение — константа.** `scripts/coverage_contract.py:9`
   `COVERAGE_CONTRACT_REVISION = "coverage-observation-v1"`; проверка — `planning_contract.coverage_revision_errors` (`:198-215`), её текст не
   называет значения; `references/field-producers.json:22-25` объявляет производителем код (`controller.py --operation prepare`), но кода,
   ставящего отметку в строки плана, нет.
2. **Проверка веток вопросов идёт ПОСЛЕ приёмки стадии.** `stage_done.py:1067-1068` — `s3_branch_line` под `stage == "S3" and status == "done"`,
   только отчёт; комментарий: «a second refusal would duplicate the S4-rehearsal stop». Итог — не отказ в контексте стратега, а новый диспатч
   (R-2). У стратега нет двери «нужен новый вопрос человеку»: регистр вопросов не даёт роли S3 завести вопрос (`question_register.py` пишет
   только ответы: `record`, `record_answers`, `record_case`), поэтому роль выдумывает `Q101`.
3. **Форма сдачи rework-диспатча рождается с пустым `scope`.** `story_step._handoff_form` → `handoff_init.py --scope` кладёт scope только в
   `header.window` (`handoff_init.py:114-122`); `carry_from_parent` переносит только скаляры (`:138`); строки плана rework едут отдельно
   (`controller.py:3404-3407`, `request["plan_rows"]`); `handoff.REQUIRED_LISTS = ("scope",)` → отказ «no rows» (R-3).
4. **Переуказание вопроса после S4 делает роль новым кругом.** Находка `missing_branch` с owner `strategist` (`planning_contract.py:1724`) →
   `controller.ANSWER_REWORK_OWNERS` → rework S3 `--rows` (`story_run.py:3508-3529`). Код ни переуказать ссылку, ни перенести ветки не умеет
   (`stage_done.py:449`, `gate_preflight.py:1615`: «writes nothing»).
5. **Нет одной самопроверки до сдачи**, а тексты роли противоречат друг другу: `agents/qa-test-strategist.md:156-158` велит перезапустить
   контракт плана, `skills/qa-story/phases/s3.md:137` — «Do not re-run the plan contract by hand».

## Класс

«Роль может сдать работу, в которой незаполнено то, что код потом отвергнет; отвергает не тот шаг (после приёмки, на следующей стадии),
и каждое такое „не заполнено“ стоит целого круга диспатча». Значения, которые знает код, заполняет код (P1, FR-47, AR-7, AR-10); всё, что
проверяется после, проверяется ДО сдачи, в контексте той же роли (FR-38, AR-10); у роли есть дверь на то, чего она не может (FR-2, FR-57).
Не правило MyBooks.

## Что именно менять

Направление выбрано (Lead, 02.11.2026, по слову владельца); дизайнер доводит до функций и тестов, критик на план — да (меняется момент
отказа и производитель поля).

1. **Отметку ставит код.** Путь записи плана (`artifact_packet.py --operation patch` и хук записи плана — тот, что уже гоняет контракт плана)
   ставит `coverage_contract_revision = coverage_contract.COVERAGE_CONTRACT_REVISION` в каждую строку, где поля нет; роль это поле не пишет,
   из `agents/qa-test-strategist.md:153-158`, `s3.md:153-156` и формы `handoffs/s3-strategist-to-designer.yaml:69` требование к роли убирается.
   Строка с ДРУГИМ значением — по-прежнему отказ (это смысл: строка планировалась по старому контракту). Тест: план без поля после записи
   несёт константу; строка с чужим значением — отказ с текстом, называющим ожидаемое значение.
2. **Проверка веток вопросов — в гейте выхода S3, не после приёмки.** Виды `variant_errors` (`unresolved_ref`, `bad_branch`,
   `settled_question`, `missing_refs`), которые сейчас доходят только пакетом `s3-remarks` после `accept`, проверяются детектором выхода S3
   (`planning_contract.detector_main` или `stages.json` → `detectors` стратега) и отказывают в контексте той же роли; `s3_branch_line` в
   `stage_done.py` остаётся только как отчёт, если что-то всё же просочилось (детектор утечки, см. ниже). Дубль одной находки (R-2 печатал каждую
   дважды) — одна строка на (строку плана, id). Тест: план с `Q101` при регистре Q1–Q6 — гейт выхода отказывает, `accept` не происходит.
3. **Дверь «нужен новый вопрос человеку» у стратега.** Строка плана, которой нужен ответ, которого нет в регистре, пишет `question: new` с текстом
   вопроса (поле формы плана); при записи плана код заводит вопрос в регистр той же функцией, которой выход S4 завёл Q7–Q9 (один писатель
   регистра, AR-14/AR-15 — найти её в `story_run.py`/`question_register.py`), и проставляет выданный id в строку. Выдуманный id вида `Q101` —
   отказ с текстом «напиши `question: new` и текст вопроса» (FR-2). Тест: строка с `question: new` после записи несёт `Q7`, регистр — вопрос Q7.
4. **Форма сдачи rework-диспатча приходит с заполненными id.** `story_step._handoff_form` / `handoff_init.py` для rework кладёт в `scope` по строке
   на каждый id из `request["plan_rows"]` (для S4 — из case scope) с пустыми `state`/`reason`, которые роль заполняет; `REQUIRED_LISTS` и проверка
   полноты остаются. Тест: rework S3 с `plan_rows=[TS-2, TS-5]` — форма несёт `scope[0].id: TS-2`, `scope[1].id: TS-5`.
5. **Переуказание вопроса после S4 — кодом.** Когда выход S4 заводит новый вопрос Qn вместо общего Qm на строках плана: если буквы чтения Qn и Qm
   совпадают, код переставляет ссылку строки и копирует её ветку `if_answered[Qm]` в `if_answered[Qn]` (запись — тем же путём записи плана);
   rework S3 порождается только когда буквы различаются (ветки — смысловое решение стратега). Тест: Qm и Qn с буквами a/b — rework нет, ветка
   скопирована; Qn с a/b/c — rework S3 ровно на эти строки.
6. **Одна самопроверка до сдачи.** Команда (`planning_contract.py --task <id> --self-check` или `exit_gate.py --stage S3 --dry-run` — выбрать ту, что
   уже собирает детекторы стадии) гоняет ВСЁ, что гейт выхода S3 проверит: детекторы стадии из `stages.json`, проверку п. 2 и `handoff_check.py`
   формы; роль запускает её последним шагом (`agents/qa-test-strategist.md`, один текст вместо двух противоречащих — `s3.md:137` исправить).
   Тест: самопроверка и гейт выхода на одном плане дают одинаковый список находок.

Соседи (правило 9, по классу): S4 дизайнер кейсов (event 34 п. 2 — буквы a/b на вопросе «было/стало») и любая rework-форма с обязательным списком
(`handoff.REQUIRED_LISTS`, п. 4 закрывает механизм для всех ролей) — дизайнер проходит роли S2–S7 по вопросу «что из отказов их гейта значение
кода, а что — проверка после приёмки» и называет остаток строками в этом узле или очередью в кучки.

Детектор: в ретро прогона — счёт rework-диспатчей роли по классу причины (формальная / смысловая); формальный круг > 0 — находка.

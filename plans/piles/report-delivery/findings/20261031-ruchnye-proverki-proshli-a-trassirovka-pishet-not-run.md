# Ручные проверки прошли, а таблица трассировки пишет «not run» и вердикт «человек проверяет 0 кейсов»

id: — | кучка: `report-delivery` | от: прогон CART-1 (MyBooks), 31.10.2026 (свод `experiments/mybooks/cart-1-run-problems.md` п. 6.1) | приоритет: П1 | кандидат наверх: нет

## Что наблюдалось

В прогоне CART-1 кейсы TC_011 и TC_012 (`manual-agent`, поверхность `ui`) агент прошёл руками: `S6-qa-runner-2`, ledger считает их
`passed_green`, сводка пишет «Manual cases planned 2 / executed 2», блок отчёта — «Checked by hand — 2 of 2» (`test-report.md:7,28-32`;
`work/ledger.md` строки TS-11, TS-12; `work/delivery-summary.md`). В той же `test-report.md` таблица трассировки пишет по этим кейсам
`not run` с причинами из ПЛАНА («server rule covered by TS-2», «degraded impact does not earn e2e code»; строки 167, 169, 182), а вердикт
говорит «A person must check 0 cases» и «0 green tests count as proven». Отчёт противоречит сам себе (отчёт t-1632, строка 27).
Лента проверена Lead: ручной проход выполнен, фабрика не показала его в таблице.

Что видно в коде (чтение, не прогон): `scripts/traceability.py`, `Story.manual_outcome` (стр. ~425) возвращает `pass` по записи ручной
проверки, но `Story.manual_case` (стр. ~411) берёт запись через `report_facts._manual` под `except Exception: pass` и при `{}` вызывающий
(`Story.case_outcome`, ветка `level == "manual-agent"`, стр. ~1004–1010) молча возвращает причину из плана. Почему именно здесь
`manual_outcome` дал `{}` (запись не «current», не сопоставлена обязательство, исключение проглочено, или requirement x case идёт
другой веткой — строка-«покрыто TS-2» без кейса) — **не проверено**; это первая работа узла.

## Класс

Один факт («кейс прошёл руками») имеет два носителя: план S3 (причина «не исполнен») и ledger/запись S6 (результат). Таблица
читает план там, где должна читать результат; читатель молча сдаётся (P1), отчёт говорит одно в двух местах (FR-10, FR-41, FR-35;
AR-13, AR-14). Родственное: `pass` на красном (B-303, RD1-1/RD1-2) — тот же класс «результат прогона главнее плана».

## Что именно менять

1. **Воспроизвести на фикстуре CART-1** (узел RD1-18, первый шаг): `scripts/tests/test_traceability_report.py` — фикстура с планом
   `manual-agent`/`ui`, двумя строками плана с причиной «covered by TS-n», ledger `passed_green` и валидной записью ручной проверки
   (schema 2, текущая, обязательство сопоставлено). Ожидание ДО правки: строка таблицы `not run` (красный тест); называет причину —
   какая из четырёх ветвей выше.
2. **Один читатель результата ручного кейса** — `traceability.Story.manual_outcome` / `report_facts._manual` (функции названы выше;
   правка в той, где подтверждена причина). Строка таблицы по ручному кейсу с валидной записью `passed` — `pass` с основанием
   «checked by hand: <снимок после действия>» ВСЕГДА, кроме красного прогона и подтверждённого бага (порядок как в `case_outcome`:
   баг, потом ручной результат, потом план). Инвариант позиции: запись, которую блок «Checked by hand» не считает, в таблицу не
   попадает (один читатель, FR-10). Тест: фикстура п. 1 — строка `pass`; запись с устаревшим `sha` — по-прежнему не `pass`.
3. **Проглоченное исключение не молчит** (`traceability.Story.manual_case`, `except Exception: pass`): P1 разрешает не ронять таблицу,
   но неразобранный блок становится строкой отчёта «ручные результаты не прочитаны: <причина>» (не «not run» как будто плану
   нечего сказать; FR-41, FR-59). Тест: подмена `RF._manual`, бросающая исключение — таблица строится, в `facts` есть строка о
   нечитаемых ручных результатах.
4. **Сверка при сборке отчёта** (`scripts/check_delivery.py`, сборка отчёта — функцию называет спека): если число кейсов «Checked by
   hand» и число строк таблицы с `level: manual-agent` и результатом `pass`/`wait` расходятся — отказ называет расхождение и
   каждый кейс (FR-4: молчаливый pass запрещён, информированный — нет). Вердикт «A person must check N cases» считается из той же
   таблицы (N из строк `wait`), а не из плана отдельно. Тест: фикстура с расхождением — отказ называет TC_011/TC_012.

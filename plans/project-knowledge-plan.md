## 1. Как сейчас и почему это не то, что задумано

**Онбординг спрашивает всё.** Банк вопросов — проза в `skills/qa-onboarding/phases/p2-interview.md:81-370`: 19 тем, 43 вопроса, 6 пачек
(аудит `docs/tasks/specs/reviews/20261030-voprosy-onbordinga-audit.md`: 7 ответов человека, ≈ 1 ч 16 мин; 6 ключей никто не читает, 3 факта
спрашиваются по 2–3 раза). Правило навыка: «обязательный факт не пропускается и не заполняется дефолтом» (`SKILL.md:41-45`); обязательным
считается всё, на отсутствие чего потом жалуется код (`p2-interview.md:44-54`). Понятия «спросить позже, когда понадобится» нет вообще.

**Стори спрашивает не по нужде.** Гейт A спрашивает ключи входа на стенд у любой стори, не глядя, нужен ли её кейсам вход
(`gate_preflight.py:3823-3857`). Для ключей интеграций это уже починено — спрашиваются, только если стори привязана к интеграции
(`_integration_keys`, t-218 после cmp2: три ключа AWS и три учётки спросили у стори, которая их не касалась). То есть правильный образец
в коде есть, но он применён к одному классу ключей из многих.

**Запоминание уже есть — пять раз, пятью способами.**

| # | Что запоминает | Где лежит | Ключ ответа | Кто решает «навсегда» |
|---|---|---|---|---|
| 1 | свойство окружения («здесь моки вместо API») | `records/environment-properties.json` (`environment_record.py`) | типизированный ключ | человек словом `accept always` (D-0029, D-0032) |
| 2 | учётка стенда, адрес UI | прямо в `config.json` (`project_decisions.py stand-account / stand-frontend`) | указатель в конфиг | всегда навсегда |
| 3 | как читать версию сборки на стенде | `records/stand-identity.json` | стенд + профиль | всегда навсегда |
| 4 | отложенное на онбординге решение | `factory-backlog.md` + `records/project-decisions.json` (строки DD-n) | `field_refs` | дозревает по триггеру |
| 5 | уроки ретро (`stand_quirk`, `gate_answer`) | проза в `strategy/*.md` (S9 `knowledge_fold`) | нет | роль ретро |
| 6 (план соседней сессии) | как добыть учётки и данные для параллельных проходов | `manual.accounts_way`, `manual.data_way` (t-1957 §3.6–3.7, узел TR3-10) | указатель в конфиг + строка DD | спрашивается один раз на проект |

Шестой — почти точно то, что нужно: значение по умолчанию «not known», вопрос поднимается при первой нужде, не держит ни одного кейса,
открытая строка реестра не даёт спросить второй раз, без ответа — показывается при первой нужде следующей стори. Но он спроектирован как
частный случай ходока, а не как общий механизм.

**Чего не хватает, чтобы это стало системой:**
- у вопроса нет постоянного ключа: «уже отвечено» ищется по хэшу текста вопроса (`story_run.py:4387`), сменился текст — спросит снова;
- нет общего места, где сказано про каждый факт: когда его спрашивать, можно ли вывести самой, что делать, пока он неизвестен, кто его читает;
- нет общего ответа на вопрос «это про эту стори или про проект» — он есть только у карточки пробела стенда (`accept` / `accept always`);
- конфиг читают двумя путями (`config_contract.read_config_file` — 13 файлов, `hooklib.load_config` — ~56 файлов) плюс прямые чтения;
  ничто не связывает ключ, читаемый в коде, со строкой шаблона и вопросом интервью (записанный пробел AR-3 и AR-22).

## 2. Целевая схема

Четыре части. Каждая существует в единственном экземпляре; новый вид знания их не меняет, а добавляет строку.

### 2.1 Каталог знаний — одна таблица данных

`references/project-knowledge.json`, строка на факт. Это и есть «система ключей», о которой говорит владелец.

| Поле | Смысл | Значения |
|---|---|---|
| `key` | постоянное имя факта; оно же ключ вопроса и ключ ответа | `environment.access`, `environments[].bring_up`, `test_data.accounts_by_role`, `automation.selection` |
| `about` | о чём факт | `project` · `environment` (свой у каждого стенда) |
| `store` | где лежит значение | указатель в файл проекта (п. 2.2) |
| `ask_when` | когда узнаём | `onboarding` (стартовый набор, ≤ 10) · `first_need` (по ходу стори) · `never` (только выводится или сообщается человеком по своей воле) |
| `derive` | чем фабрика узнаёт сама до вопроса (P5) | имя пробы/выводителя или пусто |
| `while_unknown` | что делает фабрика, пока ответа нет (AR-23, FR-59) | `default: <значение>` · `gap` (строка-пробел в отчёте) · `in_turn` (обходной путь) · `hold` (держит только названные кейсы) |
| `needed_by` | кто читает — стадия/проверка/роль | список; строка без читателя не проходит тест |
| `question` | ключ текста вопроса и цены вариантов | строка в `question-prices.json` |
| `answer` | форма ответа | закрытые варианты · слова человека (читает дирижёр, P22) |
| `person_class` | чьё это решение | класс из `person-owned.json` |

Тесты-храповики на таблицу: у каждого ключа шаблона конфига есть строка; у каждого ключа, читаемого в коде, есть строка; у строки
`onboarding` есть тема интервью, и таких строк не больше 10; у строки `first_need` есть читатель, зовущий шов (п. 2.3), и текст вопроса.
Это закрывает записанные пробелы AR-3 и AR-22 кодом.

### 2.2 Хранилище — три файла проекта, один читатель

| Файл | Что | Сейчас |
|---|---|---|
| `qa-factory/config.json` | факты о проекте | есть |
| карточка окружения (по одной на стенд) | всё о стенде: адрес, как поднять, вход, учётки по ролям, можно ли ломать, **что стенд умеет и не умеет** («нет планировщика»), как читать версию сборки, принятые свойства | размазано: `environment` + `environments[]` в конфиге, `environment-properties.json`, `stand-identity.json` |
| реестр ответов (`records/project-decisions.json`) | по каждому ключу: спрошено / отвечено / чьими словами / в какой стори / отменено | есть, но только для отложенных решений онбординга |

Читатель один — новый `scripts/project_knowledge.py`: `value(key, env)`, `state(key, env)`, `environment(name)` (собирает карточку стенда
из всех её нынешних мест). Роли и проверки перестают знать, в каком файле лежит факт, — поэтому вынос окружений в отдельный файл
становится одной миграцией, а не правкой ~120 мест.

У факта явное состояние, а не «ключ пуст»: `known` (значение + откуда: проба / слова человека / стори) · `unknown` (не спрашивали) ·
`asked` (спрошено, ответа нет) · `not_needed` (человек сказал «не нужно») · `unreachable` (проба показала, что добыть нельзя, D-0043).

### 2.3 Шов «мне нужен факт» — единственное место, откуда рождается вопрос

`project_knowledge.need(key, env, story)` зовёт **потребитель в момент нужды** — этим и гарантируется, что стори не спрашивает то, что ей
не нужно. Порядок всегда один:

1. значение есть → вернуть;
2. есть выводитель → попробовать самой (P5, FR-50);
3. в реестре есть ответ или открытая строка → второй раз не спрашивать (FR-7); действующий прежний ответ применяется со строкой
   «действую по вашему ответу от <дата>» (D-0047);
4. иначе — вопрос через существующую единую форму (`Driver.closed_question`), ключ вопроса = ключ факта; вопрос ставится к ближайшей
   остановке, которая и так будет, и не держит кейсы, если строка каталога не велит иначе (механика t-1957 §3.6 п. 3, вынесенная из ходока);
5. пока ответа нет — поведение из `while_unknown`; неизвестное никогда не становится «прошло» (AR-28).

Гейт A зовёт шов только по тем ключам, к которым привязаны план и кейсы этой стори, — как уже сделано для интеграций.

### 2.4 Область ответа — «баланс», о котором говорит Volha

Каждый ответ ложится в одну из трёх областей, и это видно человеку в самом вопросе:

| Область | Куда пишется | Пример |
|---|---|---|
| только эта стори | `pipeline.json` стори (как сейчас `waiver.py`) | «в этой стори почту не проверяем» |
| этот стенд, всегда | карточка окружения | «на dev нет планировщика» |
| проект, всегда | `config.json` | «учётки берём из фикстуры X» |

Кто решает область: строка каталога задаёт её по умолчанию (`about`); когда вопрос закрытый — в вариантах ответа есть «только сейчас» и
«всегда» (обобщение `accept` / `accept always`); когда человек ответил свободными словами — область определяет дирижёр (суждение роли,
P27/AR-29, код слова не классифицирует) и говорит вслух одной строкой: «записала как правило проекта: … ; отменить — словом». При
сомнении — узкая область: спросить ещё раз дешевле, чем жить с неверным правилом проекта. Любая запись отменяема (`revoke` уже есть у
записи окружения — становится общим).

Кроме вопросов фабрики, есть дверь человека: «запомни для проекта: …» в любой момент — дирижёр кладёт это тем же путём.

### 2.5 Как добавляется новое знание (проверка архитектуры на примере владельца)

«Проект сам указывает, что всегда / никогда автоматизировать»:
1. строка каталога: `key: automation.selection`, `about: project`, `ask_when: never` (или `first_need` на S3 — решает владелец),
   `while_unknown: default {always: [], never: []}`, `needed_by: [S3 стратег]`, `answer: слова`;
2. дефолт в шаблоне конфига;
3. строка в `inject-map`: стратег получает путь к факту в брифе (FR-15; ссылка, не копия);
4. абзац в хартии стратега: правило проекта — вход для его решения по P28, решает он (P27).

Нового кода, файла и механизма запоминания нет. Если в четыре шага не уложились — дефект схемы.

### 2.6 Растущие списки и знания, которых фабрика заранее не знает

Слово владельца 10.11.2026: накапливаемые факты дополняются — «проект обязан отправлять отчёты в регулирующие органы, и их 3 штуки, а
потом добавится 4-й и 5-й. Это могут быть любые знания о проекте: учётки, домены, варианты мобильных девайсов, которые должен
поддерживать проект, операционные системы, языки и т.д.» Отсюда два свойства схемы.

**Факт бывает списком, и список растёт.** У строки каталога поле `value: one | list`. Элемент списка добавляется, а не перезаписывает
факт; у каждого элемента своё происхождение (кто сказал, когда, в какой стори) и своя отмена. Список никогда не считается закрытым:
если стори упоминает то, чего в нём нет (четвёртый регулятор, новая роль, ещё один язык), роль это замечает и добавляет через шов со
строкой вслух — «добавила в регуляторы проекта: X». Это суждение роли, не сверка кодом (P27).

**Вид знания может завести сам проект — без правки пакета.** Каталог двухслойный:

| Слой | Где живёт | Кто заводит строку | Кто читает |
|---|---|---|---|
| ключи фабрики | `references/project-knowledge.json` в пакете | разработчик фабрики | код и роли (учётки, стенды, команды запуска) |
| ключи проекта | `qa-factory/knowledge.json` в проекте | дирижёр — по словам человека или по наблюдению роли | только роли |

Строка проекта несёт то же, что строка фабрики, но без кода-читателя: имя («регуляторы», «поддерживаемые устройства», «языки»),
одна фраза, что это и на что влияет, `about` (проект / стенд), `value: list`, и `needed_by` — каким ролям показывать (стратегу,
дизайнеру кейсов, автоматору). Регуляторов фабрика заранее знать не может (P2), поэтому код такие факты только хранит и доставляет;
что из них следует для плана и кейсов — решает роль. Типичное применение — оси покрытия: устройства, ОС, языки, роли идут стратегу как
параметры (P16: один тест с параметрами, а не кейс на значение).

Роль получает не содержимое, а оглавление знаний проекта в брифе — имя, одна фраза, путь (FR-15, ссылка, не копия) — и открывает то,
что нужно её работе. Оглавление растёт строкой, брифы не раздуваются.

Ключ проекта, который понадобился коду (или оказался общим для многих проектов), переводится в слой фабрики обычной правкой пакета;
значения проекта при этом не трогаются — ключ тот же.

## 3. Стартовый набор онбординга (≤ 10; сейчас 6)

Критерий: без факта стори не может **начаться**, и фабрика не может узнать его сама. Выводимое показывается одним пакетом «нашла — верно?»
(один ответ человека).

| # | Что | Форма |
|---|---|---|
| 1 | репозитории приложения и тестов, где лежат тесты и кейсы, команда запуска тестов, конвенции веток и коммитов | один пакет «нашла — верно?» |
| 2 | можно ли фабрике писать в репозиторий приложения | вопрос |
| 3 | откуда читать тикеты и доступ к трекеру | вопрос (проба доступа сразу) |
| 4 | что фабрике можно писать наружу: баги, комментарии, MR | вопрос (решение человека, класс outbound) |
| 5 | где живут требования, кроме тикета | вопрос |
| 6 | опишите продукт и его самые рискованные области | один необязательный вопрос |

Итого пять обязательных ответов и один необязательный (слово владельца 10.11.2026: стенды и вход на онбординге не спрашиваются;
два последних вопроса объединены).

### 3.1 Стенды и пользователи накапливаются по ходу стори

Слово владельца 10.11.2026: «стенды накопятся постепенно, так как при каждом прогоне стори мы уточняем, на каком стенде тестить и можно
ли его ломать»; пользователи зависят от стори (где-то админ, где-то юзер, где-то гость) — «эти данные тоже надо накапливать, чтобы
фабрика заглянула в перечень пользователей и увидела, что есть, например, 4 роли. Тогда при составлении тест-плана это надо учесть».

- **Стенд.** Вопрос «на каком стенде тестируем эту стори» задаётся в каждой стори (выбор стенда — область «только эта стори»); уже
  известные стенды предлагаются вариантами, плюс «другой». Названный впервые стенд получает карточку окружения: адрес, как войти,
  можно ли ломать — спрашивается то, чего в карточке нет. У известного стенда «можно ли ломать» берётся из карточки и произносится
  вслух («dev: вы говорили, что ломать можно»), человек поправляет словом (подтверждено владельцем 10.11.2026: «из карточки»).
- **Перечень пользователей.** Два факта, оба накапливаются: роли продукта (`product.roles` — факт проекта: гость, юзер, админ, …) и
  учётки по ролям на каждом стенде (`environments[].accounts_by_role` — факт стенда; только имена переменных, не значения). Роль,
  которой нет в перечне, появляется из требований стори (стратег видит её в тикете) или из слов человека; учётка под неё
  спрашивается при первой нужде и остаётся в карточке стенда. «Гость» — тоже строка перечня (вход не нужен), чтобы стратег видел
  полный набор.
- **Читатель — стратег S3.** `needed_by` обоих фактов включает план: стратег получает перечень ролей и то, под какие из них на
  выбранном стенде есть учётки, и раскладывает проверки по ролям; роль без учётки — не молчаливый пропуск, а вопрос через шов
  (держит только кейсы этой роли). Схема доступа (как именно стенд логинит) выводится пробой при первой нужде, не спрашивается.

Всё остальное — `first_need`: ключи интеграций, адрес UI и `api_path`, мобильный стенд, четыре вопроса о тест-данных,
зависимости профилей, карта классов ущерба (дефолт), пре-коммит и форматирование, TMS, права на файлы стратегии, окна параллельности
(`dispatch.parallel_windows`: дефолт 3, тему интервью из TR3-12 снять). DoD — вопрос снят (аудит 30.10, §2). Шесть ключей без читателя
удаляются (слово владельца 31.10 в узле OH3-35).

Предельный случай той же схемы — прогон без онбординга (B-092): все факты `first_need`.

## 4. План реализации

Новая кучка `project-knowledge` (заводится после решения владельца; до того — этот файл). Узлы, поглощённые из других кучек, получают там
строку `перенос: project-knowledge`. Порядок фаз обязателен: 1 → 2 → (3, 4 параллельно) → 5 → 6.

### Фаза 1. Каталог и один читатель (поведение не меняется)

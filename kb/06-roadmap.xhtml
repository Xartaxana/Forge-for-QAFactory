This page describes the plans for QA Factory after version 0.10.2; what the factory does today is on the sibling pages. What each version changed is in the package's CHANGELOG.md (ai-packages/qa-factory/CHANGELOG.md). Here: the changes that are queued, by priority; what the reference runs measured; the limits a user should know about today; and how to report a finding about the factory.

How the roadmap is kept

The roadmap is the list of piles and their batches: a pile is one theme of work, and a batch is a set of changes inside it that one developer takes and finishes. A batch is closed when every change in it is finished and accepted; the roadmap promises no dates. Piles carry a priority, first, second or third, and a pile may have several batches. The tables below list the open batches that change what a user of the factory sees; internal tooling of the factory's own development is left out.

Work in flight is described on the other pages only after it is released. The grounding step of the test plan (S3 in two windows), the Codex host and qa-collect are in the package: they are described on the sibling pages, and only what is still missing from them is listed below as a plan.

A part of a batch that is already in the package is not listed here as a plan; it is described on the sibling pages and in the CHANGELOG.md.

What release 0.10.2 (hotfix-12586 wave 1) changed

The release answers the run of TP1-12586, which stalled and spent most of its time on the factory's own plumbing. Each change below is described in full in the CHANGELOG.md.

  • One carrier for a Then number (HF2-2): the number of a Then in a test-to-Then binding and the tag of the waiting remainder are read through one place in code, and a Then written as a boolean or a float no longer reads as bound.
  • A test that covers several cases (HF2-3): when one test stops at one case's red assert, the Thens behind that assert read “not proven”, never a pass, in the ledger, in the trace and in “Left with you”, and a case whose own run failed keeps its own verdict.
  • A red test the requirement contradicts (HF2-4): it closes its S5 window with its own manifest row, without a probe and without a person's word, and S7 triages the red.
  • Merged Then bindings (HF2-5): a hand fragment replaces the rows of the units it names and leaves the rest, instead of replacing the whole array.
  • A test with no run record is not a pass (HF2-6): the trace reads pass only from a green result row of the test itself, and the report counts “proven by tests” from the same place as its green tests.
  • Answers apply at once (HF2-7): a person's answers at S2, S3 and S4 are recorded by code and laid over the plan, one open blocking question stops the stage whatever the count, Q1: until the report keeps a question open, and every role's brief carries what the person already decided.
  • The profile of a manifest row (HF2-8): the mutation probe and a --node-id run keep the profile the row names, so two profiles on one test root no longer block the probe.
  • Cost capture off the hot path (HF2-9): the capture after a tool call no longer renders the dashboard, the Stop capture is asynchronous and renders it once, and a subagent no longer shrinks its parent's cost file.
  • One collect per run (HF2-10): run_suite --mine collects test ids once, and a collect it cannot read is said as “node ids were not verified” instead of being repeated.
  • Run freshness (HF2-11): a green run of other code is stale; the ledger reads it as changed since the run, S6 sends the test back to the runner, and a stale live check is proved again by code.
  • The fields of a manifest row (HF2-12): the fields every row owes are one list, the automator learns the missing ones at the S5 exit, and the marker prints the row form before the first handback.
  • Helpers and fixtures (HF2-13): the code critic flags a second helper beside an existing one and the same fixture created twice in one window.
  • The red line names the Then (HF2-14): a test that raises before its assert is flagged, and the patterns say to assert the count before unpacking.
  • Refusal tests (HF2-15): a refusal test must tell its cause from any other 4xx answer, a masked value must not be compared with another masked value, and the critic checks that the test's level matches the level the S3 plan gave its case.
  • Integration texts: the stage files, role charters and references say what the code now does, for example that the answers to the S2 question halt are recorded by code.

What the reference runs measured

The reference run of TP1-13797 on 13.10.2026 reached gate B and closed; its price was higher than the earlier run of the same story, mostly because of the conductor and repeated resumes in automation. This page quotes no amounts: prices are described as rules and words, and the dashboard page explains how far a story's price can be trusted.

On that run the gate B road for words that are not an approval worked live: nothing was recorded as approved, the conductor offered its moves with their prices, a rework of the report ran, and the gate came back shown again on the person's words. The same road at gate A, with prose instead of the approval word, was not proven by it.

No measured cost reduction is claimed: it needs paired measurements on real stories.

Known limitations a user should know today

LimitationWhat it means in practice
Case preconditions are only as good as the cases declare themThe gate-A check covers what a case names in preconditions (a variable in the env files the runner loads, or one anonymous GET). A need nobody wrote down still surfaces in S5
Hooks act only in factory sessionsThe read-size limit and the turn counter act only where there is factory activity, a role, or an open dispatch. So a story run outside the factory is not governed by the factory's guards
The tracker read route is direct API onlyA project whose only reading route is an assistant, a skill, or an MCP tool of the orchestrating session is not configured for reading and must be re-onboarded with adapters.ticket.direct_api. The assistant stays first-class as a write channel
The write probe proves a right, not a successtracker_write proves the right to create an issue. A mandatory project field can still reject one write. After a write the id is read back, and an issue that was not created is visible immediately as a local bug file plus a row in obligations.md
Two probes are not full parityA passing install smoke and a passing allow/deny pair certify that the guard fires and the package is intact. They do not certify that every lifecycle event of every host version activates
A stale live check is proved again only under an open S6 dispatchWhen a test changed after its run, S6 proves its live check again by code, but only while an S6 dispatch is open; otherwise the digest says “re-probe skipped” and the check stays stale
Two points about a test that stops at one red assert wait for the owner's wordA Then that is red because of a product bug is not commented out in the test: the role texts are neutral on it. And a Then that passed before the red assert reads “not proven”. Both are open forks, not decisions
Regression is never executed by the factoryRegression is never executed by the factory: the plan carries a recommended regression list, and running it stays with the team.

How to report a finding about the factory

A defect of the factory itself does not go into a ticket about the product; record it as a finding about the factory. It is not a question to answer. Record it where the doctor and the dashboard will see it:

bash add-finding \ --essence "" \ --scope local-urgent|local-calibration|upstream-candidate \ --witness "" \ --idempotency-key ""]]>

It appends one FB-n row to qa-factory/factory-backlog.md under “Findings about the factory itself”; retrying the same key returns the existing row instead of duplicating it. The owner of such a finding is the factory, and it is never turned into a task for the person who hit it. The conductor and the guards write these rows by themselves when they recognise their own defect, and you can add one by hand at any time.

If a story will not move, run /qa-factory:qa-doctor first: a stuck stage or an orphaned dispatch is repaired by recover, and a dispatch nobody is doing is freed by release on your word. What the doctor cannot repair, it names with its owner — and if that owner is the factory, the finding is already recorded.

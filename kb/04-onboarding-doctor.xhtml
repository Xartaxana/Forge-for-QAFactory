Three of the factory's skills never run a story. qa-onboarding teaches the factory one repository; qa-doctor tells you whether the installation, the project and every open story are in a state where work can go on; qa-collect packs the factory's records of your project into one file for its developers. You call each of them in your session: /qa-factory:qa-onboarding, /qa-factory:qa-doctor, /qa-factory:qa-collect. This page describes qa-onboarding, qa-doctor and qa-collect as they are in QA Factory version 0.10.2.

qa-onboarding

Purpose and when to run it

One-time setup, repeatable. It discovers the test setup, the application and test repositories, environments, conventions and adapters by reading real files, interviews the team only for the gaps discovery left open, and generates the project's configuration, strategy and profile only after an explicit “yes” at a summary gate.

Run itWhy
Once per project, before the first storyqa-story requires a project that has been onboarded
Again after a major change to tests, environments, profiles or conventionsRe-onboarding is a merge, not a fresh interrogation: every question offers the existing value as its default, human values and unknown adapter extension keys are preserved, and only approved fields are updated
When the doctor says config_schema is not okThe schema moved; the doctor prints the migration_hint keys to migrate

Run it from the project's folder: the repository root. Onboarding can run from the subfolder of a monorepo that holds the project. The factory finds its project by qa-factory/config.json, not by the top level of the repository, and when the two differ it says so in one line, asks nothing and goes on.

Nothing outside reading happens before the summary gate. Nothing beyond reading the repository happens before the summary gate's explicit yes, except the run's own notes in qa-factory/state/onboarding/. No project files, no commits, no external calls until the person says “yes” in phase 3. Git ignores the notes folder from its first file.

Resuming. Every phase writes what it found and what the person answered into those notes as it goes. After a compaction or in a new session, onboarding continues from its notes, and a topic you already answered is not asked again. The notes win over memory.

The summary gate

One screen, four parts, presented exactly once per round:

  1. What was found (phases 1 and 2b), one line each, with phase 2b's three states kept verbatim.
  2. What was answered (phase 2), plus 2b: what was inferred from the repository — the conventions read out of the actual test files, as a block to correct in place. Correct a line and it is written as confirmed; say nothing and it is written as inferred, which is an honest label.
  3. What will be written — the exact file list, one line about the report probe (see below), and 3b: what the install would delete, set aside and keep — every file of every group, listed in full, because one “yes” covers a deletion and a person who says it sees every file. Files the factory does not recognise are set aside under qa-factory/state/retired/, never deleted.
  4. Deferred items — every topic that was asked and left unanswered, with the question as it was put, the marker location, its backlog row, and, for a required fact, its consequence attached.

It ends with exactly one question: “Write these files? yes / edit”. yes goes straight to phase 4. edit asks what to change and rebuilds the same full summary once more — never a loop of partial writes. Anything else is answered and then the same question is re-asked; that is not an implicit edit. There is no fifth part for topics nobody asked about: a required topic missing from parts 1 and 2 is asked, not listed as deferred. The “yes” approves the listed file edits, the listed report probe and the listed dependency preparation; it does not authorize a commit, a push, a deployment, an unlisted installation or a changed test command.

The test command is proved at onboarding

Right after the profiles are written, onboarding runs each selected profile's test command to prove that its run leaves a report the factory can read. It runs ONE existing test through each profile's own one-test command (the report goes to the OS temp folder, and nothing changes in the project except the record gate A reads), because a run that writes no readable report is recorded as not executed at every story, however green its log. The summary gate lists this probe, so its “yes” covers it. Per profile the probe ends in one of four ways:

ResultWhat you hear
ProvenNothing.
Could not be checked (no test, a timeout, a launcher that is missing)One line in words. Nothing is proposed; the card of gate A asks again at the first story.
A known cure ran greenWhen a known cure exists, onboarding proposes it in words, one proposal per profile, and applies it only on your recorded yes. The question reads “I propose to run it as: <command>. Do it?” and only an explicit yes counts, and one approval changes one key. A headless approval of a cure is refused.
No cure is known, or the cure did not proveWhat was run, what came out, and why nothing is proposed, then three answers: here is the command that writes a JUnit report · I fix it myself · not needed now. The question is asked at most twice per profile, then it is treated as “not needed now”, which records nothing.

qa-doctor

What the doctor is for and when to run it

Diagnosis, run between stories or whenever something feels wrong. It answers one question — can work go on, or is something needed — and ends in exactly one next action. It writes the dashboard, activity telemetry, smoke and host-probe receipts, and, only on a person's explicit word, the archive flag and controller.py --operation recover|release. It never edits a pipeline.json by hand.

The doctor asks only three questions, all after its report: the archive offer, whether anybody is working on a stuck story, and the price-table question. None of them replaces a fact; a diagnosis is never something a person has to answer a question to receive. The price-table question appears only when the configuration check finds a conflict in the project's model prices: it is asked as written, nothing is applied, and one already answered is not repeated.

The repair phase

The doctor is where a person comes with a story that will not move. When what stops it is the factory's own bookkeeping, the person is not told to “fix pipeline.json”, and the doctor does not edit it either. The doctor's only repairs are recover and, on your word, release. Both are shipped, idempotent, journalled code:

The archive offer

After the report, the doctor runs archive_task.py --candidates --days 14. The two candidate classes are two different conversations:

The file holds the person's words exactly as they said them. If an archived story was the source of the report's next action, the verdict is recomputed and the new one-line action printed.

What the doctor never does

  • Never asks a clarifying question to produce a fact. Facts come from a script or a plain git/file check. Its questions are decisions — the archive offer, “is anybody working on this story?” and the price-table question — with one exception, the sample ticket in step 2b when no story supplies one.
  • Never writes a config, a strategy file or anything under artifacts/. Running a read-only probe is not writing; its receipts live in state/.
  • Never sets archived by its own judgement — only archive_task.py, only on a person's word, --force only on their explicit answer.
  • Never fixes an audit finding itself: names it, names its owner, moves on.
  • Never runs project tests, installs dependencies or deploys the application, and never synthesizes a global green from independent profile results.
  • Never debugs the factory. Evidence missing after one prepare/pair/check is one line — unknown / owner: factory, the fact, one recommendation — never a reason to read or grep the plugin's scripts and manifests, and never a retry with variations.
  • Never reports a green it cannot back. A line is as good as its evidence; a status is never upgraded while summarizing; silence is not a pass (“no stories yet” is said out loud).

Sending the factory's records to its developers

/qa-factory:qa-collect packs the factory's records of your project — what ran, where it stalled or looped, what it cost, and your own words about it — into one file that you send to the factory's developers yourself. qa-collect asks two questions in one message, runs one packing command and changes nothing in your stories. Run /qa-factory:qa-collect from the project folder that holds qa-factory/config.json; the factory sends nothing from your machine.

StepWhat the skill asks and does
AskOne message with two questions, answered in your own words — either, both or neither: what problems you had with the QA factory since it was installed (or since the factory last packed them), and what you would like it to do differently or better. The reply “nothing to add” writes no file. With no person to ask, the packing records that nobody was asked
Write the words downEach answer word for word into a new file under qa-factory/state/words/ (collect-problems-<stamp>.txt, collect-suggestions-<stamp>.txt). An answer left out writes no file. One text that does not divide into the two answers is written whole as the problems file. The words are not shortened, sorted or judged, and a words file is never overwritten or deleted
PackONE command, collect_pack.py, with the files of this run only. No agent packs anything and no model is involved. A data set that is not at its standard place is named in the output as <SET>: not found at the standard place; the skill then asks where it lives and runs the command again with --extra <SET>=<path inside the project>, and nothing else is searched for
The windowBy default the archive holds what is new since the last packing; --since install packs everything since the install again. An archive you did not send stays on disk
ShowThe summary of the run, as printed (at most twelve lines): the archive file and its size, the window, the gaps named, the files skipped with a reason, and Package modified. If the place for the file would show in git, the archive goes to the temp folder and the summary names the reason. Any other refusal is shown as printed; the skill does not work around it

Everything that goes into the archive passes the factory's redaction rules. The finished archive is read back and checked again; if anything is found, the archive is deleted and the command refuses.

An archive made by qa-collect says whether the installed package was modified, by comparing it with the fingerprint the release carries. The answer is yes only for a byte difference in a named file of a release of the same version, no for equality, and unknown, with a reason, for every doubt — an install whose release carries no fingerprint file reads unknown. Editor and cache leftovers are listed apart and never count as a modification.

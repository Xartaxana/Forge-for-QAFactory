Who this guide is for

This guide describes QA Factory version 0.10.2.

Use QA Factory to test a ticket from requirements to a final QA result. This guide is for the QA engineer who runs it on a project: install it once, set the project up once, then test tickets.

You run the factory from Claude Code: you type a skill command, the story moves through its stages in that session, and the factory asks you only what a person decides. Codex works the same way once the plugin is installed there; its install steps are in section 1.

CommandWhen you type it
/qa-factory:qa-onboardingOnce per project, and again after a major change to tests, environments, profiles or conventions
/qa-factory:qa-story <TICKET-ID>For every ticket you test
/qa-factory:qa-doctorAfter installing, between stories, and whenever something feels wrong
/qa-factory:qa-collectWhen you want to send the factory's records of your project to its developers

Requirements

Claude Code: from git

Install from the marketplace:

bash

The marketplace that carries QA Factory is named qafactory.

Claude Code: from a local clone

Install from a local clone of the repository, on its default branch. If you already have a clone of QAFactory, do not clone it again: pull it.

bash

Keep the clone of the plugin repository outside every project you onboard. The factory's hooks find the project by the nearest qa-factory/config.json above their working folder, so a plugin that lies inside a project makes hooks and self-tests mistake that project's stories for their own sandbox. A sibling folder is the usual place.

A local clone is installed as it lies on disk, so anything a test run left inside the package goes along with it. Before installing from a clone, run python scripts/selftest.py --hygiene in the clone; it names every file that is not package content.

Codex

Codex has its own manifest and its own plugin commands. Follow these steps, and read INSTALL.md in the package for the access setup.

  1. Register the repository's marketplace with codex plugin marketplace add <local-clone-or-git-source>. Check the real source and marketplace name with codex plugin marketplace list and codex plugin list before installing.
  2. Install with codex plugin add qa-factory@<verified-marketplace-name>. Confirm that the installed manifest matches the source version and points to ./hooks/codex.json, the Codex hook manifest.
  3. Review and enable the plugin's hooks in the host's trust flow. Repository trust and file existence do not grant hook trust.
  4. Select Full access for the project before the first doctor or onboarding run; installing the plugin alone does not change the permissions of the current task.
  5. If your Codex CLI needs explicit custom-agent profiles, preview them with python <plugin>/scripts/codex_roles.py --root <project> and add --write to export the roles into .codex/agents/. Existing profiles of yours are protected.
  6. Start a fresh Codex task, check that its permissions say Full access, and run the doctor. A mechanism the doctor cannot prove is reported as unverified, never as green.

From there you invoke the same skills. The session dispatches the roles through the hook manifest and, in the Codex CLI, the exported profiles; in Codex Desktop it names each role's task.

Update and uninstall

An installed plugin is cached, and a plain reinstall over the same version does not refresh it. Update with the full cycle, restart Claude Code, then run /qa-factory:qa-doctor:

bash

Never update the plugin under a live story: the session would run on two versions at once. Update between stories only.

To remove the plugin, run claude plugin uninstall qa-factory. The folder <project>/qa-factory/ is yours and stays in place.

Confirm that the plugin is installed:

bash

Open Claude Code in the repository of the project you want to test, and type /qa-factory:. The list shows four commands: qa-collect, qa-doctor, qa-onboarding and qa-story.

3. Onboard your project

The project under test is the folder you start Claude Code from. Go to the repository of the project, or to the subfolder of a monorepo that holds the project, and run:

bash

The factory reads the repository first and asks only what it could not find. For example:

TopicWhat you are asked
Application repositoriesWhere the application code lives locally, if discovery could not find it
Test environments and credentialsHow each test environment is reached, which access scheme is the one, and who needs each key the environment file does not hold
Test dataAccounts, real data and the masking rule, cleanup, and shared records
Risk areas and the impact-class mapAbout risk, onboarding asks which parts of the product would hurt most if they broke, and then whether your project maps impact classes differently from the factory's canonical scale.
Where results goWhere bugs go (markdown files by default, or Jira) and where cases and results go (markdown by default, or Xray, TestRail, Zephyr)
Definition of DoneOne sentence: when your team considers a story tested

Git conventions, ticket and test-management tools and product basics are asked in the same way, and only where discovery found nothing. Questions come in batches of at most four, never one wall of every open topic.

Nothing beyond reading the repository happens before you answer yes at the onboarding summary. The one exception is the run's own notes, which git ignores. Before it writes anything, the factory shows the summary and asks one question: write these files, yes or edit.

  • Approve only if the information is correct: answer yes.
  • If something is wrong: answer edit. The factory asks what to change and shows the summary once more.

The factory proves each profile's test command at onboarding. A proven cure is offered in words, once per profile, and applied only on your yes.

If the session is compacted or you start a new one, run /qa-factory:qa-onboarding again: onboarding continues from the notes of the run, and a topic you already answered is never asked again.

After onboarding, run /qa-factory:qa-doctor again. It checks whether QA Factory is ready and names the next action, normally your first story.

5. What you do during the story

The factory runs the stages itself. Your main responsibility is two gates: gate A after the plan and the cases, and gate B after the results. Besides them it also stops for you in four places:

  • the review of the sources it found for the story, with its decision on each, at the start;
  • a halt, when a decision is missing: it names what is needed and from whom, and "go on without it" is an answer;
  • a stand-gap card, when a test cannot run because the test environment lacks something;
  • one optional closing question at the end of the story.

To approve a gate, answer with the word approve; words that ask for a change are not recorded as an approval. When you ask for a change, the stage is reworked first and the gate is asked again.

Gate A - review the test plan

Check that:

  • all important requirements are covered;
  • negative cases are included;
  • high-risk areas are tested;
  • unclear requirements are not guessed;
  • proposed tests are useful and not duplicates.

Approve only when the plan is good enough to execute.

A stand-gap card

A card names the fix, and you answer on a line of its own: the case id, a colon and one word. A card lists the words that apply to it.

WordWhat it means
changeThe factory makes the change shown on the card, on your word
myselfYou make that change yourself
runYou run this test yourself, where the missing piece exists
acceptIt stays blocked and is reported as not run

Gate B - review the results

The message opens with the verdict and the traceability table. Check:

  • what was planned;
  • what was actually executed;
  • what passed or failed;
  • what was skipped, blocked, or not run;
  • bugs and remaining risks.

Then make the final QA decision (section 6). If something was not executed, it is visible and never silently treated as passed.

6. The delivery decision

Delivery has three outcomes: ready to ship, ready once you finish the checks left with you, and not ready to ship as is.

WordThe report saysWhat it covers
yesReady to shipEverything is checked: no bug, no gap and nothing left with you
after_checksReady once you finish the checks left with youThe factory found no bug and no gap, but part of the testing is left to you or to another environment
noNot ready to ship as isA bug or a gap was found, or a requirement was not proven

The section Left with you names every check handed to you and the regression scope the factory recommends. The checks handed to you, with the exact command, are also shown at gate B.

For every gap that is yours to decide, you choose one of: fix now, verify on another environment, defer with a reminder, accept the risk. Bugs are answered by number: for example, file 1 and 3, and 2 is not a bug.

  • On yes or after_checks you decide whether the factory opens a merge request. A merge request is only ever opened as a draft.
  • When the verdict is not ready, there is no merge request to open; you may only deliver with known gaps, and only with a stated reason.

7. When the factory needs you

Every question the factory asks you is a closed question: each answer is followed by what it costs the factory, what it costs you, and what it does to the story.

When the factory has no move of its own, its conductor offers you every move that lets the work continue, each with its price; in an interactive session the session itself plays the conductor.

Your word passes any block. The factory records what you answered, in your own words. A request to change the factory is recorded as a finding about the factory; the factory never edits its own plugin.

8. If something goes wrong

Run /qa-factory:qa-doctor. Use it when:

  • the factory does not start the story;
  • a previous run was interrupted;
  • the configuration looks incomplete;
  • you are unsure what to do next.

Follow the one next action the doctor shows.

9. Send the factory's records to its developers

/qa-factory:qa-collect packs the factory's records of your project into one file that you send to the factory's developers yourself.

Run it from the project folder that holds qa-factory/config.json. The factory sends nothing from your machine.

  • qa-collect asks two questions in one message, about the problems you had and what you would like done differently, and you may answer either, both or neither.
  • It writes your answers down word for word, runs one packing command and shows you its summary.
  • Everything that goes into the archive passes the factory's redaction rules: where a secret detector hits, only that unit (one line, one JSON value or one key) is replaced, never the whole file. The finished archive is read back and checked again; if anything is found, the archive is deleted and the command refuses.
  • If the packing output names a set of records it could not find, say where it lives inside the project; nothing else is searched for.
  • Your stories are not changed. You send the file named in the summary.

10. Where QA Factory keeps its files

The factory's files of a project live under qa-factory/: records/ is committed with the project, and state/ is machine-local and ignored by git.

strategy/project-profile.mdProject context: product basics, stack, architecture, environments, test data

state/cost/Token, request, timing and execution-cost telemetry
artifacts/<TICKET>/The story's folder; the four documents written for you are understanding.md and test-plan.md (gate A), test-report.md and retro.md (the end); the rest is working material

obligations.mdFollow-up items that cannot be completed now
factory-backlog.mdFactory and setup findings and improvement items
  • The readiness report is qa-factory/state/readiness.json.
  • The coverage map is qa-factory/records/coverage-map.md.
  • The product and business context is kept in the opening sections of strategy/project-profile.md.

11. Quick checklist

First time on a project

  • Install the plugin (section 1).
  • Check that claude plugin list | grep qa-factory shows it, and that /qa-factory: lists four commands.
  • Open the project repository and run /qa-factory:qa-doctor.
  • Run /qa-factory:qa-onboarding.
  • Review and approve the onboarding summary.
  • Run /qa-factory:qa-doctor again.

For every ticket

  • Run /qa-factory:qa-story <TICKET-ID>.
  • Give one of the merge request, branch or commit, and the environment, if you know them.
  • Review gate A.
  • Review gate B.
  • Make the final QA decision.
  • After each gate, continue with the same command.

QA Factory — Dashboard and metrics

This page describes QA Factory version 0.10.2. The dashboard is one static HTML file per project, written by code. No agent ever authors it, and opening it recalculates nothing. Amounts on the dashboard are estimates, not invoices (section 8), and this page quotes no amount: the attached reference dashboard shows real figures.

1. What it is and where it lives

Every onboarded project gets exactly one file:

text/qa-factory/state/factory-dashboard.html]]>

It is a self-contained page — markup, styles and a few lines of tab-switching script in one file. Open it in a browser from disk; nothing is served, nothing is fetched, no model is called. The renderer is scripts/factory_dashboard.py, whose own docstring states the boundary: "Rendering never invokes models, product tests, schedulers or external connectors."

QuestionAnswer
Who writes it?Code only. factory_dashboard.py reads the project's recorded files and overwrites the HTML. No role, no agent and no human edits it.
When is it rebuilt?On factory events, through one chokepoint (dashboard_refresh.refresh_project): controller mutations, the cost capture at a Stop (once per Stop, after the capture), bug snapshot import, project decisions, environment preparation, S9 closure, and any qa-doctor run. Writing or editing an artifact (validate_artifacts.py) and the debounced cost capture after a tool call do not draw it.
What if a refresh fails?The refresh runs after the story's writer lock is released, so drawing the page never stalls a dispatch. A refresh that failed is recorded in qa-factory/state/dashboard-deferred.json until the next refresh succeeds. The run that hit it says so.
Is there a schedule or a metrics agent?No. Both were removed. "No metrics agent or timer runs" is the contract (references/metrics-contract.md).
Can I rebuild it by hand?Yes — see the commands below.
Does opening the file re-evaluate anything?No. The header prints when the metrics were last checked; date-dependent changes are re-evaluated at the next factory event.
bash --include-archive # a comparison page for one story, written outside the project, changing nothing in it python "${CLAUDE_PLUGIN_ROOT}/scripts/factory_dashboard.py" --task --out --read-only]]>

The flags are --root, --include-archive, --task (repeatable: show only that task; sections with no task key stay whole and say so), --out (write the page elsewhere) and --read-only (change nothing under the root; it needs an --out outside the root). A page filtered by --task or written read-only must name its --out, so it never replaces the whole page every session reads. Archived stories are hidden by default; the Testing tab says how many are hidden and how to bring them back.

One environment variable suppresses the rebuild everywhere at once: QA_FACTORY_SKIP_DASHBOARD_REFRESH=1. The red probe in S5 sets it for its whole batch, so the factory does not redraw its own dashboard underneath a running test.

2. The page shell: header, banner, three tabs

Above the tabs, in order:

  • Title and meta lines — the page title, a package-version label, the generation timestamp, and one line stating when the metrics were last checked plus how many rules were not evaluated. That last line also repeats the rule: refresh on factory events or doctor; reopening this file does not recalculate.
  • Metric warnings banner — the active and awaiting-verification signals, with evidence links that jump to the right tab and open the right detail. Rendered by dashboard_widgets.signals_html. Empty when there is nothing to say. See section 7.
  • Deferred decisions ready for review: N — one line when the factory's own deferred decisions (DD rows in factory-backlog.md) have reached their recorded trigger. The table itself is on the Factory tab; no tables live above the tabs.

Then three pill tabs: Testing, Cost, Factory. Each tab ends with an expandable "All metric values, formulas, samples and sources" block containing the full catalogue rows for that tab's metric packages — value, state, sample size, formula, sources, reporting window, formula version and evidence links.

The version label in the header is read from the installed package manifest, not typed into the renderer. A dashboard file only says what it was rendered by; what this installed host has exercised is qa-doctor's job.

Three counts on this tab are deliberately independent and must not be added up or read as each other: rejected handoffs (F02), gate blocks and unsafe completions (F03), and retries (F05). A gate block on its own is the mechanism working; blocks piling up unresolved is the problem. A retry without a cause is not a metric: the controller stamps retry_reason on every resumed dispatch (and retry_words when a person asked for the repeat), older stories are classified from the parent's checkpoint wording, and a share above 10 % or one cause three times raises a yellow row in the banner — “the factory does work twice: <cause>” — as a finding about the factory or an incident of the host, never as the person's work. A human check with no owner reads “Nobody assigned, no trigger recorded — assign an owner or record the condition”, never three negations.

6. The metric packages

The catalogue holds 48 metrics in four packages: testing, automation, factory, and cost and estimates. It is the file references/metrics/catalogue.json. Each package has a prose pack under references/metrics/ and a heading on the dashboard's formulas block. Every value carries a formula version, source references, an observation timestamp, a sample size and a status.

6.1 Testing (T01–T14) — "Testing quality"

What it measures: whether the behaviour that was promised has actually been proved, and what the defects look like. Why it exists: a run report says what ran; this package says what is verified, which is not the same thing.

T03 Test outcomesUnique current instances per pass / fail / error / blocked / skipped / not_run / stale / ambiguous, by task, level, repo and owner.
T04 Test pyramidThe same instances counted by recorded level, with separate unknown and manual lanes.
T05 Manual proof completenessShare of approved manual-agent cases whose accepted outcome carries all required evidence.
T06 Open obligations and regressionRemaining checks by kind, status and age; recommended-regression checks listed explicitly as "not run by factory".

What it measures: how the automated suite behaves as an instrument — does it pass first time, is it flaky, is it re-running work it already proved. Why it exists: an all-green suite that is green by accident, or green because nothing actually ran, is worse than a red one.

6.5 When a metric reads "not available" — and why that is honest

Every metric carries one of these statuses, and the dashboard prints it next to the value with the sample size:

StatusWhat it means
availableComputed from complete inputs.
partialThe numerator is incomplete against a complete denominator — the value is an explicit lower bound.
no_dataThe denominator is complete and empty. Genuinely nothing to measure yet.
unavailableThe denominator itself is unknown, or a required input does not exist.
staleThe inputs exist but the projection behind them has not been refreshed.
not_applicableThe metric cannot apply to this population (for example imported-only results for C07).
demoAn illustrative shape shown before any real record exists; never enters totals or alerts.

The governing rule is this. Missing inputs never imply zero, success or a monetary saving. Two metrics are permanently unavailable in a fresh install, by design rather than by neglect:

  • C14 Automation time benefit — unavailable until an approved manual baseline and verified authoring/maintenance effort exist. The factory will not turn "the gap between two timestamps" into "hours a human saved".
  • C15 Monetary ROI — unavailable until a documented counterfactual plus labour and infrastructure inputs exist. It also refuses to monetise found bugs with arbitrary severity weights.

Three bug metrics (T12 reopen rate, T13 time to first fix, T14 repeated cycles) stay unavailable until the tracker snapshot carries complete transition history over the window. A partial export produces "unknown", never a count-based guess — and an empty partial export is not a project-wide zero. None of these is a permanent removal: each becomes a real graphical widget the moment its required input exists.

Read "unavailable" as "I refuse to make this up". A dashboard that shows 0 % reopen rate because it has no history is lying; one that shows "unavailable: complete Fixed → Reopened history" tells you exactly what to go and fix.

7.4 Signal lifecycle

A signal is active, verifying or resolved. After a human decision, record the reference:

bash --ack --decision-ref ]]>

That moves the signal to verifying; it never declares recovery. Worsening reactivates the warning; only fresh healthy observations meeting the recovery policy resolve it. Repeating an observation, or changing unrelated source files, confirms nothing. Removing a policy does not silence an unresolved warning — it stays visible as not evaluated.

8. A story's price: one figure from two records

A story has one price on every page: the dashboard, the retro and the budget ceiling read the same function. That function is scripts/task_price.py, and nothing else prices a story, so two pages cannot show two prices for it.

8.1 The two records

The price is computed from two independent records, the token usage in the factory's cost files and what the command line itself charged for each session, and the two are checked against each other session by session.

RecordWhere it comes from
A — the cost filesThe token usage of each session, from state/cost/<session>.json, written by the factory's own parser and re-priced when it is read, at the catalogue's list price
B — what the command line chargedThe charge the command line itself reported for the session, as the driver's journal recorded it

A story run in an interactive session has only the first record, so its price is marked not_cross_checked. Record B is the driver's journal, and a story that does not run through the driver has no second record to compare with.

What the two share is only the API's per-request usage. Agreement proves that the parser found every request once, that the same sessions were meant, and that the list price is the one the command line used. It is not an invoice: on a subscription both records are list-price proxies.

8.2 The check, and the four statuses

The check is made per session, never on the sums, so a shortfall on one session cannot be cancelled by an excess on another. A session agrees when its two figures are within a tolerance set below the cost of the cheapest real request, so one request missed on either side always shows. The price carries one of four statuses:

StatusWhat it meansWhat is printed
agreesEvery session has a record, at least one session could be compared, and none differsOne figure
differsAt least one compared session differs between the two recordsA range, “from … to …”, with a finding that names the largest gap and says it is a defect of the factory's measurement, not a fact about the story
not_cross_checkedNo session had both records, so nothing could be comparedOne figure from the one record each session has, marked as not cross-checked
incompleteNo session has a record, or a session is in neither record, or a call of the driver's journal names no session, or the rows by agent do not add up to the total, or the forms of external-agent calls cannot be readThe figure that is known, with the reason

When the two records disagree, the price is printed as a range from the lower to the higher figure, never as one number. Only while the status is differs do the two ends differ; the dashboard prints the range as “from … to …” and keeps a range-priced story out of the $-band widgets. A price whose records are incomplete says so, and the figure shown is only a floor. The real figure can only be higher. A range never hides a defect behind one confident number, and a missing record is never a zero.

8.3 What the price includes

The price of a story includes the work of its roles, of the conductor and the calls to external agents. Where the forms of an external agent's calls cannot be read, the price says that calls may be missing and is incomplete, never agrees. The price of a story, the retro's table by agent and the Cost tab's rows by agent are one pair of figures, split by agent, and the rows add up to the story's price.

8.4 Where the numbers come from

scripts/cost_capture.py runs as a lifecycle hook. The host writes the token usage of every API call into the session transcript and into sibling subagent transcripts; capture tails those records and idempotently rewrites one file per session:

text/qa-factory/state/cost/.json]]>

Nothing is sampled, estimated from prose, or asked of a model. Every dollar on the Cost tab traces back to a recorded request in one of those files.

8.5 Sessions, activities and tasks — three different words

TermMeaning
SessionOne working session with the host. One cost file. It may touch several stories, or none.
ActivityAn explicitly opened and closed interval with a type: story, doctor, onboarding, environment-maintenance or unclassified. Boundaries are recorded, never inferred from what the prompt said.
Task attributionEvery API call is attributed to the task of the last artifact-write marker before it. This marker persists while the story waits for a human.

Sticky attribution is the important one. Activity attribution closes its interval when the story halts for a person; task attribution does not. The conversation during a halt is still that story's cost. That is why story cost is read from by_task, never from by_activity — and why the dashboard has no "By activity" table. The stickiness also covers the gap between two segments of the same story and the tail after its last one.

8.6 Subagent (role) spend

by_task[task] includes the usage of every role the task dispatched. The money a story cost is the money it cost including its roles, not just the main chain. The orchestrator entry stays the main chain only, which is what makes an orchestrator-versus-roles share computable at all. A role whose prompt carries the ticket but wrote no marker is bound to that ticket by the prompt.

8.7 "By task" and "By agent" are built from one ledger

Both tables are built from the same request ledger and filtered to the same population (factory sessions), so their totals match by construction rather than by luck. Both sum individual request valuations, and each table also prints a "Sum of sessions (check)" row so you can see the check rather than take it on faith. The check is a sum of the ledger; the agreement of the two price records (8.2) is a separate proof.

8.8 "Non-factory sessions" and "Unclassified"

8.9 Rates, and why the amounts are estimates

  • The price uses the project's own rates where it sets them: a rate in cost.rate_overrides is the person's correction, so it is the price, while the check between the two records still compares at list price.
  • Rates resolve from cost.rate_overrides in the project's config.json first, then from the bundled exact-id catalogue references/model-rates.json (provider, exact model id, aliases, validity dates, source URL, verification date, and per-million rates for input, output, cache read, cache write 5m and cache write 1h).
  • If a model has no exact rate, no price is invented — not from a family name, not from a similar model. Tokens are still counted honestly, total_cost_usd stays null, and priced_subtotal_usd reports the amount that is certain. The headline card relabels itself to "estimated known subtotal" and the By-model row says "no exact price".
  • cost.rate_confirmation records whether the project has confirmed its tariffs. Until it does, the card says the tariffs are a public reference or override and unconfirmed.
  • The amounts are estimates at API list prices for the tokens observed; they are not an invoice. They are not your subscription charge, and not what any provider will bill. They exist to compare stories with each other and with the size bands — use them as a ruler, never as an accounting figure.

8.10 Recapture of stale cost files

Before the dashboard reads state/cost/, it recomputes any cost file that is in an old format or whose activity was backfilled after the original capture (cost_capture.recapture_stale). It honours the same skip variable, so a red probe never triggers it. When a file cannot be recomputed because its transcript is gone, the file keeps its last capture and the session is named in the Stale cost files alert.

The pass reads only this project's transcripts. A cost file whose transcript slug says the session was opened in a parent or unrelated directory (the factory's own development, run from one level up) is left as it is and reported skipped: parent directory - not recaptured; the pass the dashboard build triggers also skips a transcript larger than cost.recapture_max_mb (default 64 MB) or changed in the last five minutes, because a render must not wait for files that large or still being written. An explicit cost_capture.py --recapture --session <id> still recomputes anything. The hook capture no longer writes a parent-directory session into this project's state/cost/; files already there stay and are shown apart (8.8).

10.2 What the analyst adds

At retro_mode: full — the default, and what silence means — qa-retro-analyst is dispatched over the finished numbers and is told explicitly not to open the journal or the cost files. It writes only what no table can produce:

  • the prose reading of the numbers;
  • the knowledge fold — gate answers into the project FAQ, terms into the glossary, stand and data quirks into the project profile, recurring traps into whichever single strategy document owns that kind of fact (code and run traps to the framework rules, planning traps to the test strategy — never both);
  • the obligations.md rows this run leaves behind, the only carrier between stories;
  • the estimation-ledger.jsonl precedent line that feeds the Cost tab's estimate widgets;
  • the factory-backlog.md entries, including the human's feedback row;
  • the human's one optional closing question, recorded verbatim — "skip", silence or a non-answer is recorded as declined, never paraphrased into an opinion.

Two other modes exist, and only on the person's own words: numbers (the table alone, written by code, no dispatch and no prose) and skip (nothing, with their words recorded). Nothing is archived at S9 — hiding a story from the dashboard is the human's word to qa-doctor, never a role's conclusion.

The retro carries two execution-volume numbers, computed by retro_numbers.run_block_metrics from work/run-blocks/*.json:

13. How to read it in two minutes

  1. The line under the title. When was this generated? If it is old, the project has had no factory events since — the numbers are not wrong, they are just not new.
  2. The banner above the tabs. Any metric warning? Any deferred decisions ready for review? If both are empty, nothing is asking for you.
  3. Testing → Remaining checks. The count, the oldest age, and how many are ready to perform. That is your actual to-do list.
  4. Testing → Test traffic light. Red or yellow? Open the story in "Tests by task": its bugs, its "Left with the person" list and the non-green level groups are already open, each red row carries its triage verdict, and the autotest id is one hover away.
  5. Testing → Trends. Glance at first-attempt pass rate and flaky evidence rate. If they say "History not yet sufficient", that is honest, not broken.
  6. Cost → the cards. Does the spend card say "factory spend, this project" or "known subtotal (floor)"? Is the sum check ✓, ✗ or ?. Anything but ✓ means read the alerts before quoting the figure.
  7. Cost → the price of your story. Find its row in By task or its story card and read the price the way section 8 says: one figure when the two records agree, a range “from … to …” when they differ, and a floor when the price is incomplete. A range is not a mistake to round away; it is a finding about the factory's measurement. Read the completeness column — "incomplete" means the amount is a floor, and the alert at the top of the tab names the roles whose usage never arrived. Money in "Sessions of parent directories" is not yours and is not summed.
  8. Cost → Hot cache share. Below 90 %? Something is rewriting the context instead of reusing it, and the banner will already be saying so.
  9. Factory → Next actions. One list, one decision. If it says "no recorded blocker or triggered decision", the factory has nothing to ask you.
  10. When a number looks wrong, open "All metric values, formulas, samples and sources" on that tab and read the metric's own status, sample size, formula and evidence links before arguing with it.

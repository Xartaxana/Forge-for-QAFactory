Purpose

This page describes QA Factory version 0.10.2.

QA Factory is a ticket-driven functional testing factory. You give it one ticket; it takes the story from context and grounding through a plan, test cases, automation, quiet test runs and triage to a code-computed checks ledger, and to a report whose counts code computes. It installs as a Claude Code plugin and keeps all of its state in the repository it was onboarded into, under qa-factory/.

The first principle is the one this pilot started from and the code still enforces: analyse the existing protection before creating new tests. The factory reads the project's own frameworks, fixtures, clients, helpers and conventions and works inside them; it does not bring a new automation framework with it.

Where the principle is enforcedMechanism
Existing coverage is found before anything is plannedS1 — qa-scout gathers existing coverage into the context manifest together with the ticket, its parent, the tickets it names and the MR/diff cascade
A plan row says what happens to coverage that already existsS3 — every plan row carries a disposition, a reason and a reuse_decision; the plan also carries a recommended-regression list
A case is compared with existing cases before a new one is writtenS4 — qa-case-designer updates outdated cases first and then chooses extend, dedupe or new
Test code reuses before it inventsS5 — the embedding ladder: reuse, extend, parameterize, consolidate, and only then new; the automator records the shape it chose (shape, consolidates) after an execution-design step
Green evidence is not re-executedS6 reuses current S5 evidence and runs only what a source, test, runtime, environment or build fingerprint made stale
Regression stays the team's callRegression is recommended to the person and is never run by the factory

What the factory is and what it is not

It doesIt never does
Writes and runs tests in the test repository — Python / pytest / Playwright in this pilotNever modifies application code. A hook blocks the write (P-00, guard_pre_tool.py)
Files bugs as local files plus a proposal, and executes only the exact authorized action after a gateNever writes to Jira or a TMS directly, and never through a role. A merge request is opened only as a Draft, and only when gate B authorizes it
Runs tests through the authorized runner run_suite.py with typed requestsNever launches product-test commands outside that runner
Uses an environment you say is reachableNever deploys anything and never brings an environment up
Recommends a regression scopeNever runs regression itself
Covers functional testingCovers functional testing only
Calls a conductor when it has no move of its ownNever edits the plugin's own files, and never fixes a broken artifact itself: the role that wrote it does

Who it is for

QA engineers, developers and leads who want one story tested end to end without assembling the pipeline by hand each time, and who keep the decisions: what the story really means, which plan rows matter, which bugs are real, and whether the change is deliverable. The factory owns the process; the team owns the judgement.

How a story runs

You run the factory from Claude Code: you type a skill command, the story moves through its stages in that session, and the factory asks you only what a person decides. For each ticket you type /qa-factory:qa-story <TICKET>; the session takes the story from S0 to S9, dispatches the roles of each stage, records every stage, and stops for you at gate A, at gate B, at a halt and at the source review of S1. You answer in the chat, in your own words.

After a gate decision is recorded, the session stops with one line; continue with /qa-factory:qa-story and the same ticket. Nothing you already answered is asked again.

When the factory has no move of its own, its conductor offers you every move that lets the work continue, each with its price; in an interactive session the session itself plays the conductor. The conductor runs the move you choose with the factory's own commands and records a finding. It reworks nothing itself: a broken artifact goes back to the role that wrote it.

A story can also run without a chat; the page QA Factory — Architecture describes that headless run.

From git:

The marketplace in that repository is named qafactory; qa-factory is one of its plugins. To install from a local clone of the repository (its default branch):

bash

A local clone is installed as it lies on disk: the marketplace copies the directory, and .gitignore is a git rule, not a copy rule — anything a test run left inside the package is installed with it. Run python scripts/selftest.py --hygiene from the package root in the clone before installing — it names every file that is not package content; python scripts/install_smoke.py checks the other end of the same copy from the installed copy.

Updating an installed plugin needs the full cycle. Claude Code caches an installed plugin's files, and a plain re-install over the same version does not pick up a change:

bash

Never roll out a new version under a live story session. Replacing the plugin while a story is running swaps the skill, phase and script files out from under the session that is using them. Roll out between story sessions only. Uninstalling leaves <project>/qa-factory/ in place — it is yours.

After installing or updating, run /qa-factory:qa-doctor. It reports what is missing and the one thing to do next — normally /qa-factory:qa-onboarding.

The pipeline in ten lines

StageWhat happensRole
S0 PreflightResolves task paths, existing work, required capabilities and an immutable requirements snapshot; says in its first message if this story's bugs will not be filedcode only
S1 ContextGathers the ticket, its comments, its parent, the tickets it names, subtasks, the MR/diff cascade and existing coverage into a grounded context manifest. You review the sources the factory found and its decision on each; then one closed question per kind of source that is missing. A source the factory's own probe established it cannot reach is a gap line in the report, not a questionqa-scout
S2 UnderstandingBuilds the requirements register from every source with an observable and an impact column, runs the contradiction matrix, and the story's size is computed by code (sizing.py)qa-requirements-tester
S3 PlanRisk-based plan: a disposition and a reason on every row, a budget against the size cap, and a recommended-regression listqa-test-strategist
S4 CasesAtomic Given-When-Then cases against existing coverage; the critic independently reviews the rows marked design_review_required (mandatory for critical depth, unknown impact, unknown oracle or a source conflict; the strategist may add more)qa-case-designer, qa-case-critic
GATE AOne message, after the gate has been rehearsed: the plan and the casesthe person
S5 AutomationTest code by the embedding ladder; a deterministic exit check (s5_precheck.py) before the critic, which reviews meaning and performs one isolated red probe for every new or changed test, except a red test that a contradicts_requirement row of the manifest explains: that test takes no probe, and its window closes by code with that row. When a window's repair limit is spent, the factory shows you what is still unresolved and waits for your decisionqa-automator, qa-code-critic
S6 RunExecutes only outstanding current-scope checks and agent-manual work; current green evidence is never repeatedcode + qa-runner
S7 TriageEvery failure gets a verdict from a closed vocabulary with evidence; FLAKY only after three isolated reruns with a named mechanism. When a test's repair limit is spent, the factory shows you what is still unresolved and waits for your decisionqa-failure-analyst
S8 ResultsThe checks ledger and the delivery verdict are computed by code, then written into one human test reportqa-doc-scribe
GATE BOne message: the ledger first, then the delivery verdict, one of three words with its reasons, then the bug list and what is still open before the MRthe person
S9 RetroNumbers computed by code; qa-retro-analyst always writes the prose over them (numbers / skip only on the person's own words) and folds what outlives the story into the project's documentsqa-retro-analyst

When the story has an implementation diff, S3 runs in two windows: in the first the test planner labels the diff against the requirements and fills work/grounding.yaml (the grounding table and the blast radius, both built by code); code checks that the table is complete (every changed hunk is labelled) before the second window, in which it writes the plan. Still planned: a check that the plan answers every risk and area of the table, and the lines that show the person the refactoring share and the requirement coverage before the first test.

What you are asked, and what you are never asked

Gate A and gate B are the planned decisions; the factory also asks you when it reviews the story's sources, when a role cannot go on without a decision, and once at the end for the retro. Every question the factory asks you is a closed question: each answer is followed by what it costs the factory, what it costs you, and what it does to the story.

AskedNever asked
Gate A: is the understanding right, is the size right, is the plan approved or edited row by row, and what to do with every requirement that has no counterpart in the code. Approval is its own word: answer with approve, then answer what is listed under it by name. Words that ask for a change are not recorded as an approval: the stage goes back to the role that wrote it, with your words, and the gate is asked againAnything the factory could compute itself — the gate is rehearsed first, and after the answer nothing is asked or refused that could have been computed before it
Gate B: which bugs to file, whether to open the MR, whether to publish cases, what stays open. You approve with approve again, with your bug numbers and stand-gap lines under it; words that ask for a change send the stage back to its roleTo fix the factory's own state. An inconsistency in its bookkeeping is repaired by code (recover) or stated as one line with owner: factory — never handed over as an errand, and never as “edit the plugin” or “ask the maintainers”
The source review at S1: every source found, with the factory's decision on each. Then, per kind of source still missing, one closed question: not needed, skip all like these (it covers every later gap of that kind), a route, or the content pasted inWhat the factory's own probe established it cannot reach: a gap line in the report, no question. The same applies to a kind of gap you already answered
A stand gap: a card with the exact fix by name and four answers, written as <case id>: change, myself, run or accept — the factory changes it on your word, you change it, you run those cases where it exists, or you accept it. A credential is named, never printedTo add keys the factory listed but nobody needs: onboarding writes only the keys the env file holds and proves them by one real login; a missing key names who needs it and blocks nothing

A changed ticket: on a resumed story, or when a gate answer arrives, and the last check is older than six hours, you choose the new text, the old text, or stopA question already answered. A recorded gate decision is never re-asked, not even for confirmation

Delivery: three outcomes

Delivery has three outcomes: ready to ship, ready once you finish the checks left with you, and not ready to ship as is. The report says it in one line, yes, after_checks or no, and gate B shows it right after the ledger.

WordThe report saysWhat it covers
yesVerdict: ready to ship.Everything is checked: no bug, no gap and nothing left with you
after_checksVerdict: ready once you finish the checks left with you.The factory found no bug and no gap, but part of the testing is left to you or to another environment: a handed test, a manual case, an accepted stand gap, a deferral you worded, a test the code critic could not verify, an unconfirmed expectation, a Then that waits behind another case's red check in the same test, a test that was changed after its run
noVerdict: not ready to ship as is.A bug or a gap was found, or a requirement was not proven. A failure always outranks a hand-off

The report section “Left with you” names each item left to you, how to check it, and the regression scope the plan recommends. The verdict is decided from typed records, never from the text of a reason, and a kind the factory does not know counts as not ready. The guard opens delivery on yes and after_checks; “deliver anyway” with a stated reason is recorded; a merge request is only a Draft.

Design principles

  • The person hears one sentence, or a question they decide. Everything else is a file.
  • A check stops a silent pass, never an informed one. Your word passes any block, and the pass is recorded with your words. A pass over a block the factory owns is also filed as a finding about the factory. Even a ban has a door.
  • The factory proves what it claims about its own state — a dispatch nobody is doing is proved, not guessed; absence of a record proves nothing.
  • A gate is the last stop before its next stage. Everything the approval unlocks is rehearsed before the person is addressed.
  • Nothing is generated before an explicit “yes” (onboarding), and nothing is delivered before a recorded gate decision (story).
  • Code computes, roles judge, the session moves the story. Ledgers, sizes, scopes, verdict roll-calls and costs are code; the session that moves the story never writes a case, a test, a verdict or a brief. The conductor is called only when there is no move.
  • Requirements, not a checklist. The factory works by requirements: acceptance criteria are one source of requirements, and a ticket may have none.
  • Code is never an oracle. An expected value comes from the requirements; where they are silent, the factory asks you, showing how it was before the change and how it is now.
  • Models. The factory's roles run on Sonnet or Terra, never on Haiku.
  • Enforcement is in hooks, not in a role's discretion — the application-path and secret guard, the stage guard, artifact validators and detectors, the exit gate, and cost capture.
  • Discovery before questions, and a deferral requires a question that was actually asked.
  • One fact, one owner. Every finding, reason and capability names who it belongs to: user, factory, environment, product or review.

Where things stand

The reference run of TP1-13797 on 13.10.2026 went from S0 to S9 through both gates and closed with the verdict not ready to ship as is, because one requirement was not proven. Its price was higher than the earlier run of the same story, mostly because of the conductor and repeated resumes in automation; this page quotes no amounts, because prices are described as rules and words (see the dashboard page).

Per-story outcomes belong to the projects and their trackers, not to this page. What is queued is on the roadmap page.

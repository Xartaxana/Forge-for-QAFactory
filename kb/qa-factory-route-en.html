    Onboarding and Doctor — their forks

    qa-onboarding

    • Discovery by reading only: framework, layers, run commands, CI, conventions, repositories.
    • Interview in batches of at most four questions, only on discovery's gaps.
    • person The tracker is read only by direct API; an assistant is offered only as a write channel.
    • person The bug channel closes only with confirmed write access: an assistant with write · an API token · knowingly "local only".
    • person Environments and accounts per role; where credentials are kept.
    • person Summary gate: config and strategy are written only after an explicit "yes".
    • Re-run after major changes to tests, environments, or conventions.

    qa-doctor

    • Install smoke test → capability readiness with owners (tracker_write: confirmed · no · not checked) → audit → every story's state → exactly one next action.
    • repairs Stage running, no work → recover, if you said no one is working on it.
    • person A dispatch no one will finish → release by your word, never by time.
    • A protective guard refusal repeated → "guard defect, owner: factory", no attempt to work around it.
    • person A story with no movement for 14 days → an offer to archive it; with open items — only with your note.
    • The doctor does not debug the factory and does not edit artifacts; anything recover/release does not fix is named with an owner.

    What is not on this map

    Recorded for the next version: a single "critical / not critical" criterion for asking again (today it is a rule inside the skill); the same answer logic for the S1 stop is written but not verified by a live run; reading the tracker through an assistant has been removed, and projects that were onboarded earlier need onboarding again to switch to the direct API. The factory does not write component tests in the UI repository — an owner decision.

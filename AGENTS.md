# CLAUDE.md — QA Factory development

Auto-loaded into every session and every worker: only what every reader applies — the dispatch form (rule 11), command
hygiene, worker duties, language. A worker's own rules are `.claude/agents/<role>.md` and its dispatch. The

## Worker duties

- A self-activating
   enforcement file (a hook on the active hooks path, etc.) is never placed on its live path by builder: builder hands
   it over as content or under a neighbouring filename, and Lead puts it on the real path at acceptance
   (enforcement-file review rule) — otherwise unreviewed code gates work ahead of its own review.

- A worker trims run output before it enters its context (`-q`, a 30-line tail, `Read` with a limit over 400 lines, `Grep` instead of reading a whole file) and closes a round with ONE witness run after all edits, never one after each edit (D-0035).

## The dispatch form (rule 11)

### Rule 11 · DoD in every dispatch

11. DoD in every dispatch (DoD-in-every-dispatch rule): delegating to ANY tier states what "done" means, and how
   acceptance will check it, in a form suited to that tier. builder: acceptance criteria + a verification run whose
   output becomes the witness, AND the spec NAMES ITS EDGE BEHAVIOR: for every limit/truncation it introduces, every
   empty/absent/None input its data can carry, and every pair of its own requirements that can conflict, the
   expected behavior is stated — or the fork is returned as an explicit question; a spec silent on an edge that its
   own requirements create is a dispatcher defect, not a guess left to the performer. Two sub-classes are dispatcher
   defects when silent: (i) TEMPORAL — an artifact the change itself brings into existence (a config, file or flag
   absent at spec time, present after): the behavior is stated for BOTH worlds, and the spec says which move creates
   it; (ii) POSITIONAL — when the spec prescribes WHERE in existing logic a branch goes (order, precedence,
   before/after which check), it states the INVARIANT that position must preserve (what stays unreachable, what must
   still be refused), not the location alone.

### Rule 11 · which tests a DoD asks for

   Which tests a DoD asks for: the rule text is `docs/TESTING.md` (three layers, one parameterised test per behaviour;
   tests outside them QUARANTINED in `test-layers.json`; SCOPE CEILING: that text, nothing more). Input from OUTSIDE
   (a CLI/UI that accepts user input, a ticket, a person's words, a project config, a host answer) gets an
   adversarial mini-battery — magnitude, nesting, encoding, empty/broken input — and every limit applied to it a
   case AT and BEYOND it, each a scenario variant row; an internal boundary gets no test. When the SessionStart line
   says `TEST QUARANTINE ALERT` or `READY TO DELETE`, the Lead tells the owner the same turn (detectors: check 33,
   `tools/test_quarantine.py check` in the nightly CI job
   `quarantine-check`).

### Rule 11 · scout and critic DoD; the manifest; the five-point checklist

   scout: an explicit question and a completeness criterion; "X is nowhere to be found" is a valid outcome and
   requires a trail. critic: the dispatch attaches the spec/DoD of the work under review — otherwise only general
   quality is checkable, not fit to the task. A dispatch with no DoD is returned by the worker as questions, before
   work starts. Alongside the DoD a dispatch carries a CONTEXT MANIFEST (dispatch-context-manifest rule): "given" —
   the files/data injected into the worker (its sufficiency is the Lead's responsibility); a WRITING dispatch also
   carries "owns" (the paths it may write), "non-goals" and "handoff" (what comes back for acceptance); a parallel
   fan-out declares ownership per COORDINATOR.md rule 4 plus an optional maxConcurrent cap. The manifest is DECLARATIVE on reads and
   NORMATIVE on writes: the worker reads the repo freely, and going past the basket is a report line "needed beyond
   the manifest", not a violation; for a targeted read-only dispatch the manifest is the explicit enumeration of what
   is attached. A writing/parallel dispatch with no manifest is returned as questions too. Completeness of the DoD
   and the manifest is the DISPATCHER's duty BEFORE sending, run as a FIVE-POINT CHECKLIST against every dispatch:
   (1) an explicit question / completeness criterion or acceptance keys; (2) the DoD inline (below)
   AND the edge behaviors NAMED — limits/truncations, empty/absent inputs, conflicting requirement pairs: stated, or
   explicitly forked up; (3) "given" enumerated AND sufficient — data, fixtures, paths NAMED, not implied; (4) a
   writing dispatch: owns/non-goals/handoff present and its witness scope named (COORDINATOR.md rule 4); (5) freshness — the spec's
   load-bearing facts checked against their carrier, not memory. A checklist miss exposed by a reject or a finding
   is a spec defect of the dispatcher (a calibration case); promotion to a machine layer follows the next recurrence.

### Rule 11 · inline DoD; the DOC-DISPATCH witness

   The DoD is written INLINE in the dispatch — named acceptance criteria plus the exact verification run; a bare
   pointer to a spec file or an earlier event is NOT a DoD. A brief carries FACTS by pointer: `given:` names the frozen
   file (a hand-back report, a digest) and the digest's objects by their exact ids (`q2a, q2b`), never by a prefix, so a
   scout's reservation travels with its object; changing code is pointed at by `path::symbol`, not a line range. The
   DoD, the edges and the non-goals stay inline. Prose outside the manifest is at most about 8 counted lines (a target
   read by calibration check 34, not a gate). DOC-DISPATCH WITNESS: when the owns are markdown/config
   with no test set of their own, a deterministic key-presence run is a legal mechanical layer ONLY with three
   properties: (i) the keys are quoted VERBATIM from the DoD as written BEFORE the run; (ii) the script is attached in
   FULL source with the witness in the report, never committed as a test; (iii) the run includes a NEGATIVE control
   (one key deliberately absent → the script reports failure). Missing any of the three → the witness is a
   retelling, not a run (detector: calibration check 13(k)). A worker returning a DoD-less or manifest-less dispatch
   is an emergency net, not the normal cycle: frequent returns are a coordinator defect, flagged at calibration.
   Lead-tier tasks are covered by their own mechanisms (the Lead exam, weekly calibration).

   | R11 | when | duty |
   |---|---|---|
   | m | a WRITING dispatch's "given" manifest | executed as a MARKED declaration: an inline enumeration, OR a pointer to a persisted spec that itself carries the enumeration, ONE hop away — no marker, no manifest; `owns` itself is always given INLINE, never by pointer |
   | f | a dispatch to builder, or any dispatch whose `owns:` holds an absolute path (D-0022) | carries its manifest as HEADER LINES outside fences and quotes: `given:`, `owns:` (absolute paths, on that line or right under it, no blank line, no heading marks; a path with spaces in backticks), `non-goals:`, `handoff:`, `edges:`, `DoD:` (the verification command in backticks), `siblings:` (entries, or `none -- <why>`) and, over COORDINATOR.md rule 2's threshold, `designer:` (the accepted draft's absolute path, `skip -- <reason>`, or `resubmission <task_id>`); `python -B tools/dispatch_new.py` prints these lines checked (never typed by hand); `tools/dispatch_manifest.py` refuses a dispatch without them and names what is missing; the informed pass is a line `manifest-skip: <item>[, <item>] -- <reason>` |
   | h | critic/designer dispatch | report path on `handoff:`, never `owns:`; `tools/dispatch_gate.py` refuses a dispatch whose `handoff:` names no single `.md` file in the role's folder; `tools/handoff_gate.py` lets it write only that file; a designer dispatch also carries `facts:` (COORDINATOR.md rule 2) |

## Command hygiene (permission hygiene)

The deployment runs in auto mode; three behaviours are refused by `tools/hygiene_gate.py`, every other form is allowed.
Doors: `git -C <dir> <cmd>`, `python -B <abs path>`, a Bash `( cd <dir> && ... )` subshell, a PowerShell
child shell, a byte copy (`cp`/`Copy-Item`) and its restore.

1. Tests — the canonical form, from the repo root: `python -m pytest tools/ -q` or a narrower target; locally only
   the narrow target the work needs; the full sets run on CI, never on this machine (PROJECT.md, package change p. 2);
   the canonical form of a tool = its correctly invoked form, the invocation that finds a known sample.
2. The proxy server — not used in this deployment: the contour is subscription and nothing in gateway/ is run.
3. The shell's working directory never moves (`cd`, `Set-Location`): refused.
- **Рабочий каталог шелла не меняется никогда** — ни `cd` в Bash, ни `Set-Location, Push-Location` и `cd` в PowerShell, даже
  «внутри одной команды» (каталог PowerShell переживает вызовы). Хуки запускают `python tools/...` относительно cwd: после смены
  они не находят `tools/*.py`, блокируются ВСЕ инструменты, и сессия сама себя не вернёт.
  Вместо этого — `git -C <каталог>`, `python -B <абсолютный путь>`, флаги `--repo`/`--root`; тесты пакета, которым нужен каталог
  пакета как cwd, идут у билдера в его worktree. Хук «не нашёл tools/x.py» — стоп и сброс папки сессии на корень.

4. File edits — by any tool (the owner's word 16.11.2026: the Edit/Write-only rule is retired); a worker still writes
   only inside its `owns`, judged by the diff at acceptance.

5. Log entries — through `tools/journal_write.py` only (the owner's word 14.11.2026): a redirect, tee, in-place editor
   or payload that writes `logs/journal/*.jsonl` or `logs/routing-log.jsonl` is refused; an Edit/Write of them draws a
   WARN until node B23-S makes it a refusal.

### Command hygiene · point 6 — a claim needs a measurement

6. An environment-negative claim requires verification: empty output or "command not found" from an INCORRECTLY
   invoked tool is a miscall, not proof the object is absent; a negative claim about the environment ("the
   service/key/file is missing") is valid only after a positive check using the canonical form (point 1). Not just
   negatives — ANY load-bearing claim about environment state (a quota, a time window, a resource's presence,
   "already ready/open") in a report to the operator or in a plan is valid only after verification by measurement (the
   canonical command / an external clock / a database / a provider); an unverified claim carries an explicit
   "estimate, not verified" label. Worker claims are covered by witness/trail; this point closes the gap for Lead
   itself. The same class covers ANY content search (grep/glob/script) over the repo: an empty result is reportable
   only after a positive control of the invocation — the same tool and syntax must find a sample known to exist. The
   control shares the SHAPE of the checked call (case profile, type/glob filters): a control with a different pattern
   proves the pipe, not the absence (shell-grep alternation needs -E; -P needs a UTF-8 locale; the Grep tool is
   case-sensitive by default — a content-negative claim requires a case-insensitive search). Same class — the STATUS
   of a registry entry (escalations, decisions, tasks, ledgers): a claim about it is valid only after reading THROUGH
   that entry's status line, or grepping the status field itself; the entry merely appearing inside a read window is
   NOT a check — append-only registries put the verdict at the END of a multi-section entry.

   | pt.6 | when | duty |
   |---|---|---|
   | a | a project decision rests on an UNKNOWN property of the environment | run ONE experiment first; building machinery instead of measuring is legitimate only when the measurement itself doesn't port (e.g. a port number) or the experiment would be destructive |
   | b | a measured number appears in a norm/report | it carries its counting carrier (file/command) alongside it, or it isn't written at all; a comparison stays inside ONE metric |
   | c | a character-level claim (a slash, a case, a specific symbol) | valid ONLY by reading the carrier directly (the Read tool); a search tool's output is not a basis for it |

### Command hygiene · point 7 — probes

7. Temporary corruption (a probe) is rolled back by a BYTE COPY, never by `git checkout` /
   `git restore`: (a) take the copy BEFORE corrupting, and restore FROM IT; (b) the gate refuses these on a dirty
   path whatever its status was before, so the byte copy is the only road for a probe; (c) the
   witness is the VERBATIM comparison (a hash or a diff), not "restored"; (d) a live artifact (a ledger, a
   registry) is not corrupted at ALL when a pure function's verdict proves the point: corrupt a COPY.

## Tiers (see DELEGATION_TABLE.md; all assignments are estimates until calibrated)

- **architect** (Fable) — ABOVE Lead: the owner's new ideas (PROJECT.md, steps 1–4), process questions the Lead

  checklist is `PROCESS/ARCHITECT_START.md`.

## Routing rules

### Rule 1 · recon → scout

1. Recon → scout by default: the answer requires more than 1–2 already-known files, OR any search across the repo.
   Lead reads a file itself only when it is a single, precisely known target; up to ~4 known targets are legal ONLY
   with a `dispatch_skipped` event (reason mandatory) — skipping the dispatch silently is a violation. Recon of
   unknown scope is always scout. A survey of an EXTERNAL repo for "what should we adopt" is two-pass (two-pass
   external-repo review rule): scout maps it; a mechanism enters the plan/queue only after Lead's own targeted second
   pass over the promising spots, whose trail goes into `docs/RELATED_WORK.md` (Lead-tier work, no
   `dispatch_skipped`; detector: calibration check 16). Accepting a digest goes by its trail (trail-based acceptance
   rule): scout attaches where it searched and what it read; a digest with no trail → `rejected`.

   | R1 | when | duty |
   |---|---|---|
   | a | — | not used here: no scout exam set is registered, so the lifted form of acceptance never applies |
   | b | every accepted digest | Lead checks coverage of the question and spot-verifies at least one load-bearing claim; verifying a negative claim ("X is nowhere to be found") is mandatory; the check is noted in the `accepted` event |

### Rule 2 · implementation → builder; acceptance by witness

2. Implementation from a finished spec → builder. Lead writes the spec; builder returns missing requirements as
   questions rather than inventing them. Accepting a builder diff goes by witness (witness rule): the `accepted` event
   carries in its `witness` field the actual output of the verification run (command + result), not a paraphrase; a
   report with no witness → `rejected`. A task with a UI result: the verification run includes DRIVING the UI; the
   witness is a before/after screenshot or recording — a purely textual witness is insufficient
   (enforcement-file review rule: CLAUDE.md § Worker duties).

### Rule 2 · drafting → designer

   DRAFTING → designer BY DEFAULT: a WRITING dispatch whose spec carries 3 OR MORE numbered items, OR touches 3 or
   more files (counted by `dispatch_manifest.designer_threshold`), is DRAFTED by the designer from a Lead intent brief (the draft's form, edge invariants and the error
   direction of a reused function included: `.claude/agents/designer.md` rule 1); the Lead self-drafting it anyway
   is legal ONLY with a `dispatch_skipped` event (agent = designer, reason mandatory). The motive is
   CONTEXT ISOLATION — an independent drafting context, not model price — so the event is owed whatever the tiers
   of designer and Lead. Below the threshold, and for intent briefs themselves, the Lead drafts freely with no event.
   The threshold counts the task's PRIMARY draft. A RESUBMISSION after a `rejected` — a retry under the SAME task_id —
   is a CONTINUATION of the existing spec: the Lead edits it ITSELF, with no designer dispatch and no
   `dispatch_skipped` event. Work re-badged under a NEW task_id is a NEW task and the threshold applies to it; parts
   produced after a `decomposable` event take new task_ids and each is judged against the threshold on its own.

   Before a designer dispatch the Lead MEASURES the brief's load-bearing facts by code (the owner's word 17.11.2026).
   A load-bearing fact is any claim about the CURRENT repo or data that a requirement, an edge or a reader list rests
   on: a file, function, constant, field, CLI flag or hook that exists, and its shape or value; a count (readers,
   hits, sizes, lines); a test pin or anchor text; a data premise (PROJECT.md p.6(а)). Each fact goes into the
   dispatch as a `facts:` header block, one line each: `<claim> | <command> | <verbatim result, at most 200 chars>`.
   When the brief rests on none, the block is `facts: none -- <why>`. Opinions, intent and the owner's words are not
   facts: they go in the brief.

### Rule 3 · the critic gate

3. critic — a MANDATORY acceptance gate: builder diffs over roughly 100 lines, or touching the data schema / core /
   money accounting; unclear bugs — BEFORE Lead starts debugging them itself. The first filter on EVERY diff is the
   executor's own self-run against its DoD (rule 11); critic does not substitute for it. Every diff gate also answers
   DUPLICATION and CODE QUALITY: the rule text is `.claude/agents/critic.md` rule 22, Q6-Q7 (its rule 18 points there); the clone ratchet is the deterministic layer. Acceptance still rests with Lead (flat
   delegation rule). Small diffs: a "critic: skipped, <reason>" note inside the `accepted` event is a waiver available
   ONLY to an acceptor whose tier is above the executor's. TWO-LAYER CRITIC ENTRY (two-layer review rule): a
   MECHANICAL layer — test re-runs, control values, smoke matrices — is executed by the submitting builder or a script
   and attached to critic as VERBATIM output BEFORE the verdict; critic's own zone is the VERDICT layer (architecture,
   semantics, class-wide completeness); a cheap control re-run of what is attached is legitimate, investigating the
   mechanics by reading is not; a layer not attached → critic asks the dispatcher for it and does not execute it.
   Money/numeric diffs: critic starts with EMPIRICS — control-value runs; code reading follows only on divergence or
   where no deterministic check exists. Critic-on-plan: a plan or recon deliverable that will itself serve as the SPEC
   for more than roughly 30 minutes of work gets a critic review of the PLAN before any code starts when it carries
   forks or a schema/money change; regardless of size, in PROJECT.md's mandatory cases (a new idea of the owner —
   step 6; a spec edit that changes a meaning — package change, item 6); otherwise `critic: skipped, <reason>`. That
   review checks the plan's facts by trail; feasibility is an architectural judgment that no other gate reviews.

### Rule 4 · parallel parts

4. Independent parts → several parallel subagents, each with its own spec (context isolation). Parallel specs declare
   the paths they own; Lead checks for overlap before launching (the writer cap and the full queue: Cost gates, rule
   12). Parallel SESSIONS in the same repo are the same hazard: don't touch or commit another session's uncommitted
   paths (no-silent-reuse rule). A cross-deployment queue item exists only if it is written, in the same move, into a
   carrier the TARGET reads at boot; a session's own journal notes or findings log are not such a carrier.

### Rule 4 · witness scope and the BATCH CANON

   SCOPE OF THE WITNESS RUN: for every writing node, solo or parallel, the verification run is what
   `python -B ai-packages/qa-factory/scripts/tests/scenario_walk.py --witness-for <owns>` prints
   (`docs/TESTING.md` «Что запускать по своей правке»; an owned path outside the package, where that command has no row: the test file that
   judges the path, named in the DoD) — never its big neighbours, never a quarantined file, and not merely the files
   the worker judges to be its own; another worker's uncommitted state can break a shared full run. The full sets are
   the BATCH CANON: the CI pipeline on the batch branch after the branches converge, never a run on this machine
   (D-0056, D-0059; procedure `docs/RUNBOOK.md` §7) — the coordinator's duty. Its output is APPENDED to the `witness`
   field of the batch's LAST `accepted` event: first the node's own narrowed run, then the canon output labelled BATCH
   CANON; the canon never replaces the node's own proof. A node is accepted on its own narrowed witness; a canon
   failure found after convergence is a `defect_found` against the responsible node (reopening a closed task is
   forbidden).

### Rule 4a · a task DAG; team work

   4a. A task spanning 5 or more journal events, OR 2 or more sessions, is tracked as a markdown DAG — a pile's batch
   file or a file under docs/tasks/: nodes/statuses/tiers as the carrier; a WRITING node also declares the paths it
   owns; a node's status moves in the same turn as its journal event, not separately.
   Team work in piles and batches: the rule text is PROJECT.md «Командная работа» (D-0036; detector: check 33).

### Rule 5 · flat delegation

5. Flat delegation (flat delegation rule): subagents do not launch subagents. A task that turns out to be decomposable
   is returned to Lead via a `decomposable` event.

### Rule 6 · escalation

6. Escalation: 2 failed attempts, or an explicit "this is beyond my level" signal → escalate one tier up + an
   `escalated` event; a silent retry on the same tier is forbidden. A failed attempt = a result REJECTED at
   acceptance; every rejection is a `rejected` event (agent = the worker; fields: the `rejected` row of the Routing
   log; reason in notes). Two `rejected` events with the same task_id on the same tier make escalation mandatory. The
   attempt counter is an operational proxy for the cost crossover; the crossover itself is measured by the weekly
   calibration (Update Rule 4).

## Routing log — logs/journal/<dev>.jsonl

One journal file per developer: `<dev>` is the `developer:` slug of the untracked `tools/dev.config.yaml`
(`python tools/journal_keys.py where` names the file). One JSON line per event, written by the one writer
`python -B tools/journal_write.py <event> …` (the machine lock, the clock, the validator BEFORE the write; the owner's
word 14.11.2026): the Task/Agent PostToolUse hook writes `delegated` (and the owed designer `dispatch_skipped`) and the
SubagentStop gate writes `returned` by themselves; the coordinator writes `accepted`, `rejected` and the rest with one
call (`accept --run "<cmd>"` runs the verification under bash and stores its verbatim tail as the witness):

```json
{"ts":"2026-11-11T12:00:00","event":"delegated","agent":"builder","model":"sonnet","task_id":"t-042","category":"implementation","worker_ref":"agent:<id>","feature":"F19","notes":"brief: what was delegated"}
```

The journal is append-only and records ACCOMPLISHED FACTS, not intentions: `delegated` is written by the hook AFTER
the launch returns (a hook line `JOURNAL: … NOT written` is repaired the same turn with the CLI), `escalated` after
the dispatch call returns, same turn; a new `delegated` carries a `worker_ref` — a non-empty handle of the launch (a
background-task id, a job id, `cli:<ts>`, `retro:<...>`) that exists only after launch. Open dispatches are
reconciled at both session boundaries — the SessionStart hook and the session-handoff check — worker alive / result
pending / phantom; a phantom is closed by a bare `closes:<task-id>` token (several allowed in one `notes`) in the
`notes` of any LATER event; the open-dispatch scan reads ONLY this literal token — a prose-only closing note leaves
the task open. An already written order defect (id out of order, non-monotone `ts`, repeated `delegated`) is
declared, never rewritten: a bare `order-known:<ts>` (that line's exact `ts`) in the `notes` of a LATER line of the
same file (validator rule 19; check 13(m)). A task id is read by its IDENTITY `<id>@<label>`, and another clone's journal lines are form-checked
at the merge: the rules are `tools/journal_keys.py` and `tools/journal_validator.py --merge-parent`, whose refusal
names the door.

Every event line — `journal_created` and `lead_degraded` included — carries five base fields checked by
`tools/journal_validator.py`: `ts`, `event`, `agent`, `category` and a non-empty `notes`. `ts` is ISO local time
with NO timezone suffix (a trailing `Z` fails the gate). `lead_degraded`'s `reason`/`scope` are legal extras; they
do not replace `notes`.

Typed fields (typed-fields rule: load-bearing facts go in fields, notes are a human-readable extra): each event's
fields are in the SHAPES table below, and every new event also carries `feature: Fnn` — the factory feature it
belongs to, from `plans/features.json` (`journal_validator` WARNs on a missing or unknown id for events from
2026-10-02; `tools/forge_metrics.py` attributes by it first and by tag/files/words only when it is absent;
unclassified work is a Forge metric, not an error). Old events are never rewritten. A task id is issued by
`journal_write.py next` (or by the writer when no id is given) under the machine lock, from the clone's counter in the
git common directory, shared by every session and worktree of the clone; ids may skip and land out of order, never
repeat (validator rule 9a: never seen, at most 1000 above its letter's max). An id carries the clone's LETTER — none
for the first clone of a developer, `a`, `b`, … for the next ones (`logs/journal-letters.json`, `journal_write.py clone
--claim`; the owner's word 14.11.2026 «Номер 123 и 123А», written in lower case ASCII: `t-123`, `t-123a`). Bands
(`id_band`) are retired for new lines and still read in old ones; `journal_keys.py declare` repairs only collisions
already in history. A collision noticed later is not rewritten — it gets a note on the next event and counts as two
tasks (no-silent-reuse rule). `ts` is read from the system clock by the writer, never taken from the session's
narrative; a wrong `ts` noticed later gets a note on the next event (the reference: usage reports / git log,
calibration check 13(f)). A MISSED event noticed later is repaired by a RETRO pair: append
`delegated`/`accepted` NOW, with the current `ts`, a "retroactive" mark and the event's actual boundaries in
`notes`; inserting lines into the past is forbidden; calibration watches the retro stream.

## Role ≠ tier

Three definitions that are NOT synonyms:

- The TIER of a session = the FUNCTION RANK of its ACTUAL model (verified at entry — tier-verification-at-entry
  rule): the highest function bound to that model in `delegation.config.yaml`, by exact id or by family
  (`tools/tier_ladder.py`). Opus and Fable are a MODEL NAME each; "Lead" and "architect" are tier-FUNCTIONS
  (decomposition, specs, acceptance, mechanisms; ideas, process, calibration), not roles in the conversation.
- The coordinator ROLE = ROUTING, not execution. Any model leading the dialogue with the operator carries it, from
  any tier, and it does NOT make the session a Lead. The coordinator DISTRIBUTES work across tiers (recon → scout,
  implementation → builder, review → critic, Lead-class work → Lead or its queue) and ESCALATES UPWARD everything
  that, per the matrix below, needs a tier above its own — rather than doing it itself.
- Full Lead = a coordinator whose rank is lead or above (the model bound to Lead, or the architect's model doing
  Lead work); only it changes mechanisms, the decision log, table statuses and gates.

Acceptance is only from ABOVE: `accepted` is legitimate when the acceptor's rank is strictly above the executor's
function rank, OR the decision carries input from a tier above (a critic verdict), OR acceptance is explicitly queued
for the full Lead (a note in notes). Acceptance by an equal/higher tier without that input is the session
self-certifying (self-certification violation class). An acceptance is never written from inside a worker: a critic
or designer verdict reaches the coordinator through the worker's handoff file. Matrix by the coordinator's actual
function rank:

- **architect rank** (the model bound to architect; Fable) — unrestricted; it may do any Lead work with no extra
  event (the `model` field of its journal lines records it). Routine coordination and each mechanism commit are the
  Lead's work, not its own.
- **lead rank** (the model bound to Lead; Opus) — full Lead: coordination, dispatches, acceptance of scout, builder,
  critic and designer work, the "critic: skipped" waiver over builder, mechanism commits after the critic (`tier:
  opus`), `DECISIONS.md`, statuses. Architect-class questions go by rule 6; a `Last calibration` line carrying
  `-- overdue:` → tell the owner once per session and put one item into `docs/tasks/architect-queue.md` if none is open.
- **builder rank** (the model bound to builder; a Sonnet coordinator) — coordination, dispatches; accepts scout; a
  builder diff — ONLY with critic input (the skip waiver is unavailable); critic and designer work — `basis:
  queued-to-lead`, cleared later by a Lead-ranked session writing a second `accepted` of the same task with no
  basis (calibration check 6 (iii) lists the uncleared); Lead-class work — `docs/tasks/lead-queue.md`.
- Below builder rank, coordination is not supported.

The tier names resolve through `delegation.config.yaml`. The standard mode — the owner coordinates on the Lead's
model and switches the session to the architect's model for architect work; a session on a model below lead (the mid-tier mode) is the
same matrix, and degradation (below) is an unplanned entry into it.

## Lead degradation

A refusal by the Lead's model (safety/dual-use, subscription limit, unavailability) OR an explicit operator switch
to a model ranked below lead:

1. Drop to builder rank (Sonnet) + a `lead_degraded` event (reason, scope) — ONE step. An outage of the Lead's model
   removes critic and designer with it: builder diffs finished meanwhile WAIT — one line each in
   `docs/tasks/lead-queue.md` («ждёт критика: <task_id>, <ветка>») and no `accepted`; critic and designer dispatches
   are not launched (the stand-in of rule 6 is legal when the wait hurts); recon and builder work under accepted
   specs continue.
2. While degraded: coordination and already-authorized tasks — yes; table statuses, gates — no; new decision-log
   entries are queued for the full Lead; acceptance per Role ≠ tier.
3. Default return at the task/session boundary: `lead_restored` + acceptance of the degraded window (log + diffs of
   the window) in the event's notes; an empty window is noted explicitly; clearing the queue does not substitute for
   this acceptance. Degradation spanning a session boundary is recorded as the journal's last event.
4. Tier verification at BOTH points (tier-verification-at-entry rule) — neither alone is sufficient: entry is skipped
   by self-detection while degraded, and there may be no rise back at all.
   a) ENTRY — before the FIRST Lead action of a session (dispatch, acceptance, a mechanism commit, a status change):
   check your own model by the last visible signal (the SessionStart `MODEL:` line; a switch command) against the
   lead binding; if its rank is below lead and the journal has not opened a window → `lead_degraded` BEFORE the
   action. A model that matches no binding and no known family never reads as Lead.
   b) EXIT — a visible rise from below lead to lead or architect rank is itself PROOF a window existed, independent
   of the journal: in the same turn, a retroactive `lead_degraded` (note + actual boundaries), acceptance of the
   window per point 3, `lead_restored`. A switch between the Lead's and the architect's model is NOT a window: no
   event.
   c) EXTERNAL CROSS-CHECK — check 5 of PROCESS/WEEKLY_CALIBRATION_PROTOCOL.md: the actual model of Lead sessions
   per transcripts vs. window coverage by matched event pairs; it catches failures of both in-session checkpoints,
   including a session that died while degraded.

## Как принимается изменение пакета

### Пакет: проход и свидетель

1. **Проход по правилам фабрики.** Дифф в `ai-packages/qa-factory/` проходит FR только по
   затронутым разделам `factory-rules.md` (A отказы, B текст человеку, C контракты, D идентичность,
   E сдача, F измерения, G код). Неприменимый раздел — одна строка («B — текст человеку не
   менялся»); применимое правило — одна строка факта. Проход пишет билдер в отчёте, критик
   проверяет ответы и выборочно — отрицательные утверждения. Правки `plans/`, `docs/`, `kb/`,
   `experiments/` проходят без FR. Задача билдеру, которая пишет в `ai-packages/qa-factory/`, несёт
   в «given» `design/factory-rules.md` целиком (правила билдера — его файл роли): короткий индекс правил
   (`docs/FACTORY_RULES_INDEX.md`, читает координатор, строка `COORDINATOR RULES:`) — напоминание координатору, а не
   замена текста правил для того, кто пишет код. Задача критику (дифф или план), которая трогает `ai-packages/qa-factory/`,
   несёт в «given» `design/architecture.md` и `design/factory-rules.md`: индексы в воркеров больше не грузятся.
2. **Свидетель билдера** — вывод проверки, а не пересказ. Объём проверки билдера и канон пачки — `docs/TESTING.md` «Что запускать по своей правке» (D-0056); что прикладывается критику и каким бывает его
   контрольный перепрогон — `.claude/agents/critic.md` rule 21; какие тесты пишутся и
   какие нет — `docs/TESTING.md` (три слоя: сценарии на артефактах настоящих прогонов, стыки данных,
   таблицы случаев; теста на каждую строку и мелкую функцию нет; объём считает `tools/test_volume.py`). Форма отчёта — правило 7
   `.claude/agents/builder.md`, содержание — его правило 4.
   CI, канон пачки, слияние и запасной локальный прогон — `docs/RUNBOOK.md` §7.
   Диспетчеру: цикл ожидания в диспатче — один на раунд, с капом, и только на то, что нельзя прочитать иначе
   (вопрос драйвера; пайплайн — только интегратору, «Командная работа» п. 13); диспатч интегратору или билдеру,
   требующий большего локально, — дефект координатора.

### Пакет: доказанность, эталон, смысл

3. **Доказанность.** Правка поведения роли считается доказанной только живым прогоном роли
   (FR-33); до прогона пункт бэклога закрыт кодом, но не проверен.
4. **Бэклог.** — правило: § Бэклог и находки
5. **Шаг, переведённый из роли в код, сверяется с эталоном.** Код не мыслит и молча теряет то, чего
   не предусмотрел. Поэтому любой шаг, который делает код вместо роли (снимок тикета, brief pack,
   `manifest_from_tests`, `probe_by_code`, гейты выхода), сверяется с артефактами LLM-прогонов той же
   задачи: `experiments/measurers/stage_compare.py <stage>`, результат — в тетради эксперимента
   (`experiments/<эксп>/`). Любое «меньше, чем у LLM» — стоп и разбор, а не «идём
   дальше». Для будущего переноса шага: сначала эталон, потом код.
6. **Спека, меняющая смысл, проверяется до кода.** Если спека или правка спеки между попытками меняет
   СМЫСЛ поля, условия или гейта (что значит хэш, какая расписка считается, что считается косметикой):
   (а) посылка про данные сначала измеряется на реальных данных — одна команда, результат в спеке;
   (б) текст правки проходит критика на план до билдера — правка между попытками такая же спека
   (правило 3 `COORDINATOR.md`), приёмка проверяет не только то, что края названы, но и то, что каждый
   решён верно; (в) взятая готовая функция в новой, более ответственной роли (советчик → гейт)
   получает в спеке направление допустимой ошибки и неудобные входы, написанные до отправки; (г) новое
   решение владельца открывает новый узел графа, а не вливается в работающую задачу. Цена: один
   прогон критика на план на такую правку. Детектор: журнал — два `rejected` с `failure_class: spec`
   на одном task_id означают, что правило пропущено. Держится на дисциплине, код-гейта нет.

## Как разрабатывается новая идея владельца

Слово владельца 11.11.2026. Новая идея — то, что меняет логику или архитектуру фабрики, а не узел уже
принятого плана; мелкая правка идёт обычным путём без этих шагов. Порядок:

1. **Лид понимает идею.** Вопросы о самом замысле задаются владельцу сразу, можно до разведки. Шаги 1–4 могут идти в сессии
   Архитектора (большое владелец обсуждает сначала с ним; D-0067); шаги 5–8 — маршрутизация лида, как обычно.
2. **Разведка скаутами**: как это устроено сейчас; если владелец дала другие фабрики — отдельный скаут по ним
   (два прохода, правило 1 `COORDINATOR.md`).
3. **Вопросы о нестыковке** идеи с текущей реализацией, архитектурой или принципами — после разведки, но ДО дизайна.
4. **Короткий верхнеуровневый план лида** — владельцу, до дизайнера: что меняется, фазы, какие AR/P затронуты,
   вердикт по каждой оси карты различий (`architecture.md` § A) и с какими идеями и пачками в работе это пересекается (проверка пересечений — здесь, а не после трёх готовых спек).
5. **Дизайнер** прорабатывает план в спеку; развилки возвращает.
6. **Критик на план** — обязателен для новой идеи; его ключи включают соответствие архитектуре (AR-n) и принципам
   (P-n, FR-n). Повторный проход после фикс-раунда — только если правки меняют архитектуру; иначе правки сверяет лид.
7. **Фазы режутся на параллельные потоки** по непересекающимся файлам, каждому билдеру — своя спека. Узкий узел лид
   пишет сам в диспатче (с `dispatch_skipped`), когда дизайнер обошёлся бы дороже.
8. **Код, затем критик кода** (правило 3 `COORDINATOR.md`, один проход на тему).

Детектор: журнал — у идеи `delegated` дизайнеру без предшествующего плана лида, показанного владельцу, или без
критика на план. Держится на дисциплине, код-гейта нет.

## Командная работа (кучки и пачки)

Работа над фабрикой разложена по **кучкам** (темам) и **пачкам** (D-0036) — `plans/piles/<slug>/`: карточка
для людей `README.md`, файлы пачек `batch-N-<slug>.md` (граф узлов), входящие находки `findings/` (файл на
находку). Правила:

### Пачки: взятие, заморозка, зоны, закрытие

1. **Пачку берёт один разработчик** командой интегратора `python tools/piles.py take <slug> <N> --who <кто>`
   на `main`; работа — на ветке `pile/<slug>/batch-<N>` от `origin/main`, в `main` принятое сливает
   координатор одной дорогой `python -B tools/wave.py merge` (п. 12; ручное слияние — запасной путь, его считает
   калибровка), пачку закрывает интегратор (`close <slug> <N> --hash <h> [--url …]`).
2. **Взятая пачка заморожена** — правило: `docs/TEAMWORK.md` § 2 (что меняется во взятой пачке, находка в пачку, строка
   «Содержание»).
   **Находка называет класс фабрики, не правило одного проекта** (P2): не «брать
   фикстуры харнесса», а «принятый при онбординге подход проекта не применён» (какой роли не хватило ссылки); в брифах —
   ссылки и доступ к знаниям онбординга, не копии текста. Перед «что сделать» — `grep` по `DECISIONS.md` и
   `docs/DECISIONS_ARCHIVE.md` на тему.
3. **Зоны файлов пачек «в работе» не пересекаются** — правило: `docs/TEAMWORK.md` § 3. При общем файле поздний узел сливает `main` в своё
   дерево и решает конфликт сам (пины обеих сторон зелёные), критик у него один — после слияния; зависимость по замыслу спеки остаётся
   последовательной. Пачки одного разработчика друг друга не держат (владелец, 13.11.2026).
4. **`plans/BACKLOG.md` заморожен** — правило: `docs/TEAMWORK.md` § 4. B-id выдаёт только
   интегратор на `main` при сборке пачки; у находки до этого `id: —`.
5. **Общие файлы — один писатель**: журнал — файл на разработчика `logs/journal/<dev>.jsonl`, пишут его только
   `tools/journal_write.py` и хуки, не руками (владелец, 14.11.2026; слаг из
   неотслеживаемого `tools/dev.config.yaml`; старый журнал до 08.10 — только чтение, в истории репозитория);
   `CURRENT_CONTEXT.md` — только состояние `main` (≤ 10 КБ), ход пачки — раздел «Ход» её файла;
   `DECISIONS.md` пишет только Lead владельца или Архитектор (D-0067) — предложение решения другим разработчиком идёт находкой
   с «Решение владельца нужно: да»; CHANGELOG пакета — фрагменты `changelog.d/` (п. «Релиз»).
6. **Слово владельца — только от владельца**: решения в карточке и пачке подписываются
   «владелец, дата» или «Lead пачки, дата». Перед тем как опереться на «решил владелец» в документе чужой ветки, проверить,
   что это сказано в сессии с владельцем; если нет — это предложение того разработчика (сессия второго разработчика пишет

## Что решать самому, что спрашивать у владельца

Чисто технические решения принимаются и исполняются без вопроса, но каждое явно подсвечивается в
ответе («решила сама: …»), чтобы владелец мог остановить или откатить. На решение владельцу (оператору сессии)
выносится только то, что знает он: риски продукта и процесса, приоритеты, деньги, внешние
коммуникации, бизнес-контекст и договорённости команды. Неясное требование — по-прежнему вопрос
владельцу (правило 11a в `COORDINATOR.md`): толкование замысла — не техническое решение.

**Владелец ушла спать или отошла — блокирующих вопросов нет**: вопросов с остановкой нет (`AskUserQuestion`
не вызывается), работа не ждёт ответа: развилка решается рекомендованным вариантом или самым безопасным
обратимым, помечается «решила сама» / «по рекомендации, до слова владельца», записывается в спеку и в
утренний отчёт списком, чтобы владелец могла отменить. Ждут утра только необратимое и исходящее: PR и релиз
в `QAFactory`, настройка хоста или гейтвея, деньги.
